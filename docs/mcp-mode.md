## 1. Why

The one-shot CLI starts a process, connects, logs in and sets up the session on every call, which costs about 150–250 ms on a LAN; on the dev LAN about 195 ms, 150 ms of it SQL Server 2025's login (docs/notes/connect-latency.md). An agent with limited context commonly makes several queries across turns, so that cost repeats on every one.

`sqlh mcp` runs as a long-lived stdio server instead:
- **Speed:** connections stay open, so a call costs one round trip plus execution. Measured 2026-10-17 (§9): a `SELECT 1` call took 223 ms the first time (its connect 201 ms) and 9–11 ms on each of the next seven.
- **Native tools:** harnesses such as Claude Code discover the tools natively, with schemas and descriptions.
- **Lifecycle and cancellation belong to the harness:** it starts sqlh with the session and ends it with the session, and cancels a call in the protocol (decision 14).
- **Read-only:** every tool is a read, in the rolled-back wrapper with the guard (decision 16), so a harness can allow the tools freely.
- **In the same exe, and free when unused** (decision 20): `sqlh mcp` is a subcommand of `sqlh.exe`. Its code runs only when a harness launches `sqlh mcp`, so using sqlh only as a CLI costs nothing for it at run time: no startup time, no memory, no open connections. The cost is on disk: 309.0 KiB as built, within decision 20's gate of 350 KiB, as the owner amended it on 2026-10-18 after the R35–R39 fixes took MCP past the first 300 KB (§8).

Fast cancellation and retry are essential; bulk analytics throughput is secondary. Exact total row-count usefulness remains unresolved, so the CLI's counting semantics (decision 6) carry over unchanged rather than becoming a new MCP requirement.

## 2. Protocol

**Revision.** The server is **dual-era**:
- It serves modern **2026-07-28** clients statelessly: per-request `_meta`, and no handshake.
- It also serves legacy clients that open with `initialize` (2025-11-25 and 2025-06-18), because harness support lags each spec revision. 2025-03-26 isn't served: it obliges a server to take JSON-RPC batches, which sqlh doesn't.

**The era is picked per request** (`protocol::era_of`), from the request's own `params._meta`:
- **Modern** when `_meta["io.modelcontextprotocol/protocolVersion"]` is `"2026-07-28"`. `_meta` must then also hold `io.modelcontextprotocol/clientCapabilities` as an object, or the request gets `-32602`, as the spec requires of a malformed request.
- **Another version string** gets `UnsupportedProtocolVersionError`: code `-32022`, message `Unsupported protocol version`, with `data.requested` and `data.supported`, which lists every version sqlh serves, `["2026-07-28", "2025-11-25", "2025-06-18"]` (the legacy ones are reached through `initialize`, not through `_meta`). A version that isn't a string is `-32602` (`Invalid params: _meta io.modelcontextprotocol/protocolVersion must be a string`), whatever was agreed; so is the modern version without the capabilities (above, `Invalid params: _meta needs io.modelcontextprotocol/clientCapabilities`).
- **`_meta` itself is checked first, in both eras** (`protocol::check_meta`, called by `era_of` and by `initialize`; R39, `6e1a6e7`, the log level since `4663978`). Present, it must be an object (`Invalid params: _meta must be an object`, for `5` and `null` too), and the members 2026-07-28's `RequestMetaObject` declares must have their types: `progressToken` a string or a number (`Invalid params: _meta progressToken must be a string or a number`); `io.modelcontextprotocol/clientInfo` an `Implementation`, an object whose `name` and `version` are strings (`Invalid params: _meta io.modelcontextprotocol/clientInfo must be an object with name and version strings`); and `io.modelcontextprotocol/logLevel` (declared, and deprecated by SEP-2577; sqlh sends no log notifications, so it only checks it) one of the eight `LoggingLevel` strings (`Invalid params: _meta io.modelcontextprotocol/logLevel must be one of debug, info, notice, warning, error, critical, alert, emergency`: `5`, `null`, `verbose` and `INFO` are refused). Every other member, an extension's, passes unlooked at. Until `6e1a6e7` a `_meta` that wasn't an object counted as no version (after `initialize`, a `ping` with `_meta: 5` got `{}`), and only the version and the capabilities were checked (the external review's R39); until `4663978` any log level passed (the internal review of the fixes, plan-history.md).
- **No version:** legacy, served by the version `initialize` agreed. An object `_meta` without `io.modelcontextprotocol/protocolVersion` (one holding only the capabilities, say) counts as no version: after `initialize` it is served as legacy, not refused. Before any `initialize` no version is `-32602` (`Invalid params: _meta needs io.modelcontextprotocol/protocolVersion (or start with initialize)`), with one exception: a `ping` with no `_meta` member at all is answered as legacy, since a legacy client may ping before `initialize` (a `ping` whose `_meta` is `5` gets `_meta must be an object`, above).
- **`initialize`** is always legacy. After its id (The order of a request's checks, below) its params are checked (R39, `6e1a6e7`): `_meta` as above, then the three members the legacy revisions' `InitializeRequestParams` requires, `protocolVersion` a string, `capabilities` an object and `clientInfo` an `Implementation`, each refused when left out or mistyped, with `-32602`: `Invalid params: protocolVersion must be a string`, `Invalid params: capabilities must be an object`, `Invalid params: clientInfo must be an object with name and version strings`. A refused one leaves the agreed version as it was. A well-formed one sets (or replaces) the agreed version: the client's `protocolVersion` when sqlh serves it, else 2025-11-25 (an `initialize` asking for 2025-03-26, or 2026-07-28, gets 2025-11-25, and the client decides whether to go on). It doesn't switch the process: a modern request after it is still served as modern (unit test `the_era_follows_the_request_and_initialize`).
- Notifications have no era.

**Transport.** stdio only.
- Messages are newline-delimited JSON-RPC 2.0 on stdin and stdout, and stdout carries nothing else. Logs go to stderr, only with `--verbose`.
- **Threads** (`src/mcp/mod.rs`): stdin is read on a thread of its own, one message per line, at most 4 MB (`MAX_MESSAGE`); a longer line is read to its end, dropped and answered with `-32600` (no id), `Invalid request: a message is at most 4194304 bytes`. A CR before the LF is dropped; after the UTF-8 check, whitespace at either end of a line is dropped (`str::trim`), and a line that is empty or only whitespace is ignored, with no answer. Lines reach the server through a 64-line channel, which the server keeps reading while stdout is behind, until the requests it holds back meanwhile reach their bound (Bounds, below; R35). stdout is written by a thread of its own, each message whole with its line break and then flushed, so responses never interleave; it writes a message in pieces of at most 4 KiB (`WRITE_CHUNK`: 64 KB in `dc24d4b`, 4 KiB since `9b5318d`) and counts the bytes of each as it is taken, which is how the stall rule and the end's flush wait see progress (Bounds and The end, below). With `--verbose`, a third thread writes stderr from a 256-line queue, and a log line is dropped when stderr is behind, so logging never holds the server up while it serves; the end waits for the last lines 0.5 s at most (The end, below). Requests are dispatched, and tool calls run, concurrently on the current-thread runtime (a `LocalSet`).
- **What isn't answered** (`protocol::parse`, `becb56f`), as JSON-RPC 2.0 §4.1 and the MCP base protocol require:
  - **A response:** a message with `result` or `error` and no `method` is ignored whatever its `id` (`null`, which JSON-RPC allows on an error response, or `[1]`) and whether or not it has `jsonrpc`, since it is recognized before either is checked; sqlh sends no requests, so it has nothing to match.
  - **A notification:** `jsonrpc` `"2.0"`, a string `method` and no `id` member. Its `params` are taken as none when they aren't an object (`null` included), so a malformed one goes without them: `notifications/cancelled` with `params` `[3]` is ignored, as the cancellation page asks of an invalid cancel.
  - An empty or whitespace-only line (Threads, above).
  - Until `becb56f` a response whose `id` was `null` got `-32600` and a notification whose `params` wasn't an object `-32602` (round 3, plan-history.md).
- **Malformed messages:** bytes that aren't UTF-8 get `-32700` (`Parse error: not UTF-8`) and text that isn't JSON `-32700` (`Parse error`). A JSON array (a batch) is `-32600` (`Invalid request: JSON-RPC batches aren't supported; send one message per line`), and so is any other non-object (`Invalid request: a message is a JSON object`). An `id` that is present but neither a string nor an integer that `serde_json` reads exactly, an `i64` or a `u64` (Ids, below), is `-32600` (`Invalid request: id must be a string or an integer within 64 bits`), with no id: `null`, an array, a fraction (`1.5`), an exponent form (`1e2`), `1.0`, `-0` (which `serde_json` reads as `-0.0`) and an integer past both 64-bit ranges (`18446744073709551616`, `-9223372036854775809`) among them (R38, `6e1a6e7`; the message was `id must be a string or a number` until then); so is one longer than 1024 bytes as JSON text, its quotes included (`MAX_ID_BYTES`: `Invalid request: an id is at most 1024 bytes as JSON`; `as JSON` since `6e7a0d8`): the measure is the id as `serde_json` writes it again (`Value::to_string`), so a string id of ASCII letters and digits fits in 1,022 characters, and one of 1,023 or 1,024 is refused (round 4's refuted finding 6, plan-history.md). After the id (`protocol::parse` checks in this order), a `jsonrpc` other than `"2.0"` (on any message but a response) is `-32600` (`Invalid request: jsonrpc must be "2.0"`), a message with neither `method` nor `result`/`error` (`{"jsonrpc":"2.0","id":4}`) `-32600` (`Invalid request: a message needs a method`), and a `method` that isn't a string `-32600` (`Invalid request: method must be a string`). A request's `params`, when present, must be an object, `null` included (JSON-RPC 2.0 §4.2 makes it a structured value, and MCP an object): `-32602` (`Invalid params: params must be an object`), with the request's id; only `params` left out is none (`4663978`; until then `null` counted as none, the internal review of the fixes). A notification's that isn't an object, `null` included, is taken as none (What isn't answered, above). An error carries the request's id when it could be read, and otherwise leaves `id` out, as the MCP schema allows; so a message with no `id` member that fails any of these three checks is answered, without an id, since only a message with `jsonrpc` `"2.0"` and a string `method` is a notification (What isn't answered, above): `{"method":"notifications/initialized"}` and `{"jsonrpc":"2.0","method":5}` each get an id-less `-32600`; a malformed request whose id is open gets that id's `-32600` in place of its own error (The order of a request's checks, below).
- **Ids** (R38, `6e1a6e7`; R40, `aa06856`) are strings, or integers within the signed or unsigned 64-bit range, as MCP's base protocol has them (a string or an integer): a string or a number `serde_json` reads as an i64 or u64 is taken as read and echoed exactly in every response to it (`9223372036854775807`, `-9223372036854775808` and `18446744073709551615` come back as sent). **An integer written another way is that integer** (R40): `serde_json` reads `1.0`, `1e2`, `-0` and any number past 64 bits as a float, so such an id is decided from the number as the line writes it, never from the float (`protocol::raw_member` finds the member's text, decoding the names it compares and taking the last of a duplicate, as `serde_json` does; `protocol::exact_integer` shifts the digits by the exponent as text). An exact integer within i64 or u64 is the id, as that integer, and is echoed as it: `1.0` and `1e0` are the request `1`, `1e2` is `100`, `-0` is `0`, `18446744073709551615.0` is `18446744073709551615`. A fraction (`1.5`; `1.0000000000000001`, which a float would round to 1) or a magnitude past 64 bits (`1e20`, `18446744073709551616`) is refused without an id, `-32600` `Invalid request: id must be a string or an integer within 64 bits`: an implementation limit of sqlh's, since MCP asks only for an integer. Until `aa06856` every number `serde_json` didn't read as an i64 or u64 was refused, `1.0`, `1e2` and `-0` among them (the fix verification's R40). **One rule compares ids everywhere** (`protocol::key`, the id's JSON text as `serde_json` writes it again): the calls in flight (`Server::calls`), the requests held back (Bounds, below), the open subscriptions, and a `notifications/cancelled`'s `requestId` against all three. Since only exact ids are taken, two requests share a key only when they have the same id, and `1` and `"1"` are two ids. A cancel's `requestId` is taken by the same rule, so `1e2` names the request `100`; one that isn't such an id (a fraction, or an integer past 64 bits) matches nothing, and the cancel is ignored. An id is at most 1024 bytes (above), so what a call, a held-back request or a subscription holds of it, and every response that echoes it, is bounded. Until `6e1a6e7` any number was taken as `serde_json` read it, so an integer past the 64-bit ranges was rounded before it was checked (`18446744073709551616` and `18446744073709551617` both came back as `1.8446744073709552e+19`, and a subscription under the first refused a `ping` under the second as reusing its id), a fraction was taken, and calls and subscriptions compared ids by different rules (text and value, so `-0` and `0.0` were two call ids but one subscription id): the external review's R38, which round 3 had refuted (plan-history.md). Tested by `ids_are_kept_exactly_and_compared_as_written`, `an_integral_id_is_one_request_however_it_is_written` (R40: a subscription under `1.0` refuses a `ping` under `1` and under `1e0` as reusing its id and answers one under `"1"`; `-0` is `0`; a cancel's `1e2` ends subscription `100`; `1.0000000000000001` and `1e20` refused), and the unit tests `lines_are_requests_notifications_or_errors`, `an_integral_number_is_its_integer_however_it_is_written` and `a_members_text_is_found_as_the_line_writes_it` (§9).

**Bounds on what a client can make the server hold**
- **`MAX_UNWRITTEN` (64): once 64 responses wait for the stdout thread, the server is behind,** and holds requests back instead of dispatching them; stdin keeps being read (R35, `6e1a6e7`). Until then being behind stopped the reading of stdin, so a client that kept stdout open and stopped reading had its cancels and its end of input wait, unread, for stdout to drain (the external review's R35).
  - **A notification is acted on at once,** behind or not: a `notifications/cancelled` reaches a call that is connecting or running while its client reads nothing (process tests `a_cancel_reaches_a_connecting_call_while_stdout_is_unread` and `a_cancel_reaches_a_running_batch_while_stdout_is_unread`, §9).
  - **A request is held back** (`Deferred`), in arrival order, as the bytes it came in, read again when it is let through, so its size is counted exactly. Its id is checked as it arrives (The order of a request's checks, below): a request reusing an open id, and a line refused on arrival (malformed, or over 4 MB), are answered then, the answer held back in the request's place as a finished line. While anything is held back, every new message that gets an answer goes behind it, behind or not, so answers keep the order the requests came in.
  - **When stdout catches up** (fewer than 64 waiting), what is held back goes first, oldest first (`replay`), each request dispatched as it would have been on arrival. While stdout is behind or anything is held back, the serving loop looks again every 10 ms (`POLL`); since `f1d8b51` the poll is armed whenever anything is held back, since one armed only while stdout was behind could leave requests held back up to the 30 s idle sweep, when stdout caught up without waking the loop (the internal review of the fixes).
  - **A request held back counts as open:** one reusing its id gets `-32600`, `Invalid request: a request with this id is still waiting to run`, decided as it arrives; and **a cancel for it drops it**, so it never runs and nothing is sent for it (no `--verbose` line says so). Process test `a_request_held_back_counts_as_open_and_a_cancel_drops_it` (§9).
- **`MAX_DEFERRED` (64) and `MAX_DEFERRED_BYTES` (16 MiB):** at most 64 requests (and answers decided on arrival) are held back, and at most 16 MiB of them; the bytes are checked before a line is taken, so one more message, of up to 4 MB, can take them past 16 MiB. Only once either bound is reached does the server stop reading stdin (the stdin thread then blocks once its 64-line channel is full): from then on a cancel or the end of the input waits unread in that channel until stdout takes enough for the server to stop being behind, and if it doesn't, the stall rule (below) ends the wait. The serving loop still notices a broken stdout, runs the idle sweep and takes console events meanwhile.
- **The stall rule** (`Stall`; R35, `6e1a6e7`): while the server is behind, a stdout that takes no byte for the stall limit means a client that stopped reading without closing stdout, and the server ends as if stdout had broken (`--verbose`: `sqlh mcp: ending (stdout stalled)`): the calls are cancelled and what is held back is dropped (The end, below). The clock starts again whenever stdout takes a piece (Threads, above) and whenever the server stops being behind. **The limit** (`stall_limit`) is the longest of the listed profiles' stall seconds, each the profile's query timeout, as a CLI run's stall limit is (the launch's `-t` when given, else the profile's `query_timeout`, default 60; DESIGN.md §6, exit 7), with a 0, no query timeout, counting as `STALL_WHEN_NO_TIMEOUT`, 60 s: so the limit is never none, and a profile at 0 listed beside one at 120 gets 120 s. The 60 s is the stall rule's alone: a query at `-t 0` still runs without a limit. Debug builds take `SQLH_DEBUG_MCP_STALL_MS` (milliseconds) in its place, so a test needn't wait 60 s; a release build reads no variable. Until `f1d8b51` a 0 on any listed profile meant no stall limit, so at `-t 0` a client that stopped reading behind a full queue of held-back requests (64 answers waiting, then 64 requests or 16 MiB) kept its cancels, its end of input and the server waiting for good (the internal review of the fixes, P2). Tested by `a_client_that_stops_reading_is_taken_for_gone` (`-t 1`: 120 pings, stdin left open, ended within 5 s), the three `..._behind_a_full_queue_at_t_0_ends_within_the_stall_bound` tests (debug builds, `SQLH_DEBUG_MCP_STALL_MS=1000`) and the unit test `the_stall_limit_is_always_finite` (§9).
- **`MAX_IN_FLIGHT` (64):** at most 64 tool calls run at once. One more is answered at once with a tool error, after its id (every request's first check), its era and then its tool name and arguments are checked (so a request reusing an open id still gets only `-32600`, a call that doesn't fit `CallToolRequest` `-32602`, and bad arguments their own refusal; below), and stdin keeps being read, so cancels keep arriving. The answer is the run's usage error, exit 3, in the call's `format`, built as an argument refusal is (`tools::refusal`, §4): `isError: true`, text `-- error: 64 calls are already running; wait for one to finish` then `-- failed (exit 3): usage error, N ms`, or with `format: "json"` the JSON document, `exit_code` 3, `error` `64 calls are already running; wait for one to finish`. A call counts from when it starts until its task ends, so the 64 include cancelled calls still settling, each for up to 5 s after its cancel (`SETTLE_GRACE`, the rollback of its wrapper included, §5), as each keeps its id until then (the open-id check below): just after a client cancels many calls, new ones can get the too-many-calls answer for a few seconds, though nothing is answered for the cancelled ones.
- **`MAX_SUBSCRIPTIONS` (8):** at most 8 `subscriptions/listen` streams are open at once (below); one more is refused with `-32600`.
- So what waits for stdout is bounded too: about 128 responses at most (64 waiting, plus one from each call in flight); at the end, two more lines for each open subscription, its answer and its teardown (below), 16 at most. Their size is bounded as follows. A call's result, and every refusal given as a tool result (an argument refusal, §4, and the too-many-calls answer), is held to the launch's `--max-output` (`Server::limits`, the launch limits, which hold the same `--max-output` for every profile, since no profile key sets it), shortened as a run's closing error is (DESIGN.md §4.4). That bounds the tool's text, not the line: the line queued for stdout carries the text JSON-encoded inside the JSON-RPC result (`protocol::result_line`), where each tab, newline, quote and backslash takes two bytes (the text and JSON formats escape every other control character themselves, so no byte takes more). Text results are tab-separated and newline-terminated, and JSON ones are full of quotes, so a queued line can be up to about twice `--max-output`, plus the id and the envelope: at the default of 1,000,000 bytes, about 128 lines of up to about 2,000,000 bytes each in the worst case. A name the client sent that a refusal or an error shows (the tool in `Unknown tool: X`, the method in `Method not found: X`, an unknown argument, a profile) is cut after 100 characters, with `…` (`tools::echo`; the method's since `becb56f`). The request's id, echoed in every response to it (and in a subscription's acknowledgement, answer and teardown), is at most 1024 bytes (`MAX_ID_BYTES`, above; unbounded below the message limit until `becb56f`). What is echoed whole, bounded only by the 4 MB message limit, is an unsupported version, in `-32022`'s `data.requested`: the schema defines it as the version the client requested, so it goes back as it came. Probed at `05032c0` with `--max-output 4096`: an argument refusal for a 3 MB unknown argument name was a 467-byte line, `Unknown tool: X` for a 3 MB tool name 178 bytes, and `Method not found: X` for a 3 MB method name 3,000,079 bytes, which `becb56f` cut (`an_open_id_gets_only_its_refusal` sends a 300-character method and gets `Method not found: ` and its first 100 characters, then `…`).
- **Open subscriptions** (`subscriptions/listen`, below) are not counted by `MAX_UNWRITTEN` or `MAX_IN_FLIGHT`, but by their own cap: at most 8, each holding its request id (at most 1024 bytes) until the client cancels it or the server ends.
- **In all,** what a client can make the server hold is bounded by these counts: the stdin channel's 64 lines of up to 4 MB each (it fills only once the requests held back are at their bound), the requests held back (16 MiB, plus one message), about 128 responses waiting for stdout and the answers held back, 64 calls in flight (each with up to 1 MB of SQL, and its result within `--max-output`) and 8 subscriptions' ids. These are upper bounds, hundreds of MiB at the default caps by the external review's estimate, not measured peaks; an adverse concurrent workload should be measured before any of them is raised.

**The end** (`mcp::end`; every wait in it but the last, for the `--verbose` lines (`flush_log`, below), is `End::wait`, which looks at what it waits for every 10 ms and takes console events meanwhile)
- **stdin closes** (or fails): first the requests still held back (Bounds, above) run as stdout drains (`replay`), for as long as stdout keeps taking bytes. This wait has no limit of its own, since a client that reads steadily, however slowly, is still being answered; the stall rule (always finite, above) ends it for a client that stops reading (`--verbose`: `sqlh mcp: stdout stalled during the end`; the client is then taken for gone, as when stdout breaks), and a console event drops what is left (below). Then, nothing being held back, the calls in flight get up to `END_GRACE`, 6 s, to finish and answer, so a client that pipes its requests and closes stdin gets its results; the answers still queued for stdout at that point (up to `MAX_UNWRITTEN`, 64) get the flush wait's `END_GRACE` at most (Then, below), as before R35, so a reader too slow to take them in 6 s loses the rest, which `--verbose` counts (the follow-up review measured 120 answers of about 2 KB read at 12 KB/s: 31 never written; refuted as a regression, kept as built). What is still running then is cancelled (nothing is sent for it) and gets up to 6 s more to settle. Until `f1d8b51` `END_GRACE` ran from the end of the input, the held-back requests' dispatch charged to it, so a steady slow reader with more than about 6 s of answers to take lost what was still held back when it ran out, with no sign of the loss (the internal review of the fixes; process test `a_steady_slow_reader_gets_every_answer_after_stdin_closes`, §9: 135 requests, 64 of them held back, the call among them, read at most 12 KB/s: every one answered).
- **stdout breaks** (a write or flush fails) **or stalls** (the stall rule, while serving): the client is gone, or taken for gone. The stdout thread reports a break through a flag and a wake-up outside the stdin channel, so it is noticed even while stdin is unread behind a full queue; from then on nothing is queued for stdout, the calls in flight are cancelled at once and get up to 6 s to settle, and what is held back is dropped.
- **A console event** (Ctrl+C, Ctrl+Break, the console closing, logoff, shutdown) ends the serving the same way, the calls in flight cancelled at once and what is held back dropped, and **so does one at any step of the end** but that last wait (R36, `6e1a6e7`): an event that comes after the end began, because stdin closed or stdout broke or stalled, is logged (`sqlh mcp: EVENT during the end`) and cuts what is left at once. **The end has one deadline** (`End`): an event sets it to the earlier of the one already set and now plus the event's grace, `Signal::grace`, as for the CLI's cancelled work (DESIGN.md §4.3): 2 s after Ctrl+C or Ctrl+Break, and 1 s after the console closing, logoff or shutdown, since Windows ends the process about 5 s after one of those. So a later event can bring it nearer and never puts it off. Every later wait ends at that deadline, but the flush wait (below), which gets up to `FLUSH_WAIT` (1 s) past it for the closing writes (the subscriptions' answers and teardowns, and the last answers): the end takes about 2 s at most after a close, logoff or shutdown, and about 3 s after Ctrl+C or Ctrl+Break, counted from the event, within Windows' 5 s, the process's exit included (Last, below), with up to 0.5 s more for the last `--verbose` lines when stderr isn't taking them (below). Without an event each wait is bounded by `END_GRACE`, but the held-back requests' (above). Until `6e1a6e7` events were listened for only while serving: once stdin had closed or stdout broken, an event wasn't received, though the listener kept Windows' default handling off, so Ctrl+C did nothing, and a close, logoff or shutdown left the `END_GRACE` waits standing, up to about 24 s, so Windows could end the process before the last answers and teardowns were written (the external review's R36, which reproduced 5.64 s after a Ctrl+Break 400 ms after stdin closed). Tested by `ctrl_break_after_stdin_closed_ends_the_server_at_once`, `ctrl_break_during_the_last_writes_ends_them_within_its_grace` and the unit test `a_close_logoff_or_shutdown_during_the_end_bounds_it_by_its_grace`, which plays the close, logoff and shutdown no test can send (§9).
  - **Only with its listeners.** If they couldn't be installed at startup, the server runs without them (and says so with `--verbose`, since `dc24d4b`), and a console event gets Windows' default handling instead of this end (§3, Startup failures).
- **Then** what is still running is cancelled and gets up to `END_GRACE` (or the deadline) to settle, and what is still held back is dropped, never run (counted in the `--verbose` line below, never logged as a client's cancel); each open subscription is answered and torn down (below; when stdout broke or stalled, nothing is sent); the idle connections are closed (`Engine::close_all`, given at most `END_GRACE`, or the deadline, console events taken meanwhile); and the last responses get time to reach stdout. **The flush wait** ends once every line queued for stdout has been written, or when stdout breaks, or after `FLUSH_WAIT` (1 s) in which no byte reached stdout, or at `END_GRACE` (6 s) in all; after an event, at the deadline, but never sooner than `FLUSH_WAIT` after it began. It is an async wait (`End::wait`), so it takes console events too. Until `6e1a6e7` it was a loop of `thread::sleep`, which couldn't, and it waited for the stdout thread to finish, which each call's task held up until it ended (the task holds the server, and with it the sender to the stdout thread), so a cancelled call still settling kept the flush waiting after the last line was out. After a console event the grace is shorter than a call's own `SETTLE_GRACE` (5 s, §5), so a call cancelled by the event can still be settling when the end is done; it is dropped with the runtime (Last, below). **Progress is counted in bytes** (`dc24d4b`): each piece of at most 4 KiB that the stdout thread hands to stdout (64 KB in `dc24d4b`; `9b5318d` made it 4 KiB, as the CLI's writer has it, R11, so a reader that takes 4 KiB a second is seen to progress) (Threads, above) starts the 1 s again, so a long last response that a slow reader is still taking in is written whole, up to the grace, while for a client that has stopped reading the wait ends after 1 s in which stdout took no piece: 1 s after the last piece it took during the wait, or 1 s after the wait began when it took none (a client that stopped reading before the wait began, whose last piece can be seconds older: the end's earlier waits, and any time before stdin closed, come first). Until `dc24d4b` the wait counted whole lines, so a line that took the client longer than 1 s to read was cut off at `FLUSH_WAIT`, well inside the grace: a 2,000,000-byte line read 64 KB every 50 ms got 1,179,648 bytes through, no line whole, and the process exited about 1.1 s after stdin closed (round 5's second half, finding 2, plan-history.md; process test `a_slow_reader_gets_a_long_last_response_whole`, `a_steady_slow_reader_is_not_taken_for_stopped` (4 KB every 100 ms, a 200 KB line: both answers whole; fails with 64 KB pieces), §9). With `--verbose`, responses that were never written are counted: `sqlh mcp: N responses were never written (M for requests that never ran)`, N the lines still waiting for stdout (a line still being written when the wait ends among them) plus M, the requests (and answers decided on arrival) held back that the end dropped; the parenthesis only when M isn't 0 (`6e1a6e7`). For 120 pings sent to a server whose stdout is never read: `120 responses were never written (56 for requests that never ran)`, 64 waiting and 56 held back (process tests `the_end_of_input_ends_the_server_with_stdout_unread`, `a_client_that_stops_reading_is_taken_for_gone`). **Requests the server never read aren't counted:** those left in the stdin thread's 64-line channel, or in the pipe, when it stopped reading behind a full queue (`MAX_DEFERRED`, Bounds, above) and then ended (by the stall rule, a broken stdout or a console event) get no answer and no count, so N can fall short of the requests left unanswered: 130 pings behind a full queue log `128 responses were never written (64 for requests that never ran)`, the last two never read (the `..._behind_a_full_queue_at_t_0_ends_within_the_stall_bound` tests, §9).
- **Then the last `--verbose` lines** get up to `delivery::SIDE_WAIT` (0.5 s), the CLI's bound for its own `--verbose` lines (DESIGN.md §4.3), to reach stderr (`flush_log`: the flush is an empty line, which no log line is, since `Server::log` drops one, and the stderr thread answers it through a `Notify` once every line handed over before it is written; the channel carries `String`s, as stdout's does, so the two share one copy of the channel code, where a message type of its own made the exe 8 KB larger). A stderr behind by more than the log channel's 256 lines has its lines dropped as before, and isn't waited for. This wait takes no console events, the one in the end that doesn't: by then nothing is left to cut, and every event's grace is longer than its 0.5 s, which the bounds above include. Until `32c82d5` (plan-history.md, CI failure after the push of `ef321ab`) the end didn't wait for them, but for 50 ms after the `never written` line, so a process could exit with lines still queued: on CI, a client gone at once (stdout closed) ended the server before `sqlh mcp: ending (stdout closed)` was written, failing `a_gone_client_ends_the_server_with_stdin_still_open`.
- **Last, the runtime is shut down without waiting** for what it still runs (`mcp::run`: `serve` returns, the `LocalSet` is dropped and `runtime.shutdown_background()` is called, `6e7a0d8`), and the process exits 0. What it abandons is a name lookup the driver left on a blocking thread (`tokio::net::lookup_host`, for a call cancelled while its connect resolved the server's name), which dropping the runtime would have waited for with no bound, after every response was flushed and the idle connections closed. Measured with an unresolvable single-label server name, a call cancelled 50 ms after it started and then stdin closed: at `becb56f` the process exited 1.2 to 2.6 s after `sqlh mcp: ending`, at `6e7a0d8` 15 to 45 ms after it (round 4, finding 5, plan-history.md). No process test covers it. The CLI does the same since `dc24d4b`: `app::run_command` calls `runtime.shutdown_background()` once the run, its delivery and its `-o` publication are over, so a lookup left behind by a cancelled connect doesn't hold its exit either (DESIGN.md §4.3); not measured in the CLI, and no test plays it. A call still settling when the grace ran out (after a console event, Then, above) is dropped with the `LocalSet`, where it stands: its connection is closed, with no `put_back` rollback (the server rolls back a closed session's open transaction itself), and nothing is sent for it, as for any cancelled call (unit test `a_close_logoff_or_shutdown_during_the_end_bounds_it_by_its_grace`: the call, whose attention the fake server never acknowledges, is still running when the end returns, and its connection is closed once the runtime lets it go).
- **`--verbose` lines** (profiles named as the profiles file spells them, §3): `sqlh mcp: serving A, B`; `sqlh mcp: request ID cancelled`, ID the id's JSON text (`request "abc" cancelled` for a string id), only when the cancel finds a call still running and not yet cancelled (none for a subscription the client cancels, a request held back that the cancel drops, or an unknown, finished or already cancelled id); `sqlh mcp: TOOL on PROFILE: exit N in N ms` (with ` (cancelled)` after the exit code for a cancelled call), only for a call that started (its task was spawned): an argument refusal and the too-many-calls answer get no line, while a refusal the run makes, such as SQL over 1 MB or a `GO N` past 1000, gets one; `sqlh mcp: ending (REASON)`, the reason `stdin closed`, `stdout closed`, `stdout stalled` (the stall rule, Bounds, above) or the console event (`Ctrl+C`, `Ctrl+Break`, `the console closing`, `logoff`, `shutdown`); during the end, `sqlh mcp: stdout stalled during the end` (the stall rule, after stdin closed) and `sqlh mcp: EVENT during the end`, EVENT one of those console events' names (`6e1a6e7`); `sqlh mcp: N responses were never written (M for requests that never ran)` (above); and, at startup, after `serving`, `sqlh mcp: console events can't be watched (E); Ctrl+C ends the process at once` when the listeners can't be installed (§3, Startup failures; `dc24d4b`).

**Modern behavior (2026-07-28)**
- **`server/discover`** (mandatory) returns:
  - `supportedVersions: ["2026-07-28", "2025-11-25", "2025-06-18"]` (the legacy ones through `initialize`)
  - `capabilities: {"tools": {}}`
  - `_meta["io.modelcontextprotocol/serverInfo"]: {name: "sqlh", version}`
  - `instructions` (§6)
  - `ttlMs` (3,600,000: an hour) and `cacheScope: "private"`. The instructions name the local profiles, so shared caches must not keep them.
- **Every modern result** carries `resultType: "complete"` and our `serverInfo` in `_meta`.
- **`tools/list`** returns the tools in a fixed order, with `ttlMs` and `cacheScope: "private"`. The set is the same for every launch with the same profiles (§4), never dependent on earlier calls, as the spec requires. It is one page: a request with a `cursor` gets `-32602`, `Invalid params: cursor must be a string` when it isn't one (R39, `6e1a6e7`) and `Invalid params: no such cursor` when it is.
- **`notifications/cancelled`** for an in-flight `tools/call` cancels it with a TDS attention through the call's `Cancel`. Afterwards nothing is sent for that request id: the stdio binding says a server MUST NOT send further messages for a cancelled request (the cancellation page says SHOULD). **The id stays taken until the cancelled call has settled:** any request that reuses it meanwhile, whatever its method, gets only `-32600` (`Invalid request: a call with this id is still running`), as does one that reuses the id of any call still running (below). A cancel for an open subscription ends it (below), and one for a request held back drops it (Bounds, above). A cancel is acted on as it arrives, even while stdout is behind (R35). A cancel for an unknown, finished or already cancelled id, or whose `requestId` no open request has (Ids, above), is ignored.
- **The order of a request's checks** (`mcp::arrive`, `mcp::request`; `arrive` replaced `dispatch` in `6e1a6e7`):
  - **The id first, for every method** (`mcp::in_use`: at the top of `request`, and in `arrive` for a request held back and for a malformed one): a request reusing the id of a call still running (or cancelled and still settling), of an open subscription or of a request still held back gets only `-32600`, `Invalid request: a call with this id is still running`, `Invalid request: a subscription with this id is still open` or `Invalid request: a request with this id is still waiting to run`, whatever its method, `_meta` or `params`. While the server is behind, that is decided as the request arrives, and the refusal waits its turn among what is held back (Bounds, above). So an `initialize` reusing one leaves the agreed version alone, and a `ping`, a `tools/list` or an unknown method gets no answer of its own under it. A malformed request whose id can be read and is open (a `params` that isn't an object, `null` included, a `jsonrpc` other than `"2.0"`, no `method` or one that isn't a string) gets the same `-32600` in place of its own error (`arrive`). No id is answered twice while it is open, whatever a client sends.
  - **Then** an `initialize`'s own checks and its answer (it has no era; above), and every other request's era (above: `_meta` checked first, `-32602` when it or a declared member is malformed, whatever was agreed; then no version, which includes an object `_meta` without one, is `-32602` before any `initialize`; a version that isn't a string, or the modern one without capabilities, is `-32602` whatever was agreed; an unsupported version `-32022`).
  - **Then the method's own checks** (R39, `6e1a6e7`): a `tools/call`'s envelope, tool name and arguments (`tools::plan`, §4), then the 64-call limit (above); a `tools/list`'s `cursor` (above); a `subscriptions/listen`'s filter (below), then the 8-subscription cap. A malformed envelope gets `-32602` before anything is allocated: no call starts, no connection is taken and no subscription opens. Members a method's schema doesn't declare are never looked at, so an extension's pass. The messages read `Invalid params: MEMBER must be WHAT` (`notifications.toolsListChanged must be true or false`). Until `6e1a6e7` only a `tools/call`'s tool name and `arguments` (`null` counting as none) and a `listen`'s `notifications` (left out, it asked for nothing) were checked (the external review's R39). Tested by `method_envelopes_are_checked_before_anything_runs` (§9).
  - Tested by `an_open_id_gets_only_its_refusal` (§9): with a subscription open under id 5, a `ping`, a `tools/list`, a `subscriptions/listen` with `notifications: 3`, an `initialize`, a `ping` with `params` `[1]` and the method `nope`, each with id 5, got six `-32600`s and nothing else under it. Until `becb56f` only `tools/call` and a modern `subscriptions/listen` checked open ids, after the parser's checks and the era (and `listen` after its `notifications` too), so a client reusing an open id could get a second response under it (probed at `05032c0`: eight answers under one subscription's id, and its closure at the end; round 3, finding 1, plan-history.md). Only a client that breaks MCP's rule against reusing an open id meets the check.
- **`subscriptions/listen`** (the subscriptions page) is acknowledged at once, with the subset of what it asks for that the server honors, which is none: sqlh's tool list never changes during a server's life, and it has no prompts or resources. The acknowledgement is a notification, `notifications/subscriptions/acknowledged`, with `params` `{"_meta": {"io.modelcontextprotocol/subscriptionId": ID}, "notifications": {}}`, ID being the request's id.
  - **It stays open, holding its id:** any request with that id (compared by its key, the id's JSON text: Ids, above), whatever its method, gets only `-32600` (`Invalid request: a subscription with this id is still open`; The order of a request's checks, above).
  - **At most 8 are open at once** (`MAX_SUBSCRIPTIONS`): sqlh honors none of their notifications, so a few are plenty, and each holds its id until it ends. One more is refused with `-32600`, `Invalid request: at most 8 subscriptions may be open; cancel one first`, and isn't acknowledged; a cancel frees a place.
  - **It ends** silently on `notifications/cancelled` for its id, compared the same way (nothing is sent for it). **When the server ends** (The end, above), each open one, in the order they were opened, gets two lines (`mcp::end_subscription`): an answer, a result with `resultType: "complete"` and `_meta` holding `io.modelcontextprotocol/subscriptionId` (and `serverInfo`, as every modern result), so the client can tell a graceful end from a dropped transport (the subscriptions page's Graceful Closure, which has the answer sent before the stream closes); then the teardown, `notifications/cancelled` with `params` `{"requestId": ID, "reason": "the server is ending"}`, which the cancellation page requires: a server MUST send it, referencing the `subscriptions/listen` request's id, when it tears that stream down (on stdio, the one use a server makes of that notification). sqlh sends `notifications/cancelled` for nothing else.
  - **Its filter is checked first** (the `SubscriptionFilter`, R39, `6e1a6e7`): `notifications` is required, and left out or not an object it is `-32602`, `Invalid params: notifications must be an object`; of its members, `toolsListChanged`, `promptsListChanged` and `resourcesListChanged` must be booleans (`Invalid params: notifications.toolsListChanged must be true or false`, `null` refused too) and `resourceSubscriptions` an array of strings (`Invalid params: notifications.resourceSubscriptions must be an array of strings`), and an extension's members pass. A malformed filter takes no place among the 8 and is neither acknowledged nor answered at the end. Until `6e1a6e7` a `listen` without `notifications`, or with `toolsListChanged: "yes"` or `resourceSubscriptions: [1]`, was acknowledged and took a place (the external review's R39). It is a 2026-07-28 method: in the legacy era it gets `-32601`.
  - Tested by `a_subscription_is_acknowledged_and_answered_at_the_end`, `an_open_id_gets_only_its_refusal` and `a_legacy_session_initializes_and_calls` (§9). Until `e8175d4` it got `-32601` in both eras, which the self-review found departs from the base protocol, where subscribe-and-notify is among the patterns every implementation supports; until `05032c0` the server's end sent only the answer, which the second round found misses the cancellation page's MUST, and nothing capped how many were open (plan-history.md, Phase 5.2 and 5.3).

**Legacy behavior (initialize-based revisions)**
- `initialize` gets back the negotiated `protocolVersion` (above), `capabilities: {"tools": {}}`, `serverInfo` and `instructions`.
- `notifications/initialized` is accepted.
- `ping` is answered, with `{}` in the legacy era (in both eras: harmless in the modern one, where the method was removed).
- Legacy results carry no `resultType`, `_meta`, `ttlMs` or `cacheScope`. Everything else is shared with modern mode.

**Not implemented**
- Resources, prompts, completion and list-changed notifications: the tool list is fixed for the life of the process, so a subscription is acknowledged with none of them (above).
- Sampling, roots and logging: all deprecated in 2026-07-28.
- MRTR/elicitation: there's nothing to ask the user mid-call.
- Tasks (an extension in 2026-07-28, not core).
- Progress: a request's `_meta.progressToken` is ignored (only its type is checked, above) and no `notifications/progress` is sent; a call's result comes whole when it ends.

Unknown methods get `-32601` (`Method not found: X`, X cut after 100 characters with `…`, `tools::echo`).

## 3. Launch and configuration

```
sqlh mcp --profile NAME [--profile NAME ...] [--max-rows N] [--max-cell N] [--max-output N] [-t seconds] [--pool N] [--idle MINUTES] [--verbose]
```

**The profiles listed are the server's whole reach** (decision 18). Each tool takes a `profile`, which must be one of them. With one listed it is optional, and the default. With several, every tool's schema lists `profile` in `required`, and a call without one is refused as a tool error (§4): `-- error: invalid arguments for query: missing required property profile: one of A, B`, exit 3. A profile not listed can't be reached, whatever a tool call asks.

**A profile is named as the profiles file spells it.** The launch's `--profile` finds a profile in any (ASCII) case, as the CLI's does (`config::find`), and `mcp::resolve` then takes the file's spelling, which is what the `profile` enum (§4), the instructions (§6) and the `--verbose` lines (§2) show. A call's `profile` matches a listed one in any ASCII case too, as the launch's does (`tools::plan`, `eq_ignore_ascii_case`, since `becb56f`); a client that checks its arguments against the schema's enum sends the file's spelling anyway. Probed at `05032c0`: the file's `Other`, launched as `--profile other`, is listed as `Other` (enum `["win", "Other"]`, `Profiles: win; Other.`, `serving win, Other`), and a call with `profile: "other"` was then refused (`profile other isn't one of win, Other`); since `becb56f` it reaches `Other` (unit test `calls_are_checked_against_the_schema`: `Reporting` reaches `reporting`). A name that matches none is refused, `-- error: invalid arguments for query: profile X isn't one of A, B`, exit 3, with X cut after 100 characters (`tools::echo`).

Strict separation stays possible: a profile can get its own server entry, listed alone, so the harness gates it separately.

**Connection settings are fixed at launch** by the profiles (and, for what a profile leaves unset, the server's environment, below), exactly as for the CLI. No tool argument can name a server, a login or a password. That prevents a prompt-injected agent from pointing the server at another host or harvesting a password (DESIGN.md §8).

**Each listed profile is resolved at launch** as a CLI run's would be with the launch flags (`--max-rows`, `--max-cell`, `--max-output` and `-t` over the profile's own settings), its password from Credential Manager as usual, and then made read-only (`mcp::resolve`):
- Writes are off whatever its `write_policy` (decision 16): `--allow-write` isn't accepted, and a profile whose `write_policy` is `allow` still gets only read tools, its refusals worded for MCP (`guard::WritesOff::Mcp`).
- The output's advice, and the limits it names, are worded for MCP (`output::Advice::Mcp`, §4), and a failed connect's hints name the profile's keys (`db::Hints::Profile`, §4).
- **A profile's `read_uncommitted = true` holds, even when its `write_policy` is `allow`.** The CLI drops it in a run that can write, so no write rests on a dirty read (DESIGN.md §4.2); no MCP call can write, so here the profile's choice applies. `check` never reads uncommitted.
- The profile's `exact_count`, `lock_timeout` and `query_timeout` apply as in the CLI. A `query` call can also ask for exact counting itself (`exact_count: true`, §4, decision 45).
- **What a profile leaves unset comes from the server's environment,** as in the CLI (`config::resolve`, DESIGN.md §4.2's precedence): its server from `SQLCMDSERVER`, its database from `SQLCMDDBNAME`, and a SQL login's password from `SQLCMDPASSWORD` when Credential Manager holds none for the profile (or the profile names no server, so its stored password isn't sent). They are read once, at launch, from the environment the harness started sqlh with; no call reads them. A profile without `server` and no `SQLCMDSERVER` connects to `.`, the local default instance. Where the password came from `SQLCMDPASSWORD`, the 18456 hint (§4) still says `check the profile's login and its saved password (sqlh profiles add)`, as built.

**Launch rules.**
- **`sqlh mcp` must be the first argument.** `sqlh --profile x mcp` isn't a `sqlh mcp` launch: it is the CLI's own usage error (where it would have run `mcp` as SQL), on stdout in the text format, with stderr empty and exit 3: `-- error: mcp must come first: sqlh mcp ...` then `-- failed (exit 3): usage error (see sqlh --help), 0 ms`.
- **`sqlh mcp --help`** (or `-?`) prints sqlh's `--help` on stdout and exits 0, before the console check below and before any profile is read (when it comes ahead of any refused argument): the one `sqlh mcp` invocation whose stdout isn't protocol.
- **Refused:** no `--profile`; a profile listed twice (in any case); a profile name with characters other than letters, digits, `_` and `-` (`profile name "a b" may only use letters, digits, _ and -`); `--allow-write` (`sqlh mcp is read-only: it takes no --allow-write (writes go through the sqlh command line)`); `--pool` outside 1–8; `--max-output` under 4096 bytes, since a call's result is held in memory, so it can't be unlimited (0). Any flag not in the usage line above, the CLI's connection flags (`-S`, `-U`, `-E`, `-d`) among them, and any positional argument are refused with one message, `invalid option '-S' (sqlh mcp takes its connections from its profiles); usage: sqlh mcp --profile NAME ...` (`unexpected argument "extra" (...)` for a positional one); the parenthetical is the same for a flag that has nothing to do with connections, such as `--format` or `--exact-count`, as built. `--query-timeout` is taken as `-t`.
- **A stdin that is a console** is refused too: sqlh mcp is started by a harness, and never waits on a person. The check comes after the arguments' own (the refusals above) and before any profile is read, so it takes precedence over an unknown profile. It is `sqlh mcp: usage error: sqlh mcp speaks MCP on stdin and stdout, so a harness starts it (claude mcp add sqlh -- sqlh mcp --profile NAME); it doesn't read from a console`, exit 3 (`mcp::run`), the one launch error that names a harness command.
- **Launch errors** are one line on stderr, `sqlh mcp: usage error: ...` (for a profile that can't be resolved, `sqlh mcp: usage error (see sqlh --help): ` and the CLI's own resolution error, §4), with exit 3, and stdout stays empty; the panic hook leaves stdout alone too. **The line is escaped as any field is** (`app::mcp_log`, through `output::escaped`, DESIGN.md §5.1; `app::main` sends an argument refusal through it too), as the CLI's usage error is in its `-- error:` line, so one error is one line whatever a launch argument holds: `sqlh mcp --profile win --idle $'1\n-- forged'` writes `sqlh mcp: usage error: --idle 1\n-- forged: expected a non-negative whole number`, one line, the `\n` escaped, exit 3, as the CLI's `--max-rows $'1\n-- forged'` gets `-- error: --max-rows 1\n-- forged: ...`. A backslash is doubled with it, as in every `-- ` line (decision 11): a profiles file that can't be read is named `C:\\...\\profiles.toml:1: expected key = value`, and a profile name the refusal quotes with its escapes shows them doubled (`profile name "a\\nb" may only use letters, digits, _ and -`, as the CLI's `no profile named "a\\nb"`). It isn't cut, as a last-resort message's fields are at 1,000 characters (DESIGN.md §6): a 3,000-character `--idle` value comes back whole in its refusal. Probed at `dc24d4b`. Until `dc24d4b` the line was written as it is (found in the docs check at `4519341`), so such an argument split it into two lines, the second starting `-- forged`; only whoever writes the harness's launch command could put one there (plan-history.md, Phase 5.2 and 5.3).
- **Startup failures** are one line on stderr too, with exit 10 (internal, DESIGN.md §6) and stdout empty: `sqlh mcp: cannot start the async runtime: E`, `sqlh mcp: cannot start the stdin reader` and `sqlh mcp: cannot start the stdout writer` (the `--verbose` stderr thread, if it can't start, just leaves the server without logging). **If the console-event listeners can't be installed** (`Signals::new` fails), `sqlh mcp` serves without them, and with `--verbose` logs `sqlh mcp: console events can't be watched (E); Ctrl+C ends the process at once` (`serve`, `dc24d4b`; without `--verbose` nothing is written, and until `dc24d4b` nothing was even with it): a console event then gets Windows' default handling, not the end of §2 (a Ctrl+C or a close ends the process where it stands), where the CLI fails such a run with exit 10 (`cannot watch for Ctrl+C and other console events: E`; running without being able to cancel isn't an option there). As built; no test plays it.

**Startup is fast and doesn't touch the database.** The profiles are read and checked at launch (an unknown profile is a usage error, exit 3, before any message is read); `server/discover` and `tools/list` answer without connecting. A profile's first tool call connects, so a harness can list sqlh's tools even while a database is down.

## 4. Tools

Short names are used, because clients prefix them with the server name (Claude Code shows `mcp__sqlh__query`). The order below is the `tools/list` order. Every tool also takes `profile` (§3), `database?` (1–128 characters), `max_cell?` (0–1,000,000), `timeout?` (seconds, at least 1; below) and `format?` (`text`/`json`), and every tool but `info` takes `max_rows?` (0–10,000). `info` returns one row, so it doesn't offer `max_rows` since decision 45 (MCP client feedback, 2026-10-31); a call that passes it gets the unknown-argument error. Decision 45 had dropped `max_cell` from `info` too, but a profile's or the launch's small `max_cell` still cuts `info`'s values, and its note advises raising it, so it is back (R49). `max_rows: 0` shows every row and `max_cell: 0` every value whole, within the server's `--max-output`, as `--max-rows 0` and `--max-cell 0` do in the CLI.

| Tool | Arguments | What it does |
|---|---|---|
| `query` | `sql`, `exact_count?` | Runs T-SQL under the read-only guard: the classifier, then the rolled-back wrapper transaction. A blocked write returns `isError` with the guard's message. `exact_count: true` counts every hidden row, as `--exact-count` does (decision 45); `-t` can still stop that count in a read-only run (DESIGN.md §4.4). |
| `check` | `sql` | Compile only (`SET NOEXEC ON`), with `--check`'s caveat about missing tables. |
| `info` | — | `sqlh info`, with its connection note (`-- note: profile P; connected in N ms, session setup N ms; server S version V, database D, encrypted true`; `connected in 0 ms` on a reused connection that opened at once; after a probe or a retry, the time they took, the same figure as the status line's `connect N ms`, §5). |
| `databases` | — | `sqlh dbs` |
| `tables` | `pattern?` | `sqlh tables` (an empty pattern is no pattern) |
| `describe` | `object` | `sqlh describe` |
| `find` | `pattern`, `in_definitions?` | `sqlh find` (`in_definitions` is `--text`) |

**Notes on the tools**
- **Annotations:** every tool sets `readOnlyHint: true` and `openWorldHint: false`; the database is a closed system. Annotations describe the tools; they don't enforce anything (§7).
- **Input schemas** (built with `json!` from a static table, `mcp::tools`): JSON Schema 2020-12 objects with `additionalProperties: false`. `required` holds the tool's own required arguments (`sql`, `object`, or `find`'s `pattern`), each with `minLength: 1`, plus `profile` when several profiles are listed. `profile` is an enum of the listed profiles, spelled as the profiles file has them (§3). `database` has `minLength: 1` and `maxLength: 128` (the check counts UTF-16 units, as SQL Server does). `max_rows` and `max_cell` are integers with their bounds. `timeout` is an integer with `minimum: 1` and no maximum, because the server's limit is per profile: a value above it is clamped silently, not refused (below), up to 4,294,967,295; a larger one is refused as an argument error (`timeout must be a whole number from 1 to 4294967295`), though the schema states no maximum. A whole number may be written `30`, `30.0` or `3e1`, as JSON Schema's `integer` allows, and is decided from its text, never through a float (R41, `a55c70d`): `protocol::parse` reads a `tools/call`'s numeric arguments as it reads ids (§2, `raw_member` and `exact_integer`), so one `serde_json` read as a float becomes the integer its text is, or stays a float, which the tool refuses as no whole number. Only the declared numeric arguments are reread (`tools::NUMERIC_ARGS`: `max_rows`, `max_cell`, `timeout`, which a unit test pins to every schema's `integer` properties), each with one scan of the line and only when `serde_json` read it as a float, so the rereading costs a call at most three linear scans of its line however many other arguments it holds, on top of the front parse, `serde_json`'s own (Parser work, below); any other argument is refused by name (`unknown argument`) with no value read (R42, `e60a1de`). From `a55c70d` to `e60a1de` every float-valued member was reread, unknown ones included, with a scan of the whole line each, so a call of 76 KB with 4,000 of them held the serving loop past 12 s, and a pending call's cancel behind one of 2,000 waited 4.8 s (the R41 fix verification's R42, P2). So `10.0000000000000001` (which a float would make 10), `max_rows: -1e-9999` (which a float would make 0, every row), a fraction such as `2.5`, a negative number and a magnitude such as `1e30` are each refused, the run's usage error with `isError: true` before anything connects (`max_rows must be a whole number from 0 to 10000`, `max_cell must be a whole number from 0 to 1000000`, `timeout must be a whole number from 1 to 4294967295`); a zero stays valid however it is written (`0`, `0.0`, `-0`). Until `a55c70d` the check went through an f64, so those near-integers were taken (the R40 fix verification's R41). **External verification closed R41 but found P2 R42:** until `e60a1de`, normalization scanned the whole message once per float-valued argument, including unknown members, before schema refusal, causing quadratic work and delaying cancellation. The restriction to declared numeric arguments fixes it; R42 is closed and this increment accepted (plan-history.md, R42 fix verification). Signed zero remains accepted where zero is valid.
- **Parser work, R42 verification (2026-10-18):** a message's cost is two parts. **The rereading** is at most three linear scans of the line for a call's numeric arguments (`raw_member`, one per declared argument written as a float), and one more for a float-form id. **The front parse** is `serde_json`'s whole `Value` parse, a cost bounded by the 4 MB message limit but not linear in the message: its object maps (`BTreeMap` in the locked serde_json 1.0.151) cost more per member as members grow, so neither part, nor the two together, is a per-message time guarantee or a claim of O(bytes). The operation-count and two-second cancellation regressions are accepted. Parsing remains on the serving thread for this stage. Independent near-cap release samples allowed cancellation in 0.234 s (long string) and 0.875 s (199,000 unknown members), including input delivery. Revisit placement on measured client latency; moving parsing to stdin alone would not let a cancellation line overtake an earlier parse. plan-history.md, R42 fix verification.
- **Descriptions** (what the model reads in `tools/list`; the source is `tools::TOOLS` for the tools and `tools::definitions` for the arguments). Each tool's says what it returns, in more detail than the table above: `query`'s that a guard refuses writes and everything runs in a transaction that is rolled back, that several batches separated by `GO` are allowed and temp tables last only within one call, how the text format reads (as the instructions say it, §6), the three status forms, the escapes (`\\` one backslash, `\t`, `\n`) and the `…[+N]` cut marker, to raise `max_rows` only when needed, that `≥N` is a lower bound that `exact_count` makes exact, that a capped result with statements after it is counted for up to 5 s so they run and that `-- partial:` means some didn't (put each query in its own `GO` batch), and that `format: json` gives the same as one document (the last four since decision 45); `check`'s the missing-table caveat; `describe`'s that it works for system views too (`sys.dm_exec_requests`) and to use it before writing queries against unfamiliar tables; `tables`' and `find`'s what a pattern is. The arguments' are, exactly: `sql` `The T-SQL to run.`, and in `check` `The T-SQL to compile (not run).`; `exact_count` (`query` only) `Count every hidden row of a capped result instead of stopping early (default false), so later statements in the batch run unless the timeout ends the count.`; `object` `The object's name: Orders, dbo.Orders, [My Table], db..t`; `pattern` `A substring or a * ? glob.`; `in_definitions` `Also search module bodies (views, procedures, functions).`; `database` `A database to run in, instead of the profile's.`; `max_rows` `Rows shown per result set (DEFAULT); 0 shows all (within the size limit).` and `max_cell` `Characters shown per value (DEFAULT); 0 shows all (within the size limit).`, where DEFAULT is the call's default (`tools::limit_descriptions`, since decision 45): `default N` for the launch's `--max-rows N` or `--max-cell N` (`default: no limit` for `--max-cell 0`); otherwise `default 2000` rows for `describe`, `deps` and `definition`, `default 4000` characters for `describe` and `deps`, `default: no limit` for `definition`, and `default 100, or the profile's max_rows` and `default 500, or the profile's max_cell` for the rest; `timeout` `Seconds a batch may run, up to the server's own limit.`; `format` `text (the default, compact) or json.`; and `profile`'s depends on the launch: `The server to use; the only one is the default.` with one profile listed, `The server to use: one of the profiles named in the server's instructions.` with several.
- **Timeout:** a call's timeout is its profile's `-t` (the launch `-t` over the profile's `query_timeout`, default 60), lowered by the call's `timeout` and never raised past it: the smaller of the two, silently. When the server's is 0 (no limit), the call's own holds; without one, the server's. It is per batch, as `-t` is in the CLI, and it also bounds the wait for a free connection, the session setup and the call's `USE`; on a reused connection the setup's first try gets at most 5 s instead, the probe, and a second try, when the probe cut the first on a live connection, the call's timeout, while the `USE` always gets the call's timeout and runs once on its connection (§5). **It doesn't bound a connect:** when a call needs one (a profile's first call, a call after an idle close or after every connection was dropped, and the retry of §5), the connect is bounded by its profile's `login_timeout` (default 15 s; the whole login gets one second more, DESIGN.md §4.2), as a CLI run's is by `-l`, so a call can take that long, on top of its wait and its batches, before it fails. Probed at `becb56f`: a profile with `login_timeout = 3`, on a listener that never answers, under `timeout: 1`, ended `-- error: login timeout: ... didn't complete the login within 4 s; ... raise the profile's login_timeout` then `-- failed (exit 4): timeout, 4002 ms`. A cancel ends a connect at once. **A call at the server's limit** (no `timeout` argument, or one at or above the limit, with the server's not 0) is offered no larger timeout when one runs out: the advice says the limit has been reached instead (`run::raise_timeout` returns none, and `tools::execute` sets `Limits::timeout_at_limit` for the count note; the forms are in the table below). A call below the limit is told how far it can go: `raise timeout (the server allows up to S s)`.
- **No write tool** (decision 16). An `execute` tool, separate from `query` so a harness can gate it, comes with Phase 6's command categorization. Until then a write goes through the CLI, with its own safeguards.
- **Database argument:** on the first-release SQL Server target, `database` runs `USE [db]`, with each `]` doubled (`a]b` is sent as `USE [a]]b];`, which is what keeps the argument from injecting SQL), as a request of its own after the session setup and before the call's SQL, for that call only; the reset before the next call restores the profile's database (§5), so it never leaks. Future Azure SQL Database support requires a connection directly to the selected database rather than this switching mechanism.
- **Limits:** a call's limits are the launch limits (the profile's, then the flags), lowered or raised per call within the bounds above; the schema tools keep their own defaults (schema-commands.md §4) unless a launch flag or the call sets them. `--max-output` caps every call's result, as in the CLI, and every refusal given as a result (an argument refusal, the too-many-calls answer); a JSON-RPC error shows a client's tool or method name cut at 100 characters and an id of at most 1024 bytes, so only `-32022`'s `data.requested` can carry more of the client's text, up to the message limit (§2, Bounds).
- **No `$(var)`:** substitution is off for every call. In the CLI it reads the caller's own environment; here the environment is the server's, so a call could read what the harness keeps there.
- **SQL text** over 1 MB (1,048,576 bytes) is refused as a tool error before anything connects: `-- error: the SQL is N bytes; a call takes at most 1048576`, exit 3.
- **The JSON document's `source`** for `query` and `check` is `-Q`, as in the CLI (a schema tool's is its CLI command's name: `dbs` for `databases`, `def` for `definition`); text shows no source for a single batch. The one refusal that names it is a `GO N` past 1000, which the script splitter words with the source label (`-- error: -Q:2: GO 999999999 would run the batch 999999999 times; the most is 1000`, exit 3; Still naming a flag, below).

**Results**
- One `text` content item in the sqlh text format, with the same contract, limits and final status line as the CLI. The models using this were tuned for the CLI output, and it's the cheapest in tokens.
- `format: "json"` returns the JSON document as text instead.
- No `structuredContent`/`outputSchema` for now. The spec suggests duplicating structured content as text, which would double the tokens of every result (§10).

**Errors**
- `isError: true` whenever the run's exit code isn't 0: SQL errors, a blocked write, a timeout, a lost connection, SQL over 1 MB, too many calls (§2). The text includes the error lines and the status, so the model can correct itself.
- **JSON-RPC errors only for a request that doesn't fit `CallToolRequest`** (the tools page's Error Handling: unknown tools and malformed requests are protocol errors): `-32602` for no tool name, or one that isn't a string (`"name": 5`; `Invalid params: tools/call needs a tool name` for both), an unknown tool (`Unknown tool: X`, X cut after 100 characters with `…`), `arguments` that is present but not an object, `null` included (`Invalid params: the arguments of tool X must be an object`; left out, it is none), or the other members of `CallToolRequestParams` mistyped, the multi-round-trip `inputResponses` (an object) and `requestState` (a string), which sqlh never asks for (`Invalid params: inputResponses must be an object`, `Invalid params: requestState must be a string`), all checked before any argument (R39, `6e1a6e7`; until then `arguments: null` counted as none, so a `query` with it got a tool error for its missing `sql`); and a `tools/call` whose `params` itself isn't an object, `null` included, gets `Invalid params: params must be an object` (§2); `-32600` for an id still in use, which is checked first, before the era and any of these, so a `tools/call` reusing an open id gets that and nothing else, whatever its `_meta`, tool name or arguments (§2, The order of a request's checks).
- **Arguments the tool can't take are a tool execution error** (`tools::Refused::Arguments`), as the same page lists input validation errors (a wrong format, a value out of range) and says clients SHOULD pass tool execution errors to the model, which can correct the call: an unknown argument, a wrong type, a missing or empty required one, a number out of bounds or not whole, a database outside 1–128 characters, a profile outside the list, or none given when several are listed. The result is `isError: true` with the run's usage error, exit 3, in the call's format (text unless the call named `format: "json"`, which is checked first; an invalid `format` itself gets text), through the same sink as a run's output, so the client's text in it is escaped like any field: `-- error: invalid arguments for query: unknown argument rows (query takes sql, profile, database, max_rows, max_cell, timeout, format)` then `-- failed (exit 3): usage error, 0 ms`. Nothing connects.
  - **Bounded, whatever the client sends** (`05032c0`): a name the client sent that the refusal shows, an unknown argument's or a profile's, is cut after 100 characters with `…` (`tools::echo`: a 3 MB argument name shows as its first 100 characters, then `… (query takes ...)`), and the whole result is held to the server's `--max-output`, as a call's result is, shortened as a run's closing error is (`tools::refusal` renders with the launch limits, §2, Bounds).
  - The too-many-calls answer (§2) is made the same way, in the call's format.
  - (Until `e8175d4` these were `-32602`, which the self-review found departs from the tools page; until `05032c0` they were held to the default 1,000,000 bytes, not `--max-output`, and echoed names whole; plan-history.md, Phase 5.2 and 5.3.) Everything the run itself finds (a bad object name, a refused write, a SQL error, a timeout, no connection) is a tool error too.

## 5. Connections

Every call is stateless (decision 15): MCP 2026-07-28 has no protocol sessions, and sqlh keeps none of its own.

**The engine** (decision 14) is a library module, separate from the MCP front end, so a daemon behind the CLI could later use it unchanged. It keeps a small pool per listed profile and runs each call through the execution core (`run`), exactly as the CLI does: `run::preflight` (what ends a call before it needs a connection: the guard's refusal, or no SQL to run), then a connection, the session setup (`run::setup`), the call's `USE` when it names a database (`run::use_database`), and `run::run_opened` (the batches). The CLI runs the setup and the `USE` together as `run::open`; the engine calls the two apart, so that its probe (below) bounds and repeats the setup alone (`4519341`).

**What the driver doesn't do behind the engine** (mssql-tds 0.3.0, docs/notes/driver-0.3.0.md; unchanged in 0.4.0, driver-0.4.0.md §1.6, §2.3):
- **No session recovery.** `connect_retry_count = 0` keeps the driver's idle connection resiliency off, and `Session::connect` fails if it were ever negotiated (decision 41), so the engine's one retry on a new connection (decision 19) is the only reconnect, and its login shows as connect time (`live::mcp_tools::a_pooled_connection_killed_between_calls_is_replaced_by_the_engines_retry`).
- **A setup or `USE` the driver cuts mid-send leaves the connection dead** (0.4.0, driver-0.4.0.md §2.1): the driver's own timeout now covers the request's send, and a deadline that passes mid-packet retires the connection. Nothing of the call ran, so it gets decision 19's one retry on a new connection; a deadline that passes while waiting for the reply is the attention and 5 s, as before.
- **But it may remember an address.** The driver keeps a process-wide DNS cache with no TTL and no off switch: after a login the server accepted with DNS caching acknowledged (likely only Azure SQL: the on-prem SQL Server 2025 test server answers `allowed=false`, measured 2026-10-31, driver-0.3.0.md §8), it remembers the addresses the server name resolved to, and uses them only when a later lookup of that name fails. In this long-lived process, a login during a DNS outage can then go, with a SQL password, to the address from the last accepted login; TLS still checks the certificate against the name wherever it checks it at all: under strict encryption, even with `trust_server_certificate`; under mandatory without it; and under optional only when the server requires full encryption and trust is off (R46; decision 42, DESIGN.md §8, upstream-issues.md U7).

**Reset before every call**
- A reused connection is reset with the TDS RESETCONNECTION flag on the call's first request (mssql-tds `prepare_reset_connection`, the mechanism ADO.NET pooling uses), which carries the session setup. The server's `sp_reset_connection` restores the login's options and database, drops temp tables and rolls back a stray transaction. The driver verifies its acknowledgement (§5, After a cancel).
- **It doesn't restore the isolation level.** On SQL Server (all but Azure SQL Database) the reset leaves the level as the last call set it, so a call that ran `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` (which the guard allows) would hand it to the next call on its connection: range locks, or dirty reads without the note. So the session setup sets the level on every call, a reused connection's included, before the wrapper's `BEGIN TRANSACTION`: `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`, a fresh login's level, which still reads row versions where the database has `READ_COMMITTED_SNAPSHOT` on, or `READ UNCOMMITTED` when the profile reads that way (§3; never for `check`). It rides in the same batch, so it costs nothing (DESIGN.md §4.3). Checked live 2026-10-17: `db::spike::spike_reset` asserts that a bare reset leaves SERIALIZABLE in place and that sqlh's setup after it gives READ COMMITTED (docs/notes/mcp-reuse-spike.md §1), and through `sqlh mcp --pool 1` a call that set SERIALIZABLE was followed, on the same session, by a call that read level 2, READ COMMITTED.
- The rest of the setup is the agent defaults (DESIGN.md §4.3; PLAN.md §6.7), then the read-only wrapper's `BEGIN TRANSACTION`; the call's `USE`, if it names a database, follows as a request of its own (§4).
- Every call therefore behaves exactly like a one-shot CLI run, just without the connect cost. Within one call, its batches share the connection and its temp tables, as a CLI run's do.
- **Checked live in 5.4** (2026-10-18; §9, Live tool tests, with the table), through `sqlh mcp --pool 1` on one SPID:
  - **The reset** gives the next call a fresh login's database, language, `NOCOUNT`, `IMPLICIT_TRANSACTIONS` and `ARITHIGNORE`, and the external review's question 3 states: `ROWCOUNT`, `TEXTSIZE`, `DATEFORMAT`, `DATEFIRST`, `CONTEXT_INFO` and no global cursor, each value and its effect (a `DATEFORMAT` or `DATEFIRST` set without `SET LANGUAGE` is restored too). These are states the setup doesn't set, and the tests fail with the reset taken out of the engine (tests 3, 4 and 5 of §9). **Pool** (decision 19)
- Up to 2 connections per listed profile by default (`--pool N`, 1–8), each opened only when a call needs one, so a second exists only when calls overlap.
- **The wait for a free connection:** a call beyond the pool waits for a connection for at most its timeout (§4), measured from when the call started. That budget is the wait's alone: once the call has a connection, each batch still gets the full timeout, as `-t` is per batch in the CLI (so under `timeout: 10` a 9 s wait and then a 9 s batch both pass). Past it, the call fails with exit 4: `query timeout after N s waiting for a free connection (all M of the profile's connections were busy); raise timeout (the server allows up to S s), or start sqlh mcp with a larger --pool` (with `--pool 1` the parenthesis reads `(the profile's only connection was busy)`, since `becb56f`), or, for a call that already had the server's limit (any call without a `timeout` argument, when the server has one), `...; start sqlh mcp with a larger --pool or -t` (§4). With no timeout at all (the server's `-t 0` and no `timeout` in the call) only a cancel ends the wait. A cancel ends it at once, exit 6, `cancelled while waiting for a free connection`, holding no connection (in MCP the cancelled call gets no response; `--verbose` logs its exit).
- A connection idle for 15 minutes is closed (`--idle MINUTES`; 0 keeps connections open while the server runs), by a sweep every 30 s and by a call that would have taken it. The next call reconnects.
- **A call takes the most recently used idle connection** (`take_idle`: the idle ones are a stack, `put_back` pushing and a call popping), so once calls stop overlapping they keep reusing one connection, and an extra one opened while they overlapped is the one left to reach `--idle` and be closed. A call drops only the expired connections it pops on its way to a live one; since the stack is in the order the connections were put back, a live one on top leaves any expired ones below it to the sweep.
- **A reused connection's setup is a probe** (`engine::REUSE_PROBE`, 5 s; `becb56f`, narrowed in `6e7a0d8` and `4519341`). The setup (`run::setup`) is the call's first request and carries the reset; on a reused connection the engine gives it 5 s instead of the call's timeout when that timeout is longer than 5 s or 0 (no limit). On a live connection it answers in milliseconds; one that went silent while idle (a firewall's idle cut, a half-open socket) would otherwise hold the call for its whole timeout and then the driver's 5 s wait for the attention's acknowledgement. A call whose timeout is 5 s or less keeps its own for the setup, and a new connection's setup, every `USE` and every batch get the call's timeout.
- **A setup the probe cuts on a live connection runs again on that connection** (`engine::run_pooled`, `6e7a0d8`; the setup alone since `4519341`). When the probe's timeout ends the setup, the driver kept the connection (the server acknowledged the attention within the driver's 5 s attention wait, so within about 10 s of the setup being sent: it is alive, only slow) and the call isn't cancelled, the connection is reset again (`Session::reset_before_next`, which also undoes what the cut setup did, its `BEGIN TRANSACTION` included) and `run::setup` runs once more, with the call's own timeout and no probe. No new login is made and the profile's idle connections stay: under server-wide load, when a DBA is most likely investigating, a login is the costly step and the one most likely to fail. Engine test `a_setup_the_probe_cuts_short_keeps_its_live_connection`: a reused setup answered after 7 s, under `timeout: 60`, succeeds in 5 to 15 s on the one connection, which carries the reset on the cut setup and again on the setup after it, and stays pooled. From `becb56f` to `6e7a0d8` such a call ran again on a new connection instead, dropping the profile's idle connections, so a failed login failed a call that would have succeeded (round 4, finding 1, plan-history.md).
- **The boundary: a live server silent past about 10 s is taken for dead** (round 5's second half, finding 1; stated in `REUSE_PROBE`'s doc since `dc24d4b`; `dead_before_work`'s names the 5 s condition). A server that doesn't acknowledge the probe's attention within the driver's 5 s can't be told from a half-open connection: the driver marks the connection dead, so it can't be kept, and the call is retried like any dead one (below): the profile's other idle connections are dropped, healthy or not, and the call depends on a new login. Reproduced at `4519341` with throwaway engine tests, two idle connections whose reused setup answers late and a call under `timeout: 60`: answered after 11 s, the call ended at about 10 s, ok on a third connection (`connect` about 10,000 ms; three connections accepted, only the new one left idle), or, when that connection's server closed it at once, exit 2, `connection lost`; a setup never answered gave what the 11 s one did with a working third connection; answered after 9 s, ok on the same connection at about 9 s, both idle connections kept. **Both sides are kept tests since `c3c4a63`** (the external review's question 1): `a_setup_acknowledged_within_the_attention_wait_keeps_its_connection_and_its_peer` (answered after 9 s: ok in 9 to 12 s on the same connection, its cut setup and its setup again each carrying the reset, no new login, both connections kept, connect at least 9,000 ms) and `a_setup_silent_past_the_attention_wait_is_replaced_with_its_idle_peer` (answered after 11 s: ok in 9 to 15 s on a third connection, the dead one and its healthy peer both closed, only the new one left idle, connect at least 9,000 ms); a replacement whose login fails is `a_replacement_that_cannot_log_in_fails_the_call_and_frees_its_slot` (below). Taking such a connection for dead is inherent to the probe, and dropping the peers is right for its real target, a firewall's idle cut, where they most likely died the same way; when the new login works, the call is no slower than a plain wait. So the code is kept as built, and the boundary is recorded here and in decision 19's note (PLAN.md §6); the external review accepted decision 19 as built, with this ten-second boundary stated (its question 1).
- **The call's `USE` gets the call's timeout and runs once on its connection** (`run::use_database`, after the setup has worked, `4519341`): the setup has answered by then, so the connection has shown it is alive, and a slow `USE` (a database being opened, a lock on it) is waited for on that connection, the probe playing no part. A `USE` that runs out at the call's timeout on a connection the driver kept ends the call, `query timeout after N s changing to the call's database`, exit 4, at about that timeout; one whose attention went unanswered left the connection dead and is retried (below). Engine tests `a_slow_use_is_not_probed` (a 6 s `USE` under `timeout: 60` succeeds on the one connection, `connect 0 ms`) and `a_use_past_the_calls_timeout_fails_once` (a `USE` never answered, the attention acknowledged, under `timeout: 6`: exit 4 with that message in 6 to 10 s, the `USE` sent once, one connection). Until `6e7a0d8` the probe bounded the `USE` too (round 4, finding 2); from `6e7a0d8` to `4519341` the loop that sets a cut setup up again wrapped the whole first `run::open`, so a `USE` past the call's own timeout on a probed connection was taken for the probe's: the reset, the setup and the `USE` ran again, and the call took about twice its timeout, or succeeded past it (found in the docs pass to `6e7a0d8`, confirmed in round 5's first half, P2, plan-history.md).
- **A reused connection found dead is replaced and the call retried once**, silently (decision 19): nothing of the call has run, since the setup and the `USE` are sqlh's own requests, and a retry is safe anyway because every call is a read in a rolled-back wrapper. If the retry fails, the call gets the real error, and its slot is freed (engine test `a_replacement_that_cannot_log_in_fails_the_call_and_frees_its_slot`, `c3c4a63`: with `--pool 1`, a reused connection the server closed while idle and a replacement whose login is refused: exit 2 with the 18456 error and the profile's hint, exactly, no third attempt, the permit released, and the next call connects). **The rule as built** (`engine::dead_before_work`, `6e7a0d8`), for a reused connection whose setup (the setup again, above, when the probe cut the first) or `USE` fails, the first time, the call not cancelled:
  - **Retried:** the driver marked the connection dead, or retired it, and the error is neither a SQL error nor a cancel: closed while idle (`Lost`), an unacknowledged reset (`Protocol`), or gone silent (a timeout, at the probe or at the call's own limit, whose attention went unanswered within the driver's 5 s, a live server's stall past that included: the boundary, above).
  - **Not retried:** a SQL error (such as a `database` that doesn't exist); a cancel (`DbError::Cancelled`, and any failure once the call's cancel is set, so a cancel during the probe's attention wait is neither set up again nor retried, `6e7a0d8`; engine test `a_cancel_during_the_probes_attention_wait_is_neither_set_up_again_nor_retried`, `c3c4a63`: cancelled 6 s in, a connection whose server acknowledges the attention at 7 s goes back to the pool after `put_back`'s `SET NOEXEC OFF` and rollback, which undo the cut setup's `BEGIN TRANSACTION`, and the next call reuses it with a reset; one whose server never acknowledges is dropped at about 10 s and the next call logs in anew; either call ends `query timeout after 5 s in the session setup`, exit 4, which `sqlh mcp` never sends, §2); and a timeout at the call's own limit on a connection the driver kept.
  - So a reused connection that dies at the `USE`, after its reset was acknowledged, is retried too, and so is one that dies at its setup again after the probe. That includes a `USE` that ran out at the call's own timeout and whose attention went unanswered: the retry runs the setup and the `USE` again on the new connection, each with the call's timeout, so such a call can spend its timeout twice on the `USE`, plus the attention wait and a login, before its batches (decision 19's retry, as decided). Engine test `a_connection_that_dies_at_the_calls_use_is_retried_with_its_use` (`c3c4a63`): a server that closes the connection once it has answered the setup, and a `USE` never answered under `timeout: 6`, are each retried once, the setup and `USE [d];` sent again on the new connection; the silent one takes 10 to 16 s (the call's 6 s, the driver's 5 s for the attention, a login), its connect time at least 10,000 ms. The connection replaced is closed, not pooled. The retry connects afresh, and the profile's other idle connections are dropped, since they most likely died the same way (true of a firewall's idle cut; after a live server's stall past about 10 s, the boundary above, they were healthy). The retry's connect, like any, is bounded by the profile's `login_timeout`, not by the call's timeout (§4, Timeout).
  - **What it costs:** a silent connection holds the call for the probe and the driver's attention wait, about 10 s, then a new connection runs it (engine test `a_reused_connection_gone_silent_is_retried_after_the_probe`: 9 to 20 s, two connections, the output the first call's and its connect time at least 9 s); a slow but live setup costs the probe's 5 s, the attention's acknowledgement and then the setup's own time, on the same connection, when the server acknowledges the attention within the driver's 5 s (a server silent longer than that, about 10 s in all, costs what a dead connection does, the profile's idle connections and a new login included: the boundary, above), and one that runs out again, at the call's timeout, on a connection the driver kept, ends the call with `query timeout after N s in the session setup` (N the call's timeout) after about the probe's 5 s plus that timeout (no engine test plays it). Until `becb56f` no timeout was retried: a silent reused connection ended its call with a bare `query timeout` after the call's timeout plus 5 s (round 3, plan-history.md).
  - **Decision 19, as built:** only a dead connection is replaced, as the decision says. The probe, and the setup again on a live connection it cut (the setup alone; the call's `USE` runs once after it, `4519341`), are how a dead connection is found within about 10 s without replacing a slow live one that acknowledges the attention within the driver's 5 s; a live server silent longer than that is taken for dead and replaced, its idle peers with it, which the probe can't avoid, since the driver has marked the connection dead by then (the boundary, above; `dc24d4b` states it in the code's comments). Recorded as the decision's implementation (PLAN.md §6, decision 19), and accepted as built by the external review (2026-10-18, its question 1), which asked for the regressions now kept (`c3c4a63`).
  - A call that fails otherwise (at its setup or `USE` without a retry, or later, in its batches) is not retried, and its connection is discarded only when the driver marked it dead or retired it; otherwise it goes back to the pool, after `put_back`'s rollback (below).
- **A timeout in the setup or the `USE` says where it struck**, since none of the call's own SQL was running: `query timeout after N s in the session setup` (`run::setup`) or `query timeout after N s changing to the call's database` (`run::use_database`), exit 4, with no advice (`becb56f`; a bare `query timeout` before). N is the timeout that request had (`run::setup` words the setup's with the timeout it was given, the probe's or the call's, since `6e7a0d8`; the `USE` always has the call's), and in every result a client gets it is the call's timeout: a setup the probe cut is set up again or retried, never the call's error, except in a cancelled call, whose result isn't sent (§2). The CLI's setup goes through the same `run::setup`, inside `run::open`, so a CLI run's setup timeout reads the same (DESIGN.md §4.3); a CLI run has no `USE` (it connects to its database, so its `Request::database` is `None`). Engine test `the_probe_is_never_longer_than_the_call`: a reused connection's 3 s setup under `timeout: 1` ends `-- error: query timeout after 1 s in the session setup`, with no retry.
- **The connect time** (`engine::run_pooled`, `6e7a0d8`): the status line's `connect N ms`, the JSON document's `connect_ms` and `info`'s `connected in N ms` are one figure (DESIGN.md §5.1, §5.2), and it tells a slow connection from a slow query:
  - a reused connection whose setup worked at its first try, and that neither the setup nor the call's `USE` found dead: 0, the call paid no connect;
  - a reused connection the probe cut and set up again, or a call retried on a new connection (after its setup or its `USE` found the reused one dead): the time from the call's first attempt (once it had its free connection) to the start of the setup that worked, so the probe's 5 s, the attention's wait and, for a retry, the new login are connect time rather than an unexplained part of the total (round 4, finding 3): at least 5 s in `a_setup_the_probe_cuts_short_keeps_its_live_connection`, at least 9 s in `a_reused_connection_gone_silent_is_retried_after_the_probe`;
  - a new connection (a profile's first call, or one after an idle close): its connect and login, as in the CLI.
  - The wait for a free connection is in none of them (it is in the call's total), and `info`'s `session setup N ms` is the time of the setup that worked. The call's `USE` that worked is in neither figure, only in the total; a `USE` that found a reused connection dead is part of the retry's connect time, which runs from the first attempt and so covers the first connection's setup and its failed `USE` (for a `USE` that ran out at the call's timeout with its attention unanswered, that timeout and the driver's 5 s attention wait), then the new login. Until `6e7a0d8` a retried call's connect time was the new login's alone: a silent connection's 10 s showed only in the total, which in text, MCP's default, gives no time per batch for a one-batch call, so a reader took it for the query's.
- **A call whose setup or `USE` fails** and isn't retried ends without the status line's `server/db, connect N ms` tail (and the JSON document without `connection` and `connect_ms`): a connection is described only once it is ready (its setup and `USE` succeeded), so a retry never describes the dead one. A call whose `database` doesn't exist ends that way too. (The CLI describes its connection before the setup, so a CLI run whose setup fails keeps the tail.)
- **Putting a connection back:** a connection the driver kept goes back to the pool. If the call's wrapper is still open (a cancel or a timeout left it), `put_back` first sends `SET NOEXEC OFF;` as a request of its own and then `IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;`, both within 2 s (`ROLLBACK_WAIT`, the driver's own timeout and attention wait included), so an idle connection holds no transaction. The NOEXEC OFF is for a `check` call cut short, which left `SET NOEXEC ON` in force (only its normal end turns it off): under NOEXEC the rollback would only be compiled. Without NOEXEC in force it changes nothing. If either request fails, the 2 s pass or a transaction is still open, the connection is dropped instead, so a server gone silent can't hold up the call's reply.
- **A call that turns on `SET FMTONLY`, `PARSEONLY` or `SHOWPLAN_XML`** (the guard allows each) loses its connection: under them the wrapper's closing rollback, and `put_back`'s after `SET NOEXEC OFF`, are only compiled or described, not run, so the wrapper is still open and the connection is dropped, not pooled; the server rolls a closed session's transaction back, so nothing leaks, and the next call logs in again (seen by hand in 5.4: connect 148–185 ms). No test plays it.

**After a cancel** (decision 17)
- A call ends with a TDS attention when the client cancels it (`notifications/cancelled`), when its timeout fires, or when the bounded count of hidden rows stops at its budget (decision 6). Count stops end any query with many hidden rows, so this is routine.
- When the driver kept the connection (it settled the cancel within sqlh's settle bound, R15 B, and didn't mark it dead), the connection goes back to the pool, and the reset before the next call clears what the cancelled call left. mssql-tds (0.2.0, and 0.3.0 too: docs/notes/driver-0.3.0.md §2) gives no receipt for an acknowledged attention: a kept connection also follows a cancel before the request was sent and a half-sent request it withdrew (upstream-issues U4), all in step with the server.
- **The check is the reset itself:** the driver verifies that the reply to the next request starts with the server's ResetConnection acknowledgement, or fails that request (`ConnectionResetNotAcknowledged`) and marks the connection dead, so a session in an unknown state is never trusted. Then the connection is discarded and the call retried once on a new one (§5 Pool).
- A connection the driver marked dead is discarded: an attention the server never acknowledged (`DbError::CountStopUnconfirmed` for a count stop), a protocol error, a lost connection; so is one past sqlh's settle grace. The next call reconnects.
- **A cancelled call gets 5 s to settle** (`SETTLE_GRACE`, the driver's own wait for an attention's acknowledgement); past it, the call is dropped where it stands, and its connection with it: `cancelled: the call didn't finish within 5 s of the cancel, so its connection was closed`.
- **Between a kept cancel and the next call** (checked live in 5.4, `mcp_a_cancel_the_driver_kept_leaves_the_next_call_clean`, §9): the idle connection holds no transaction, since `put_back` rolled the wrapper back (which also dropped the #temp table the call made inside it), but its session keeps the cancelled call's `SET`s, language and isolation level, as the server shows (`sys.dm_exec_sessions`), until the next call's reset and setup; nothing runs on it meanwhile. The next call, on the same SPID with no new login, gets a fresh call's `@@TRANCOUNT` (1, its own wrapper's), `@@OPTIONS`, language and level, and no #temp table: decision 17's requirement.

**Concurrency**
- Requests are read and dispatched concurrently on the current-thread runtime, and tool calls run concurrently, at most 64 at once, cancelled ones still settling included (§2), each with its own cancel. Database work is serialized per connection.
- Each call has a timeout per batch (§4) that sends a TDS attention when it fires.

## 6. Instructions (`server/discover` / `initialize`)

Short guidance the model sees once. `tools::instructions` builds exactly this text, with `{profiles}` each listed profile as `name (description)`, or `name` alone when it has no description, joined by `; `, and `{choose}`, when several profiles are listed, a space and then the sentence ``Pass `profile` to choose one.``, else nothing:

```text
sqlh runs read-only T-SQL against SQL Server. Profiles: {profiles}.{choose} Use `describe`, `find` or `deps` before writing queries against unfamiliar tables. Results come in a compact text format: `-- ` lines are metadata, the header is `name:type`, rows are tab-separated, NULL is `NULL`, `\\` is one backslash, and the last line is the status: `-- ok:`, `-- partial:` (a stopped row count kept later statements of its batch from running; put each query in its own GO batch) or `-- failed`. Results are cut at row and size limits, which the output says; raise `max_rows` only when you need more. Every call is read-only (writes are refused and rolled back) and starts fresh: temp tables last only within one call.
```

The backslash and `partial` clauses were added from MCP client feedback (2026-10-31, decision 45; docs/notes/mcp-client-feedback.md).

For example, with `win` described as `closed port for tests` and `other` without a description, the text after the first sentence begins ``Profiles: win (closed port for tests); other. Pass `profile` to choose one.`` (tested by `the_tools_are_listed_with_closed_schemas` and `a_modern_session_discovers_lists_and_calls`).

The profile names (spelled as the file has them, §3) and descriptions come from the profiles file at launch, without connecting. Server version details appear only after a call, via `info`. Profile descriptions are the owner's text (4.1), which the profiles file already holds to one line of at most 300 characters with no control or bidi characters; they go into the instructions as they are, JSON-encoded like the rest of the response.

## 7. Security

Database permissions are expected to be configured appropriately. The tool's checks also protect against accidental damage when an agent receives excessive privileges. Command categorization and allowlist/blocklist policy need further design around legitimate DBA workflows (Phase 6); the current classifier is an MVP mechanism. Tool annotations do not replace database enforcement.

- **Fixed reach:** the profiles listed at launch are the only targets, connection settings and credentials are fixed at launch (§3), and tool arguments never carry secrets.
- **Read-only:** every tool runs under the guard and in the rolled-back wrapper; there is no write tool, `--allow-write` isn't accepted, and a profile that allows writes is read-only here (decision 16).
- **Isolation between calls:** the reset before every call and the isolation level the setup sets (§5), and a connection discarded whenever the driver lost track of it, with the reset's acknowledgement verified on every reuse. Checked live in 5.4, after a call that set them and after a kept cancel (§5, §9). State the reset isn't known to clear is refused (decision 30(e), §5).
- **Input limits:** a JSON message over 4 MB is answered with `-32600` and skipped, and nothing else changes; an id that isn't a string or an integer within 64 bits, or is over 1024 bytes, is refused (§2), and so is a method envelope whose declared members are malformed, before anything is allocated. SQL text over 1 MB is refused (a tool error). Pattern and object arguments are passed as literals (`docs/schema-commands.md` §3), and `database` as a bracketed name with `]` doubled (§4).
- **Bounded server memory, and a client that can't hold the server:** at most 64 calls run at once, at most 8 subscriptions are open, at most 64 requests (or 16 MiB of them) are held back while stdout is behind, a client that stops reading is ended by the stall rule, and about 128 responses at most wait for stdout, plus two lines for each open subscription at the end (§2): a call's result and every refusal given as a result within `--max-output` as text, so up to about twice that as a JSON-RPC line once JSON escaping has doubled its tabs, newlines, quotes and backslashes (§2, Bounds), a JSON-RPC error within the 4 MB message limit (only `-32022`'s `data.requested` can come near it), each with the request's id, at most 1024 bytes, on top.
- **No `$(var)`:** a call can't read the server's environment (§4).
- **Output limits:** limits always apply. Control characters are escaped by the text format, so database contents can't forge protocol framing; results are JSON-encoded inside the response anyway.
- **Prompt injection through data:** rows can contain text that reads like instructions. sqlh can't prevent that, and the instructions don't pretend otherwise. The harness's tool-result handling is the defense.
- **No secrets in logs:** stderr logs (`--verbose`) never include passwords or connection strings, and no general logger is installed while the driver runs (AGENTS.md).
