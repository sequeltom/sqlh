### The profiles file under a packaged app (found and built 2026-11-01, decision 53)

The Claude desktop app is a packaged (MSIX) Windows app, and Windows redirects `%APPDATA%` for what it starts. A Code-tab shell's `C:\Users\<user>\AppData\Roaming\sqlh\profiles.toml` was served from `...\AppData\Local\Packages\Claude_<id>\LocalCache\Roaming\sqlh\profiles.toml`; a profile added in the user's shell, or in the app's Terminal panel, wrote the real Roaming file and never appeared there, and the run failed with `no profile named "..."` and nothing to say why. Credential Manager isn't split.

Probes with throwaway files, between a Code-tab shell (in the package) and the Terminal panel (not):

| Case | Result |
|---|---|
| A folder the real `AppData` has first; the package reads, adds to and changes files in it | passes through to the real files; nothing in the cache |
| A folder the package made first; the same name then made outside | the package sees only its cached copy |
| The package deletes its cached copy | the real file appears to it |
| The package deletes that real file | the real file is gone |
| The package writes under `%USERPROFILE%` | a real file, read from outside |

Built: the file is `%USERPROFILE%\.sqlh\profiles.toml`, and runs bring in what's under `%APPDATA%` (DESIGN.md §8). On the owner's machine, from a Code-tab shell, one `profiles list` took the cached copy (two profiles), then the real file behind it (a third): nothing lost, no conflict, the cached copy's `default` kept, and the Terminal panel then read the same file. `test` and `test2016` connect with the passwords already stored, and `sqlh mcp` run from that shell does too. Tests: unit tests in `config.rs` (a copy, a merge, a difference set aside, a broken file, a file that can't be removed, both moves in a row) and one process-level test. The uncovering of a real file can't be arranged in a test, so it rests on the probes and that one run.

Not measured: `sqlh mcp` launched by the desktop app itself, as its configured server; it should be the same as the Code-tab shell, also a child of the package. This touches where credentials' profiles are read, so it goes in the next external review (decision 52).

### Setting the default profile (owner, 2026-10-26, from manual testing; planned, not started)

`profiles.toml` has a top-level `default = "NAME"` (DESIGN.md §3 and §8: used when no `--profile`, no `SQLH_PROFILE` and no `-S`/`SQLCMDSERVER` is given), but nothing in the CLI sets it after the first `profiles add` (which makes the first profile the default, `profile.rs`, `became_default`). `profiles rm` of the default clears it silently (`Config::remove`), so removing the first of three profiles leaves two profiles, no default and no CLI way to choose one; the only fix is editing the file. `--help` mentions the default only as "Without -S: the default one" on the `--profile` line. (S)

2. **`profiles rm` says so when it clears the default**, naming the fix: `NAME was the default profile: runs without -S or --profile now need one (sqlh profiles default NAME)`.
3. **`--help`:** one more line under `PROFILES`, and the `--profile` line points to it. Keep `--help` under about 60 lines (it is at 62 now, so trim elsewhere).
4. **Not chosen, with reasons:** promoting another profile when the default is removed (with two or more left it is a guess, and a wrong guess makes a bare `sqlh -Q ...` hit the wrong server silently, worse for an agent than a clear "no profile selected" error; promoting only when exactly one is left was considered and rejected for one rule in every case); an `add --default` flag (redundant once `profiles default` exists).
5. **Same change:** DESIGN.md §8 (the subcommand and the `rm` note), `src/help.txt`, tests (`profile.rs` unit tests with a fake store, a process-level test in `tests/cli.rs`, an `rm` of the default that prints the note), and README's "Built for agents" list only if it changes what an agent gains (likely not: it is a person's setup command).

9. **Ask upstream to redact the password in packet dumps?** At debug level, mssql-tds hex-dumps every TDS packet before TLS encrypts it (`io/packet_writer.rs`), including the login packet ([notes/connect-latency.md](notes/connect-latency.md)). The password in it carries only the scramble the TDS protocol requires (nibble swap and XOR 0xA5), which anyone can reverse. It's a logging-hygiene issue (CWE-532), not a remote vulnerability: nothing leaks unless an application turns on debug logging for the driver. Other drivers' traces usually mask the password. The channel is the owner's choice: a GitHub issue, or Microsoft's security process. Check `main` first; this was read in 0.2.0. **Decided 2026-10-12 (owner): no, sqlh doesn't ask.** Its own rule stays the defense: never install a general logger while mssql-tds runs (AGENTS.md, Driver logging). Re-check the dump when bumping the driver.
10. **Provenance in the text output: always, on the status line (owner decision, 2026-10-11).** Every text and csv run that connected ends its status line with the server, the database the run started in and the connect time, for about 10 to 15 tokens a call: `-- ok: 1 batch, 241 ms; db01/master, connect 195 ms` (csv: on stderr with the rest of the metadata). Left out when nothing connected (usage error, guard refusal, failed connect). Names are escaped and cut like other metadata, within the ending's reserve. Auth method and encryption stay in JSON and `--verbose`. Shown every time, not only when `-d` was missing, so the shape of the status line doesn't depend on how the run was invoked. Rest of plan-history.md 2.11, built 2026-10-11.
11. **Paths in metadata lines keep the escape rule (owner decision, 2026-10-11).** A backslash in a path inside a `-- ` line is written `\\`, like any other escaped field (DESIGN.md §5.1), and a reader decodes it like any other field. Input is never escaped: paths, SQL text and `-v` values are taken exactly as typed, so a path from Explorer's "Copy as path" (double-quoted, single backslashes) works as is after `-i` or `-o` in cmd.exe, PowerShell and Git Bash; only Git Bash eats an unquoted backslash, which is the shell's rule. Rejected: forward slashes (rewrites what was typed, and some cmd built-ins refuse them) and escaping a backslash only before an escape letter (changes the reader rule, and `C:\new` would still be doubled). Done 2026-10-11 in plan-history.md 2.13's follow-up: DESIGN.md §5.1 says paths follow the rule, the `--help` FORMAT lines say so without growing, and a process-level test runs a quoted "Copy as path" spelling, spaces included.
12. **Agents and the write switch (owner decision, 2026-10-12, from agent trial 2): new profiles refuse writes.** `sqlh profile add` saves `write_policy = "deny"` for a new profile unless `--write-policy` is given; existing profiles keep their policy, and a profile saved without the key is still `flag` (DESIGN.md §8). Built with plan-history.md 2.16. **Decided 2026-10-12 (owner): `profile list` keeps showing the server's address and the login.** Every run's status line already names the server, and a login isn't a secret; hiding them would make choosing a profile harder for an agent without protecting anything. A control over what agents may see or change in profiles would be a separate design. The background: An agent asked to clean up a table added `--allow-write` on its own and ran a 927,269-row `DELETE`; only the profile's `deny` stopped it. Options: make `deny` the default for new profiles (so writes take an explicit change to the profile's policy), keep `flag` and rely on agent guidance (the skill, Phase 8), or both. Also: `sqlh profile list` showed the agent the server's address and the login; whether it should, in agent hands, is part of the same question. Precedent (comparison with the owner's earlier sql-query-runner skill, 2026-10-12): that skill gives agents no write path at all (a query must start with `SELECT` or `WITH`, or be one allowed `EXEC` or `DBCC TRACESTATUS`), so trial 2's cleanup would have stopped at its refusal. Its check is weaker than sqlh's, though: it looks only at the first word and runs with no rollback, so `WITH x AS (...) DELETE ...`, `SELECT 1; DELETE ...` and `SELECT ... INTO` pass and write. The nearest sqlh equivalent of "no write path for agents" is `deny` as the default for new profiles, which keeps the stronger guard and makes writing an explicit change to a profile's policy. That change can run unattended, so an agent that can run `profile add` can make it (R19): `deny` stops an agent reaching for `--allow-write`, it doesn't make writing a person's decision. A human-only control over profiles, if wanted, is a separate design.
13. **`profile list` is text only (owner decision, 2026-10-13, from R25).** Profiles are ancillary to the product: listing them is setup an agent does once per session, and text is the cheapest format to read. A json listing would need a document shape of its own (R25 found that the anonymous batch it used breaks contract 2.0's batch metadata), which isn't worth its cost now, so `--format` is refused for `profile list` and the JSON contract is unchanged. Search (`--search`) stays. Revisit only if a consumer that can't read text needs the list (Phase 8's MCP connector might).
14. **Connection reuse comes through MCP first (owner decision, 2026-10-15, Phase 5).** The reuse engine (connections kept open, reset between calls, the cleanup and clean-cancel rules) is built once as a library module, and `sqlh mcp` (docs/mcp-mode.md) is its first front end. A local per-profile daemon behind the CLI, which would speed up Bash-driven use too, is deferred: it would be added on the same engine only if evidence (an agent trial with MCP) shows Bash-driven use stays the main path. Why: VISION.md asks that reuse preserve execution policy, isolation between calls and reliable cleanup, and under MCP the harness owns the lifecycle and cancellation is part of the protocol, where a daemon would make sqlh build auto-start, stale-process, idle-exit, pipe-security and cross-process cancellation itself; MCP also gives native tools and separate read and write tools a harness can gate, and Phase 8 already plans the connector. The cost, accepted: until a daemon exists, a CLI call still pays its connect (about 195 ms on the dev LAN, plan-history.md 2.1). **The deferral stands (decision 48, 2026-11-01):** the connect is about 0.5–1.5% of a small model's turn.
15. **MCP calls are stateless, for now (owner decision, 2026-10-15, Phase 5).** Before every call the reused connection is reset (TDS RESETCONNECTION: login defaults restored, temp tables dropped, a stray transaction rolled back, the profile's database restored), then the session setup and, for reads, the per-call wrapper transaction run: each call behaves exactly like one CLI run, without the connect. No `session_open` handles, so docs/mcp-mode.md §5's sessions, and the hour-long read-only transaction they needed, are not built. Why: isolation between calls and reliable cleanup (VISION.md) come from the reset itself, a cancelled call can leave nothing behind but the connection, and agents and sqlh have no handles, expiry or long transaction to manage. Sessions can be added later on the same engine if an agent trial shows agents need state across calls. The cost, accepted: work that needs state across calls isn't possible read-only (a wait-stats delta is two snapshots the agent compares itself); within one call, a script's batches still share one connection and its temp tables. **As built (plan-history.md 5.2, 2026-10-17; the decision is unchanged):** on SQL Server (all but Azure SQL Database) the reset doesn't restore the transaction isolation level, so a call's `SET TRANSACTION ISOLATION LEVEL` would outlive it on its pooled connection; each call is still like one CLI run because the session setup sets the level on every call, a reused connection's included (`READ COMMITTED`, or `READ UNCOMMITTED` for a profile that reads that way; `run::session_setup`). Found by the self-review (plan-history.md, Phase 5.2 and 5.3, round 1, P1); docs/notes/mcp-reuse-spike.md §1, DESIGN.md §4.3.
16. **MCP is read-only, for now (owner decision, 2026-10-16, Phase 5).** The first `sqlh mcp` offers only read tools (`query`, the schema commands, `info`), each in the read-only wrapper with the guard, whatever the profile's `write_policy`; there is no `execute` tool, so docs/mcp-mode.md's write tool and write sessions are not built. A write goes through the CLI, with its safeguards: the profile's policy (`deny` by default for new profiles, decision 12), `--allow-write` and the guard. Why: the speed win matters most for the many repeated reads of an investigation; agent trial 2's agent added `--allow-write` on its own and only the profile's `deny` stopped a 927,269-row `DELETE`, and under an `execute` tool the last check would be the harness's permission prompt, which users often set to always allow; and Phase 6's command categorization is where which statements need explicit approval, and how, gets decided, so `execute` is added with it rather than designed twice. The cost, accepted: a write during an MCP investigation pays the CLI's connect.
17. **A connection is reused after a cancel only when the server confirmed it (owner decision, 2026-10-17, Phase 5).** A call that ends with a TDS attention (a cancel from the client or harness, `-t`, or the bounded count of hidden rows stopping at its budget, decision 6) keeps its connection when the server acknowledged the attention within the settle bound (R15 B); the reset before the next call (decision 15) clears what the cancelled call left: an open wrapper transaction, temp tables, `SET`s (as built, all but the isolation level, which the session setup sets on every call: decision 15's as-built note). Anything less discards the connection and the next call reconnects: no acknowledgement (today's `COUNT_STOP_UNCONFIRMED`), the settle grace running out, a protocol error, a lost connection. Why: count stops end any query with many hidden rows, so cancels are routine, and always discarding would make the calls agents make most pay the login again; the reset is the mechanism connection pooling relies on, and the unclear cases are the ones discarded. Required before it ships: a live test that a confirmed cancel leaves the next call clean (`@@TRANCOUNT` 0, the cancelled call's temp table gone, the agent session's `SET`s restored), and fake-server tests that an unacknowledged or stalled attention discards and reconnects. The cost, accepted: more code and tests than always reconnecting, and a residual risk of driver state the reset doesn't clear, which those tests are there to catch (the driver can be swapped behind `src/db/`). **Amended 2026-10-17 (owner), after spike 5.1:** mssql-tds 0.2.0 gives no receipt for an acknowledged attention, so "confirmed by the server" can't be checked; a connection the driver kept (`is_connection_dead()` false, which covers an acknowledged attention, a cancel before the request was sent and a half-sent request withdrawn with EOM|IGNORE, all in step with the server) is reused, and one it marked dead, or one past sqlh's settle bound, is discarded. The check that a reused session is clean is the next call's reset, whose acknowledgement the driver verifies (the server's ResetConnection ENVCHANGE must come first, or the request fails with `ConnectionResetNotAcknowledged` and the connection is marked dead); then the connection is discarded and the call retried once on a new one (decision 19). Why: what matters is whether the session is clean and in step, which the verified reset answers on every reuse after any kind of cancel; the spike found every kind clean after it (docs/notes/mcp-reuse-spike.md §2). The missing receipt is U4 in docs/notes/upstream-issues.md, for the owner to raise; the rule can tighten if upstream adds one. **The live test it requires is built (plan-history.md 5.4, 2026-10-18):** `mcp_a_cancel_the_driver_kept_leaves_the_next_call_clean`: the idle session holds no transaction, and the next call on the same session gets a fresh call's `@@TRANCOUNT` (its own wrapper's 1), `SET`s, language and level, with the cancelled call's temp table gone (plan-history.md, Phase 5.4).
18. **An MCP server reaches the profiles listed at its launch (owner decision, 2026-10-17, Phase 5).** `sqlh mcp --profile test --profile reporting` serves those profiles and no others; each tool takes an optional `profile`, which must be one of them (with one listed, it is the default). The server's instructions name the allowed profiles with their descriptions (plan-history.md 4.1), so the agent picks the right server in one call; a profile's connection opens on its first use. No tool argument names a server, a login or a password (docs/mcp-mode.md §3 stands for those). Why: the owner sets the reach once, in the harness config, and the agent never gets more; profile descriptions keep their job under MCP; one copy of the tool definitions keeps the agent's context cost flat however many profiles are listed; and with read-only tools (decision 16) the risk within the list is reads from servers the owner chose. Strict separation stays possible: a profile can get its own server entry, listed alone, so the harness gates it separately. The cost, accepted: within one server's list, the harness can't prompt per profile. **As built (plan-history.md 5.3, 2026-10-17; the decision is unchanged):** `profile` is optional only with one profile listed (the default); with several, every tool's schema lists it in `required` and `tools::plan` refuses a call without one (`missing required property profile: one of A, B`, exit 3; plan-history.md, Phase 5.2 and 5.3, round 1). A call's `profile` matches in any ASCII case, as the launch's `--profile` does (since `becb56f`; until then it had to match the profiles file's spelling exactly), and the schemas' enum and the instructions show the file's spelling (mcp-mode.md §3).
19. **MCP connection limits (owner decision, 2026-10-17, Phase 5).** Per listed profile, up to 2 connections by default (`--pool N`, 1–8), opened only when a call needs one, so a second exists only when calls overlap. A connection idle for 15 minutes is closed (`--idle MINUTES`; 0 keeps connections open while the server runs). A reused connection found dead (a network drop, a killed session) is reconnected and the call retried once, silently; if the retry fails, the call gets the real error. Why: harnesses make several tool calls at once (parallel discovery), and two connections cover that without loading the server; 15 minutes covers a human pause mid-investigation and ends idle sessions on production servers well before firewalls drop them; and a retry is safe because every call is a read in a rolled-back wrapper (decisions 15, 16). The cost, accepted: the first call after a long pause pays the login again, and a busy session holds up to two server sessions per listed profile. **As built (plan-history.md 5.2, 2026-10-17, `becb56f`, `6e7a0d8` and `4519341`, its boundary stated in `dc24d4b`): the decision's implementation, recorded for the owner's code review; the decision is unchanged, and the implementation raises no question of its own, since only a dead connection is replaced. Accepted as built by the external review (2026-10-18, its question 1), its ten-second boundary explicit, with the regressions it asked for kept since `c3c4a63`.** A reused connection shows it is dead at its first requests, the session setup (`run::setup`, which carries the reset) and the call's `USE` when it names a database (`run::use_database`), before any of the call's own SQL, so the call is retried on a new connection when either fails with the connection dead or retired (`engine::dead_before_work`): closed while idle (`Lost`), a reset the server didn't acknowledge (`Protocol`), or gone silent (a timeout whose attention went unanswered within the driver's 5 s). Not retried: a SQL error (a `database` that doesn't exist), a cancel (nor anything once the call's cancel is set), and a timeout at the call's own limit on a connection the driver kept, which ends `query timeout after N s in the session setup` (or `... changing to the call's database`). **The probe** (`REUSE_PROBE`): a reused connection's setup gets at most 5 s when the call's timeout is longer or 0; the `USE` keeps the call's timeout and runs once on its connection, after the setup has worked. Why: a connection gone silent while idle (a firewall's idle cut, a half-open socket) would otherwise hold the call for its whole timeout and the driver's 5 s attention wait and then fail it; with the probe it is found dead in about 10 s and the call runs again on a new connection, which is what the decision asks of a dead connection. **A setup the probe cuts on a live connection** (the server acknowledged the attention within the driver's 5 s attention wait, so within about 10 s of the setup being sent: slow, not dead) is reset and run again, the setup alone, on that same connection with the call's own timeout, not replaced. Why: a slow server is most likely one under load, when a DBA is investigating, and there a new login is the costly step and the one most likely to fail; replacing a live connection would also drop the profile's healthy idle ones. The probe costs a slow live setup its 5 s and the attention's acknowledgement, which the call's connect time reports (DESIGN.md §5.1). **The boundary** (round 5's second half, finding 1; stated in `REUSE_PROBE`'s doc in `dc24d4b`, whose `dead_before_work` doc names the 5 s condition, the code as built): a live server that doesn't acknowledge the attention within those 5 s, stalled more than about 10 s on the setup, can't be told from a half-open connection. The driver marks the connection dead, so it can't be kept, and it is replaced like a dead one: the profile's other idle connections are dropped, healthy as they are, and the call depends on a new login, which costs the call nothing more when it works (reproduced: ok at about 10 s on a new connection) and fails it when it doesn't (exit 2). Kept as built: taking such a connection for dead is inherent to the probe, and dropping the peers is right for the case the probe is for, a firewall's idle cut, where they most likely died the same way; it needs a stall of more than about 10 s on a trivial request against a server that still answers. History: until `becb56f` no timeout was retried, so a silent reused connection failed its call with a bare `query timeout` after the call's timeout plus 5 s, which round 3 found departs from this decision (plan-history.md, Phase 5.2 and 5.3, round 3, finding 5). `becb56f` added the probe, over the setup and the `USE`, and retried a setup it cut on a live connection on a new one, beyond "found dead", recorded then for the owner to confirm; round 4 found that costly (a failed login could fail a call that would have succeeded, finding 1), and `6e7a0d8` narrowed it to the above. `6e7a0d8`'s loop around the cut setup also caught a `USE` that ran past the call's own timeout on a live connection, so the `USE` ran twice and the call took about twice its timeout; round 5 confirmed it (P2) and `4519341` fixed it: the engine calls `run::setup` and `run::use_database` apart, and the loop runs the setup alone (plan-history.md, Phase 5.2 and 5.3, round 5, first half). Round 5's second half found the boundary above undocumented, the code's comments and the docs saying a slow server keeps its connection without the driver's 5 s, and `dc24d4b` recorded it (round 5, second half, finding 1); mcp-mode.md §5.

22. **Kinds of change are granted separately, per profile and per run (owner decision, 2026-10-23, Phase 6, command-categories.md D1(b)).** Changes come in six kinds a person can grant, named in DBA words: `data`, `maintenance`, `tuning`, `kill`, `remote` and `unvetted` (code sqlh can't classify). A profile's `allow` list, written by the owner, says which kinds it permits, and it holds even under `write_policy = "deny"`; a run uses a listed kind with `--allow KIND`. `--allow-write` stays as the blanket switch for everything outside the deny tier. `read`, `scratch` and the deny tier are never switch names; finer reason labels (contention, settings, cost, ...) appear only in refusal text and the docs. Why: today a `deny` profile, every new profile's (decision 12), has no way to update statistics, force a plan or kill a runaway session short of moving to `flag`, which opens data writes too; separate kinds let an owner grant the narrow change without the broad one. Retiring `--allow-write` (option (c)) was not chosen: it would break existing scripts and agents' habits for little gain. The mechanics (the `allow` list's defaults by `write_policy`, `--allow` limited to it, which kinds keep the rollback wrapper) are D11; the deny tier is D10; the `execute` tool is D15. Like `deny`, the list is an accident guard: an agent that can run `profile add` can change it (R19).
23. **Refusals say what they are, and what lifts them (owner decision, 2026-10-23, Phase 6, command-categories.md D2(a)).** Now, independent of classifier v2: an unknown procedure is refused as `EXEC X isn't on sqlh's list of read-only procedures, so sqlh can't tell what it does` (implicit calls: `... it isn't on sqlh's list of read-only procedures`), with `Rerun with --allow-write to run it as written`; an unknown DBCC command as `DBCC X isn't on sqlh's list of read-only DBCC commands`, naming its documented replacement first where there is one (`PAGE` → `sys.dm_db_page_info`, `LOGINFO` → `sys.dm_db_log_info`, ...); DDL refusals name the statement (`ALTER EVENT SESSION`, not a bare `ALTER`); `sp_query_store_flush_db` gets the aggregation advice in place of a flag. With v2: every refusal names its kind or reason label (decision 22) and the narrowest switch that lifts it, or says that none does (the deny tier). No JSON `kind` member for now (contract 2.2, if a consumer needs it). Why: "would write" is wrong for a procedure or command sqlh merely doesn't know, and steers agents to `--allow-write` for reads. It changes the output contract: DESIGN.md §5.1 and §7, the golden tests and README's "Built for agents" change with the code.
24. **Read-only runs and `sqlh mcp` refuse lock-holding SQL; SNAPSHOT becomes a run setting after a live test (owner decision, 2026-10-23, Phase 6, command-categories.md D3(a) and (i)).** Refused, and lifted by the `data` kind (decision 22): the hints `UPDLOCK`, `XLOCK`, `TABLOCKX` and `HOLDLOCK`; `SERIALIZABLE` and `REPEATABLEREAD` (hint or isolation level) and `REPEATABLE READ` after `ISOLATION LEVEL`; `SET DEADLOCK_PRIORITY` with anything but `LOW` or a literal from −10 to −5; `SET LOCK_TIMEOUT` outside a literal from 0 to the run's own lock timeout (10,000 ms when the run has none; never −1 or a variable); with `WAITFOR`, `sp_getapplock` and `sp_releaseapplock`, refused already. `TABLOCK` alone, `NOLOCK`, `READPAST` and the other hints stay reads. The advice names what the caller can change: remove the hint; `--lock-timeout`; in MCP, the profile's `lock_timeout`. Why: inside the wrapper these hold their locks to the run's final rollback, the one risk the wrapper makes worse, and the in-SQL `SET`s override decision 7 from inside the input; the rare legitimate SERIALIZABLE read gives way. **SNAPSHOT:** a run setting like decision 7's READ UNCOMMITTED (`--snapshot`, a profile's `snapshot = true`), set in the session setup before `BEGIN TRANSACTION`, exclusive with `read_uncommitted`, once a live test shows it works inside the wrapper; then an in-SQL `SET TRANSACTION ISOLATION LEVEL SNAPSHOT` is refused with advice naming it. The test needs `ALLOW_SNAPSHOT_ISOLATION ON` on a test database, a database-level change outside decision 21, so it waits for the owner's approval of that step.
25. **Linked-server reads are allowed with a note; paths an agent chose are refused (owner decision, 2026-10-23, Phase 6, command-categories.md D4a(i) and D4b(i)).** **D4a:** a four-part read through a linked server a DBA configured (`SELECT ... 45. **A capped result no longer cancels later statements unseen; it gets a longer count first, and a run that still loses them says `partial` (owner decision, 2026-10-31, from MCP client feedback: docs/notes/mcp-client-feedback.md).** This amends decision 6.
    - **The problem:** a stopped count cancelled the rest of its batch while the status line still began `-- ok`. One client's model said it was the only issue that made it "confidently report something false".
    - **The link:** over the owner's real link the 250 ms budget stopped after about 600 wide rows, so it hit modest results, and models often send several queries in one call.
    - **The longer budget:** a batch that may produce output from more than one statement counts the hidden rows of a capped result for 5 s, not 250 ms, so its later statements still run. `guard::several_outputs` counts the statements conservatively: an `EXEC` counts as two; `DECLARE`, `SET` and `USE` count as none. A batch of one output statement keeps 250 ms, since a stop there cancels nothing.
    - **The run's result-to-statement mapping:** sqlh can't tell from the server's replies which statement a result came from, so a several-statement batch gets the longer budget for its last result too. It then waits up to 5 s for an exact count that cancels nothing.
    - **When even that stops the count,** whether by the 5 s or by `-t`: the status line begins `-- partial:` instead of `-- ok:`, exit 0, and names the batches whose rest didn't run (`partial: 1 batch, counting stopped in 1, the rest of batch 1 not run, ...`). The note says the same, with the `GO` advice.
    - **A stop in a single-output batch** keeps `ok` and its note says only that the total is a lower bound.
    - **JSON's contract is unchanged (2.1):** `summary` carries the status line, `ok` stays true for exit 0, and `counting_stopped` keeps its 2.0 meaning, that the rest of that batch may have been cancelled.

So `Session::connect` sets `VectorVersion::V2`, which is what the driver would pick anyway, so that a later default can't change how vectors arrive unseen, as decision 40 did for failover; the LOGIN7 test pins the 0x0E byte at 2, and that 0x09 (data classification) is absent. float32 vectors arrive and print as before. float16 vectors (SQL Server 2025's preview half-precision type) arrive natively once the server acknowledges version 2 (the driver also accepts an acknowledgement of 1, and float16 then comes down-level, as before; which one 2025 sends is not yet observed, since `sqlh_test` keeps `PREVIEW_FEATURES` off and the server refuses the type, error 195), and the driver widens each element to f32 exactly; sqlh writes each in the shortest decimal that reads back as the same float16, DESIGN.md §5.1's shortest round-trip form at the element's own precision (`0.1`, not `0.099975586`), and a whole number whole (`65504`, not its shortest form `65500`); checked against every finite float16, and through the driver's decoder by a fake-server row of both column types. The header's type stays `vector` (the `vector(N, float16)` spelling of driver-0.4.0.md §6.6 is not taken). Why: follow upstream where it costs nothing to sqlh's contract. The alternatives were version 1 (no output change) and off (no vector feature; float32 vectors down-level too).

72. **Windows auth's SPN comes from the driver's per-hop hook, `SecurityContextProvider`, built now, for 0.1.0 (owner decision, 2026-11-08, driver-0.4.0.md §7.3 and §6.1).** Asked whether to keep sqlh's 500 ms SPN pre-lookup before the connect, with keeping it recommended and the hook recorded as the replacement after 0.1.0, the owner's words: "build the long term replacement now. as I said I want to flow with the 0.4.0's defaults, this is in the spirit of that ask". So the pre-lookup (`spn_if_lookup_is_slow`, `host_and_spn`, the `-K ReadOnly` skip) is replaced by a provider the driver calls for each login hop with the host and port it dials: SQL Browser's port for a named instance, and each routed host. The lookup keeps its 500 ms bound and its cap (R53), and closes R52's two exclusions. The cost, accepted with it: the lookup moves inside the login deadline, after TCP, prelogin and TLS, where DESIGN.md §4.2 promised it before `-l`'s limits; and it is new authentication code, so it goes to the external review with the driver upgrade (decision 52). The alternative was keeping the pre-lookup for 0.1.0 and the hook after it.

73. **The local-pipe check takes this computer's name from the driver (owner decision, 2026-11-08, driver-0.4.0.md §7.4).** Asked whether `check_server` should compare `np:<name>` with the driver's `this_computer_name()` (public since mssql-tds 0.4.0: the DNS host name, `GetComputerNameExW`, which the driver itself compares to decide a pipe is local) instead of the `COMPUTERNAME` environment variable, with the driver's recommended, the owner's words: "yes, i'll go with your recommendation". Built: `db::this_computer`, the driver's name, with `COMPUTERNAME` only when the driver has none. Why: the refusal exists to match what the driver will open; with `COMPUTERNAME`, an environment naming another host let `np:<that host>` through to the driver's remote pipe open (U1), while the driver's own name can't be moved by the environment. The cost: on a machine whose DNS name is longer than 15 characters, `np:<NetBIOS name>` is now refused (with the TCP spelling); it went over SMB to this machine. The alternative was keeping `COMPUTERNAME`.

74. **mssql-tds 0.4.0's other new features wait for after 0.1.0, as candidates (owner decision, 2026-11-08, driver-0.4.0.md §7.5).** Asked whether to record them as candidates after 0.1.0, with that recommended (none is needed for the release, and decision 70 holds 0.1.0 to the upgrade itself), the owner's words: "yes, i'll go with your recommendation". The candidates, each a feature of its own with its own design, review and, for the first two, output changes: (a) the connect-stage spans (driver-0.4.0.md §6.2) for `--verbose`, `sqlh profiles test` and `db::phases`, which would replace the debug texts `db::phases` matches; a tracing subscriber only if it measures no larger than the log path, and enabling only `mssql_tds::connect` spans (AGENTS.md, Driver logging); (b) sensitivity labels for a DBA, by the catalog (`sys.sensitivity_classifications`, SQL Server 2019 and later), not the driver's data-classification token (§6.5); (c) refusing a login to a cached address or a routed host sqlh didn't name (§6.3), only if decisions 42 and 43 are to become enforceable. The first of §7.5's list, the per-hop SPN hook, was built for 0.1.0 by decision 72.
75. **AppVeyor runs the release's own exe and tests against its SQL Servers; GitHub builds everything; AppVeyor holds a read-only GitHub token (owner decisions, 2026-11-08, §4, AppVeyor).** The owner offered an AppVeyor account for integration tests of other SQL editions, "not triggered every time" but for release certification. Asked about a draft that compiled on AppVeyor's VM, the owner's words: "compile should stay on the GH runner. I wanted to use the AppVeyor VM for integration/release tests after the exe is built." So `release.yml`'s build job also builds the live suite's test binary and keeps it as a workflow artifact, never a release asset; AppVeyor downloads it and the signed exe (the `sqlh-<version>` artifact `sign` uploads) from that commit's release run, checks the exe's signature and `SHA256SUMS.txt`, and runs the live tests against each instance, only for a tag or a build started by hand. The repository is private, and GitHub's signed download links expire in minutes, so AppVeyor needs a token. Asked, with recommended a fine-grained token for `sequeltom/sqlh` alone with Actions: read only and an expiry, kept as an AppVeyor encrypted variable and made by the owner (never passing through an agent), the owner's words: "yes, go with the read-only token". It can download workflow artifacts, and read workflow runs and their logs (Actions: read is broader than artifacts alone; corrected by the R59-R61 review), but not change code or releases, nor read the values of GitHub's stored secrets.
