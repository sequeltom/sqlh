### The profiles file under a packaged app (found and built 2026-11-01, decision 53)

The Claude desktop app is a packaged (MSIX) Windows app, and Windows redirects `%APPDATA%` for what it starts. A Code-tab shell's `C:\Users\<user>\AppData\Roaming\sqlh\profiles.toml` was served from `...\AppData\Local\Packages\Claude_<id>\LocalCache\Roaming\sqlh\profiles.toml`; a profile added in the user's shell, or in the app's Terminal panel, wrote the real Roaming file and never appeared there, and the run failed with `no profile named "..."` and nothing to say why. Credential Manager isn't split.

Probes with throwaway files, between a Code-tab shell (in the package) and the Terminal panel (not):

| Case | Result |
|---|---|
| A folder the real `AppData` has first; the package reads, adds to and changes files in it | passes through to the real files; nothing in the cache |
| A folder the package made first; the same name then made outside | the package sees only its cached copy |
| The package deletes its cached copy | the real file appears to it |
| The package deletes that real file | the real file is gone |
| The package writes under `%USERPROFILE%` | a real file, read from outside |

Built: the file is `%USERPROFILE%\.sqlh\profiles.toml`, and runs bring in what's under `%APPDATA%` (DESIGN.md §8). On the owner's machine, from a Code-tab shell, one `profiles list` took the cached copy (two profiles), then the real file behind it (a third): nothing lost, no conflict, the cached copy's `default` kept, and the Terminal panel then read the same file. `test` and `test2016` connect with the passwords already stored, and `sqlh mcp` run from that shell does too. Tests: unit tests in `config.rs` (a copy, a merge, a difference set aside, a broken file, a file that can't be removed, both moves in a row) and one process-level test. The uncovering of a real file can't be arranged in a test, so it rests on the probes and that one run.

Not measured: `sqlh mcp` launched by the desktop app itself, as its configured server; it should be the same as the Code-tab shell, also a child of the package. This touches where credentials' profiles are read, so it goes in the next external review (decision 52).

### Setting the default profile (owner, 2026-10-26, from manual testing; planned, not started)

`profiles.toml` has a top-level `default = "NAME"` (DESIGN.md §3 and §8: used when no `--profile`, no `SQLH_PROFILE` and no `-S`/`SQLCMDSERVER` is given), but nothing in the CLI sets it after the first `profiles add` (which makes the first profile the default, `profile.rs`, `became_default`). `profiles rm` of the default clears it silently (`Config::remove`), so removing the first of three profiles leaves two profiles, no default and no CLI way to choose one; the only fix is editing the file. `--help` mentions the default only as "Without -S: the default one" on the `--profile` line. (S)
1. **`sqlh profiles default NAME`** sets the default (`NAME` must exist, as the file's load check already requires; case as `find` matches it); **`sqlh profiles default --clear`** removes it. A text note says what it did, and the profiles file's path is written as typed (decision 38).
2. **`profiles rm` says so when it clears the default**, naming the fix: `NAME was the default profile: runs without -S or --profile now need one (sqlh profiles default NAME)`.
3. **`--help`:** one more line under `PROFILES`, and the `--profile` line points to it. Keep `--help` under about 60 lines (it is at 62 now, so trim elsewhere).
4. **Not chosen, with reasons:** promoting another profile when the default is removed (with two or more left it is a guess, and a wrong guess makes a bare `sqlh -Q ...` hit the wrong server silently, worse for an agent than a clear "no profile selected" error; promoting only when exactly one is left was considered and rejected for one rule in every case); an `add --default` flag (redundant once `profiles default` exists).
5. **Same change:** DESIGN.md §8 (the subcommand and the `rm` note), `src/help.txt`, tests (`profile.rs` unit tests with a fake store, a process-level test in `tests/cli.rs`, an `rm` of the default that prints the note), and README's "Built for agents" list only if it changes what an agent gains (likely not: it is a person's setup command).
6. **Open:** the owner has not yet approved the design; record it in §6 as a decision when taken.

## 5. Sequencing rationale

Why Phases 1–3 came in the order they did; their tasks are in plan-history.md. The order of the work since is set by decisions 46–51 (§6).

- **1.1 (F04) first.** It is the only finding where the tool states something false while possibly executing writes.
- **The test harness comes before the other fixes,** so every fix lands with a process-level regression test.
- **2.1 (connect latency) early, but time-boxed.** It is cheap to measure and could change Phase 5 entirely. Building pooling to hide a fixable 150 ms would be the wrong order. 6. **The drain default: a bounded count for read-only runs (owner decision, 2026-10-11).** Following [notes/drain-experiment.md](notes/drain-experiment.md): in read-only runs, sqlh counts hidden rows for about 250 ms and then stops (an attention), reporting a lower bound floored to one significant digit (`100 of ≥800000 rows shown (counting stopped)`), so a result that ends inside the budget stays exact and the same query gives the same output. The exact count stays under `--allow-write` (a stopped count skips later statements, which can include a `COMMIT`), for input that mentions `XACT_ABORT`, and on request (a flag such as `--exact-count`). Independently, `-t` expiring while only hidden rows are being counted reports `≥N` with the run's own exit code, not exit 4, since the rows shown are complete. Accepted cost: "limits never change what runs" no longer holds strictly, because a stopped count cancels the rest of that batch; in a read-only run nothing it skips outlives the run, and the output says it happened. plan-history.md 2.15, built 2026-10-11. **Clarified in building it, confirmed by the owner 2026-10-11:** `-t` expiring during the count stays exit 4 (i) with writes allowed, because a stop would skip a later `COMMIT` and the run would report success, and (ii) with `XACT_ABORT` in the input, because the attention rolls the read-only wrapper back, so the run would end with exit 1, or exit 0 with the wrapper gone, in place of the timeout. 17. **A connection is reused after a cancel only when the server confirmed it (owner decision, 2026-10-17, Phase 5).** A call that ends with a TDS attention (a cancel from the client or harness, `-t`, or the bounded count of hidden rows stopping at its budget, decision 6) keeps its connection when the server acknowledged the attention within the settle bound (R15 B); the reset before the next call (decision 15) clears what the cancelled call left: an open wrapper transaction, temp tables, `SET`s (as built, all but the isolation level, which the session setup sets on every call: decision 15's as-built note). Anything less discards the connection and the next call reconnects: no acknowledgement (today's `COUNT_STOP_UNCONFIRMED`), the settle grace running out, a protocol error, a lost connection. Why: count stops end any query with many hidden rows, so cancels are routine, and always discarding would make the calls agents make most pay the login again; the reset is the mechanism connection pooling relies on, and the unclear cases are the ones discarded. Required before it ships: a live test that a confirmed cancel leaves the next call clean (`@@TRANCOUNT` 0, the cancelled call's temp table gone, the agent session's `SET`s restored), and fake-server tests that an unacknowledged or stalled attention discards and reconnects. The cost, accepted: more code and tests than always reconnecting, and a residual risk of driver state the reset doesn't clear, which those tests are there to catch (the driver can be swapped behind `src/db/`). **Amended 2026-10-17 (owner), after spike 5.1:** mssql-tds 0.2.0 gives no receipt for an acknowledged attention, so "confirmed by the server" can't be checked; a connection the driver kept (`is_connection_dead()` false, which covers an acknowledged attention, a cancel before the request was sent and a half-sent request withdrawn with EOM|IGNORE, all in step with the server) is reused, and one it marked dead, or one past sqlh's settle bound, is discarded. The check that a reused session is clean is the next call's reset, whose acknowledgement the driver verifies (the server's ResetConnection ENVCHANGE must come first, or the request fails with `ConnectionResetNotAcknowledged` and the connection is marked dead); then the connection is discarded and the call retried once on a new one (decision 19). Why: what matters is whether the session is clean and in step, which the verified reset answers on every reuse after any kind of cancel; the spike found every kind clean after it (docs/notes/mcp-reuse-spike.md §2). The missing receipt is U4 in docs/notes/upstream-issues.md, for the owner to raise; the rule can tighten if upstream adds one. **The live test it requires is built (plan-history.md 5.4, 2026-10-18):** `mcp_a_cancel_the_driver_kept_leaves_the_next_call_clean`: the idle session holds no transaction, and the next call on the same session gets a fresh call's `@@TRANCOUNT` (its own wrapper's 1), `SET`s, language and level, with the cancelled call's temp table gone (plan-history.md, Phase 5.4).

19. **MCP connection limits (owner decision, 2026-10-17, Phase 5).** Per listed profile, up to 2 connections by default (`--pool N`, 1–8), opened only when a call needs one, so a second exists only when calls overlap. A connection idle for 15 minutes is closed (`--idle MINUTES`; 0 keeps connections open while the server runs). A reused connection found dead (a network drop, a killed session) is reconnected and the call retried once, silently; if the retry fails, the call gets the real error. Why: harnesses make several tool calls at once (parallel discovery), and two connections cover that without loading the server; 15 minutes covers a human pause mid-investigation and ends idle sessions on production servers well before firewalls drop them; and a retry is safe because every call is a read in a rolled-back wrapper (decisions 15, 16). The cost, accepted: the first call after a long pause pays the login again, and a busy session holds up to two server sessions per listed profile. **As built (plan-history.md 5.2, 2026-10-17, `becb56f`, `6e7a0d8` and `4519341`, its boundary stated in `dc24d4b`): the decision's implementation, recorded for the owner's code review; the decision is unchanged, and the implementation raises no question of its own, since only a dead connection is replaced. Accepted as built by the external review (2026-10-18, its question 1), its ten-second boundary explicit, with the regressions it asked for kept since `c3c4a63`.** A reused connection shows it is dead at its first requests, the session setup (`run::setup`, which carries the reset) and the call's `USE` when it names a database (`run::use_database`), before any of the call's own SQL, so the call is retried on a new connection when either fails with the connection dead or retired (`engine::dead_before_work`): closed while idle (`Lost`), a reset the server didn't acknowledge (`Protocol`), or gone silent (a timeout whose attention went unanswered within the driver's 5 s). Not retried: a SQL error (a `database` that doesn't exist), a cancel (nor anything once the call's cancel is set), and a timeout at the call's own limit on a connection the driver kept, which ends `query timeout after N s in the session setup` (or `... changing to the call's database`). **The probe** (`REUSE_PROBE`): a reused connection's setup gets at most 5 s when the call's timeout is longer or 0; the `USE` keeps the call's timeout and runs once on its connection, after the setup has worked. Why: a connection gone silent while idle (a firewall's idle cut, a half-open socket) would otherwise hold the call for its whole timeout and the driver's 5 s attention wait and then fail it; with the probe it is found dead in about 10 s and the call runs again on a new connection, which is what the decision asks of a dead connection. **A setup the probe cuts on a live connection** (the server acknowledged the attention within the driver's 5 s attention wait, so within about 10 s of the setup being sent: slow, not dead) is reset and run again, the setup alone, on that same connection with the call's own timeout, not replaced. Why: a slow server is most likely one under load, when a DBA is investigating, and there a new login is the costly step and the one most likely to fail; replacing a live connection would also drop the profile's healthy idle ones. The probe costs a slow live setup its 5 s and the attention's acknowledgement, which the call's connect time reports (DESIGN.md §5.1). **The boundary** (round 5's second half, finding 1; stated in `REUSE_PROBE`'s doc in `dc24d4b`, whose `dead_before_work` doc names the 5 s condition, the code as built): a live server that doesn't acknowledge the attention within those 5 s, stalled more than about 10 s on the setup, can't be told from a half-open connection. The driver marks the connection dead, so it can't be kept, and it is replaced like a dead one: the profile's other idle connections are dropped, healthy as they are, and the call depends on a new login, which costs the call nothing more when it works (reproduced: ok at about 10 s on a new connection) and fails it when it doesn't (exit 2). Kept as built: taking such a connection for dead is inherent to the probe, and dropping the peers is right for the case the probe is for, a firewall's idle cut, where they most likely died the same way; it needs a stall of more than about 10 s on a trivial request against a server that still answers. History: until `becb56f` no timeout was retried, so a silent reused connection failed its call with a bare `query timeout` after the call's timeout plus 5 s, which round 3 found departs from this decision (plan-history.md, Phase 5.2 and 5.3, round 3, finding 5). `becb56f` added the probe, over the setup and the `USE`, and retried a setup it cut on a live connection on a new one, beyond "found dead", recorded then for the owner to confirm; round 4 found that costly (a failed login could fail a call that would have succeeded, finding 1), and `6e7a0d8` narrowed it to the above. `6e7a0d8`'s loop around the cut setup also caught a `USE` that ran past the call's own timeout on a live connection, so the `USE` ran twice and the call took about twice its timeout; round 5 confirmed it (P2) and `4519341` fixed it: the engine calls `run::setup` and `run::use_database` apart, and the loop runs the setup alone (plan-history.md, Phase 5.2 and 5.3, round 5, first half). Round 5's second half found the boundary above undocumented, the code's comments and the docs saying a slow server keeps its connection without the driver's 5 s, and `dc24d4b` recorded it (round 5, second half, finding 1); mcp-mode.md §5.

40. **Multi-subnet failover is always explicit: off unless `-M` (owner decision, 2026-10-31, driver upgrade, docs/notes/driver-0.3.0.md §1.1).** sqlh passes `Some(options.multi_subnet_failover)` to mssql-tds 0.3.0, never `None`, which would inherit the driver's default (on) or `MSSQL_RS_MULTISUBNET_FAILOVER_DEFAULT`. Connects stay sequential, with today's timings, exit codes and texts (connect-failures.md); `-M`'s 0.3.0 behaviour (local names connect over parallel TCP; `np:`, `lpc:`, `admin:`, LocalDB and a named instance without a port refused; a parallel timeout is exit 4) goes in DESIGN.md §4. *Superseded in part (2026-10-31, the internal review, accepted by the external review's judgment 2): a parallel race in which no address accepted TCP within `-l` is a connect failure, exit 2, `no address accepted a TCP connection within N s (-M tries them all at once)`; a login that stalls after TCP stays exit 4 at `-l` + 1 s (DESIGN.md §4, driver-0.3.0.md §8).* Tests: the policy a connect resolves to, and the environment variable set to `true` and to garbage leaving `-S 127.0.0.1,1` unchanged.
41. **Driver session recovery stays off (owner decision, 2026-10-31, driver upgrade, driver-0.3.0.md §2).** `connect_retry_count = 0` keeps the driver from advertising or using idle connection resiliency, in both 0.2.0 and 0.3.0, and the engine's one retry on a new connection (decision 19) stays the only reconnect, with honest connect times. A guard at connect checks that the client reports session recovery off, and a fake-server test checks that LOGIN7 carries no session recovery feature. Why: a silent driver reconnect would hide a login in the status line's times, bypass the engine's peer-drop rule, could add a second login to the engine's, and would continue an `--allow-write` script in a new session; it gains the read-only wrapper nothing, since recovery is refused inside a transaction.
42. **mssql-tds 0.3.0's DNS cache is accepted, documented (owner decision, 2026-10-31, driver upgrade, driver-0.3.0.md §1.2).** It can't be turned off; it matters only to `sqlh mcp`'s long-lived process, and only if the server acknowledges the feature (likely only Azure; the on-prem SQL Server 2025 test server answers `allowed=false`, measured 2026-10-31) and a later lookup of the name fails. DESIGN.md §8 says so, and upstream-issues.md U7 asks for an opt-out, for the owner to file.
43. **Server routing is accepted as the server's decision, and DESIGN.md §8's wording corrected (owner decision, 2026-10-31, driver upgrade, driver-0.3.0.md §1.3).** A server can route a login, and the driver follows with the same credentials (0.2.0 already did; 0.3.0's Enhanced Routing can also name the database). DESIGN.md §8 now says a stored password goes to its profile's own server "or to a server that server routes the login to"; R20's protection against an agent repointing a profile is unaffected. 44. **Versioning: the exe says which build it is, in `--version` and in its Windows properties (owner decision, 2026-10-31, from manual testing: Explorer's Properties > Details showed nothing, and `--help` didn't mention `--version`).** Built the same day; DESIGN.md §4 has the exact behaviour.
    - **The version resource:** `build.rs` writes a VERSIONINFO resource as a compiled .res file and links it, with no rc.exe and no crate, so it works wherever the exe builds. It adds 1,024 bytes and no import.
    - **The numeric version:** major.minor.patch, then the release workflow's run number (`SQLH_BUILD`; 0 for any other build), so the numbers only grow: `0.1.0-dev.5` is 0.1.0.5, and a 0.1.0 release built at run 9 is 0.1.0.9.
    - **The fields:** `CompanyName` `Tom Willwerth`, the copyright from LICENSE, product `sqlh`.
    - **`--help`:** its first line names `--version` and `--help`, with no new line.
    - **Local builds:** a build outside the release workflow reports `<Cargo.toml version>-local`, so it never passes for a release.
    - **Checks:** `the_exe_carries_its_version_in_its_windows_properties` reads the resource through Windows PowerShell 5.1, and `a_build_outside_the_release_workflow_is_marked_local`; both run in `check.ps1`, against the release exe too. The release workflow checks the signed exe's properties against `SQLH_VERSION` and `SQLH_BUILD`.
    - **Policy:** semver, with `Cargo.toml` as the source and a release tag that must match it. Before 1.0, a release that changes the output contract or flags bumps the minor, and a fix-only release bumps the patch. The JSON contract keeps its own version (DESIGN.md §5.2).
45. **A capped result no longer cancels later statements unseen; it gets a longer count first, and a run that still loses them says `partial` (owner decision, 2026-10-31, from MCP client feedback: docs/notes/mcp-client-feedback.md).** This amends decision 6.
    - **The problem:** a stopped count cancelled the rest of its batch while the status line still began `-- ok`. One client's model said it was the only issue that made it "confidently report something false".
    - **The link:** over the owner's real link the 250 ms budget stopped after about 600 wide rows, so it hit modest results, and models often send several queries in one call.
    - **The longer budget:** a batch that may produce output from more than one statement counts the hidden rows of a capped result for 5 s, not 250 ms, so its later statements still run. `guard::several_outputs` counts the statements conservatively: an `EXEC` counts as two; `DECLARE`, `SET` and `USE` count as none. A batch of one output statement keeps 250 ms, since a stop there cancels nothing.
    - **The run's result-to-statement mapping:** sqlh can't tell from the server's replies which statement a result came from, so a several-statement batch gets the longer budget for its last result too. It then waits up to 5 s for an exact count that cancels nothing.
    - **When even that stops the count,** whether by the 5 s or by `-t`: the status line begins `-- partial:` instead of `-- ok:`, exit 0, and names the batches whose rest didn't run (`partial: 1 batch, counting stopped in 1, the rest of batch 1 not run, ...`). The note says the same, with the `GO` advice.
    - **A stop in a single-output batch** keeps `ok` and its note says only that the total is a lower bound.
    - **JSON's contract is unchanged (2.1):** `summary` carries the status line, `ok` stays true for exit 0, and `counting_stopped` keeps its 2.0 meaning, that the rest of that batch may have been cancelled.
46. **The CLI is the center; MCP is a second front end on the same core (owner decision, 2026-11-01, from the review of the plan, design and vision).** sqlh is first a command-line tool for shell-driven agents, small-context models included: the owner's original vision, turn-by-turn speed for agents like Qwen. `sqlh mcp` serves MCP hosts from the same execution core. When the two compete for design, size budget or review attention, the CLI comes first: a feature is designed as a command or flag, and MCP gets it through the shared core.
    - **Why:** the CLI costs an agent's context least. `--help` is 4.7 KB (about 1,200 tokens), read once and only when needed; MCP's nine tool definitions and its instructions are 12.5 KB of JSON (roughly 3,000–4,000 tokens; `query` alone 2.2 KB), sent with every request of a session whether or not it touches SQL (measured 2026-11-01 on the release build of `7feae17`).
    - **MCP stays:** agent trial 3's model (`qwen3.8`, offered both) and the owner's Claude Desktop sessions (2026-10-31) used it, and it is the only surface with connection reuse today.
    - **Open, in this order:** (a) the scope of hosted MCP over Streamable HTTP: loopback, a team service (on an application server, which decision 1 as amended allows for MCP) or the internet (claude.ai's remote connectors connect from Anthropic's cloud); (b) whether MCP moves to an exe of its own (decision 20), which follows (a), so that `sqlh.exe` never gains a network listener; (c) connection reuse for the CLI itself (decision 14's deferred daemon), since the CLI's connect on every call (about 195 ms on the dev LAN, 585 ms in the real environment of 2026-10-31) is its largest gap from MCP's 9–11 ms per reused call.
    - **This answers** whether MCP or the CLI is primary (raised 2026-11-01 for Phase 8's order): the skill for shell-driven agents keeps its place ahead of MCP packaging. VISION.md's Purpose and Speed sections record it.
47. **Hosted MCP goes on the roadmap with one identity model, Entra pass-through (owner decision, 2026-11-01, from a colleague's request for Cowork-style access).** A hosted `sqlh mcp` for remote connectors (claude.ai's connect from Anthropic's cloud) is planned, not started: each caller signs in with Entra ID, sqlh exchanges the caller's token for one scoped to SQL (on-behalf-of) and logs in with it, so every query runs as that person, with their permissions and in the server's own audit. Its targets are servers that take Entra logins: SQL Server 2022 and later with Entra set up, Azure SQL Managed Instance and Azure SQL Database. The first environment is a colleague's SQL Server 2025 Standard on an Azure VM, with a Managed Instance perhaps to follow; PaaS hosting is preferred (Windows App Service, say). The plan: "Hosted MCP with Entra pass-through" (§4).
    - **Why:** the host holds no shared SQL credential, so nothing on it is worth stealing; database permissions stay the boundary person by person (VISION.md, Safety); and the driver already has a token login (`AccessToken`, read from mssql-tds 0.3.0's source, untested).
    - **Option (a), a shared read-only login per profile on the host, is the backup:** not built and not planned, but open for reconsideration if a server without Entra (SQL Server 2016 to 2019, say) needs hosting. Options (b), a login per caller stored on the host, and (d), Kerberos delegation, are not planned.
    - **For decision 46's open questions:** this answers (a) for the internet tier, and its plan builds MCP's own exe first, (b), so `sqlh.exe` never listens on a network; loopback and team-service tiers stay undecided, and the hosted server runs on an application server, which decision 1 as amended (2026-11-01) allows for MCP.
48. **The CLI is optimized for local, offline and small models; no daemon; MCP is the recommendation for frontier models (owner decision, 2026-11-01).** The CLI's audience is agents on local or offline models such as Qwen in OpenCode (agent trial 3), generally on GPUs with 24 GB of VRAM or less. When a choice trades their context or their reading for something else, theirs wins: compact output, a short `--help`, fewer calls per answer, and results that say what to do next. The user docs recommend MCP for frontier models (README, Quick start), whose context barely notices sqlh's tool definitions and which get connection reuse there.
    - **No daemon behind the CLI (decision 14's deferral stands, now with evidence; decision 46's open question (c) closed):** in agent trial 3, 47 calls across ten tasks took 1,844 s, about 39 s a call, mostly the model's own generating and reading; a connect is 195 ms on the dev LAN (about 0.5% of that) and 585 ms in the real environment of 2026-10-31 (about 1.5%). A daemon's costs (auto-start, stale processes, idle exit, pipe security, cancellation across processes, harnesses that kill it with their commands) buy too little for these agents. A script's batches, split by `GO`, already share one connect.
    - **Reopen it** only if a measurement shows the connect is a material share of real CLI turns (a fast model over a slow link, say).

55. **Read-only runs refuse `AI_GENERATE_EMBEDDINGS` (owner decision, 2026-11-02).** Asked "should read-only runs refuse AI_GENERATE_EMBEDDINGS?", the owner's words: "yes, refuse it". Refused the way `OPENROWSET` is, in read-only runs and so in every `sqlh mcp` call; `--allow-write` lifts it where a profile allows that, and the `remote` kind (decision 22) can grant it later. Why: on SQL Server 2025 `AI_GENERATE_EMBEDDINGS(... USE MODEL m)` is a function, so the guard read it as a read, and with an external model defined it sends its text to an outside endpoint, as `sp_invoke_external_rest_endpoint`, already refused, does; an agent misled by what it read could send what it reads off the server, and no rollback calls that back. The cost: a read-only or `sqlh mcp` query that embeds at query time. The alternative was keeping it allowed, given that only a DBA can define a model. A view or a user function over it stays invisible, as for the others (DESIGN.md §7).

56. **Read-only runs refuse a call of `sys.fn_ledger_retrieve_digests_from_url` (owner decision, 2026-11-07).** Asked "should `sys.fn_ledger_retrieve_digests_from_url` be refused now?", with refusing it by name like `OPENROWSET` recommended, and `fn_get_audit_file_v2` and `fn_full_dblog` going to decision 25's D4b, the owner's words: "yes, i'll go with your recommendation". Why: its definition reads from the URL its one argument names, so a query can put what it read in that URL, in a variable as well, with no model or anything else a DBA set up, decision 55's harm with less in its way; leaving it to D4b would have shipped it in 0.1.0. The cost: a read of ledger digests from a URL, and a user's function of that name. The evidence is its definition; it was never called.
