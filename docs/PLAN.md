## 3. New evidence from the test server

- **Connecting dominates every call.**
  - `SELECT 1` takes 171–265 ms inside sqlh, of which **162–254 ms is connect plus login**. The query itself, with setup and rollback, is about 10 ms. Ping to the server is 2.3 ms.
  - `-No` didn't help, so it isn't data-path TLS.
  - About 70 round trips' worth of time for a handshake that needs perhaps 5 points at something in the connect path: name lookups, SChannel credential setup, certificate parsing, or driver retries.
  - This is the largest lever on VISION's "time to the next useful answer". It also decides how urgent pooling is.
  - **Explained by 2.1** ([notes/connect-latency.md](notes/connect-latency.md)): about 150 ms of each connect is the login step, most likely the server hashing the SQL login's password (PBKDF2, new in SQL Server 2025), by design. That attribution is an inference from the measured interval. sqlh and the driver add about 5 ms.
- **A harness kill cancels server work promptly, for waits at least.** sqlh was killed with TerminateProcess during a 20 s `WAITFOR`. Within about 200 ms (the observer's own connect time) the server request and session were gone. CPU-bound and lock-blocked queries aren't measured yet.
- **The test login is sysadmin.** The over-privileged connection VISION.md worries about is the default situation here, and the read-only guard is the only thing standing between an agent and writes.
- **Draining has a cost.** Showing 100 of 299,398 `Users` rows took 1.3 s, all of it spent counting rows nobody sees. Bigger tables scale linearly.

The earlier sql-query-runner skill already allows these two, so they come from real use. (S)
- **Principle:** the allowlist says which commands are read-only. Whether a login may run one is the server's call, and database permissions stay the enforcement boundary (VISION.md). So a command belongs on the list because it only reads, not because this login happens to have the rights, and a login without the permission just gets the server's error.
- **First additions:** `xp_readerrorlog` and its wrapper `sp_readerrorlog`, and `xp_instance_regread`. Name them exactly: a prefix match on `xp_*` would also admit `xp_cmdshell` and `xp_instance_regwrite`, which stay blocked. `xp_instance_regread` reads registry values, which can disclose information; record that in the category notes.
- **Already allowed:** the skill's other diagnostics, `sp_who`, `sp_who2` and `DBCC TRACESTATUS`, pass sqlh's guard today (checked against the test server, 2026-10-12), so these two `xp_` procedures are all that sql-query-runner allows and sqlh refuses. The refusal also says the procedure "would write", which is wrong for an unknown procedure; the categorization should give it its own wording.
- **Candidates to evaluate in the same pass:** `xp_fixeddrives`, `xp_msver`, and `sp_configure` in its listing form only (with arguments it changes settings, so it needs the argument check `sp_spaceused` gets).

- **Acceptance:** table-driven guard tests (allowed bare and qualified as `sys.`/`master.`; `xp_instance_regwrite` and `xp_cmdshell` still blocked; stacked statements still refused); a live read of the error log; DESIGN.md §7 updated in the same change.

## 5. Sequencing rationale

- **1.1 (F04) first.** It is the only finding where the tool states something false while possibly executing writes.
- **The test harness comes before the other fixes,** so every fix lands with a process-level regression test.
- **2.1 (connect latency) early, but time-boxed.** It is cheap to measure and could change Phase 5 entirely. Building pooling to hide a fixable 150 ms would be the wrong order. Bounded output and cancellation under a stalled reader (2.2–2.4) are release requirements, so they come before pooling or more discovery features, whatever 2.1 finds.
- **The Runner refactor (3.1) after the correctness fixes and before schema/MCP work.** Fixing defects first keeps the refactor behavior-neutral and easy to verify; schema commands and MCP both need its policies.

6. **The drain default: a bounded count for read-only runs (owner decision, 2026-10-11).** Following [notes/drain-experiment.md](notes/drain-experiment.md): in read-only runs, sqlh counts hidden rows for about 250 ms and then stops (an attention), reporting a lower bound floored to one significant digit (`100 of ≥800000 rows shown (counting stopped)`), so a result that ends inside the budget stays exact and the same query gives the same output. The exact count stays under `--allow-write` (a stopped count skips later statements, which can include a `COMMIT`), for input that mentions `XACT_ABORT`, and on request (a flag such as `--exact-count`). Independently, `-t` expiring while only hidden rows are being counted reports `≥N` with the run's own exit code, not exit 4, since the rows shown are complete. A stopped count is visible to machines: the status line says so (`ok: 2 batches, counting stopped in 1`) and each JSON batch gets a flag. Accepted cost: "limits never change what runs" no longer holds strictly, because a stopped count cancels the rest of that batch; in a read-only run nothing it skips outlives the run, and the output says it happened. Task 2.15, built 2026-10-11. **Clarified in building it, confirmed by the owner 2026-10-11:** `-t` expiring during the count stays exit 4 (i) with writes allowed, because a stop would skip a later `COMMIT` and the run would report success, and (ii) with `XACT_ABORT` in the input, because the attention rolls the read-only wrapper back, so the run would end with exit 1, or exit 0 with the wrapper gone, in place of the timeout. The 250 ms start at the first hidden row, so a stall before it is bounded by `-t` (default 60 s). Each JSON result also says whether its `row_count` is exact, and the contract is 2.0 (R16).
7. **Agent session defaults (owner decision, 2026-10-11).** Every connection gets `SET DEADLOCK_PRIORITY LOW` (the agent is the deadlock victim, error 1205) and `SET LOCK_TIMEOUT 10000` in both modes, so a blocked query fails after 10 s with error 1222 instead of waiting out `-t`; the lock timeout can be changed by a flag and a profile setting. The isolation level stays the database default (`READ COMMITTED`, which honors read-committed snapshot where the DBA turned it on): `READ UNCOMMITTED` is opt-in only (a flag such as `--read-uncommitted` and a profile setting), for read-only runs only, never under `--allow-write`, and the output notes it, because dirty reads can silently return uncommitted, duplicated or missing rows. Task 2.8, built 2026-10-11. The flag in a run whose profile allows writes (`write_policy = "allow"`) is a usage error too, since that run can write.

9. **Ask upstream to redact the password in packet dumps?** At debug level, mssql-tds hex-dumps every TDS packet before TLS encrypts it (`io/packet_writer.rs`), including the login packet ([notes/connect-latency.md](notes/connect-latency.md)). Re-check the dump when bumping the driver.
10. **Provenance in the text output: always, on the status line (owner decision, 2026-10-11).** Every text and csv run that connected ends its status line with the server, the database the run started in and the connect time, for about 10 to 15 tokens a call: `-- ok: 1 batch, 241 ms; db01/master, connect 195 ms` (csv: on stderr with the rest of the metadata). Left out when nothing connected (usage error, guard refusal, failed connect). Names are escaped and cut like other metadata, within the ending's reserve. Auth method and encryption stay in JSON and `--verbose`. Shown every time, not only when `-d` was missing, so the shape of the status line doesn't depend on how the run was invoked. Rest of task 2.11, built 2026-10-11.
11. **Paths in metadata lines keep the escape rule (owner decision, 2026-10-11).** A backslash in a path inside a `-- ` line is written `\\`, like any other escaped field (DESIGN.md §5.1), and a reader decodes it like any other field. Input is never escaped: paths, SQL text and `-v` values are taken exactly as typed, so a path from Explorer's "Copy as path" (double-quoted, single backslashes) works as is after `-i` or `-o` in cmd.exe, PowerShell and Git Bash; only Git Bash eats an unquoted backslash, which is the shell's rule. Rejected: forward slashes (rewrites what was typed, and some cmd built-ins refuse them) and escaping a backslash only before an escape letter (changes the reader rule, and `C:\new` would still be doubled). Done 2026-10-11 in 2.13's follow-up: DESIGN.md §5.1 says paths follow the rule, the `--help` FORMAT lines say so without growing, and a process-level test runs a quoted "Copy as path" spelling, spaces included.
12. **Agents and the write switch (owner decision, 2026-10-12, from agent trial 2): new profiles refuse writes.** `sqlh profile add` saves `write_policy = "deny"` for a new profile unless `--write-policy` is given; existing profiles keep their policy, and a profile saved without the key is still `flag` (DESIGN.md §8). Built with task 2.16. **Decided 2026-10-12 (owner): `profile list` keeps showing the server's address and the login.** Every run's status line already names the server, and a login isn't a secret; hiding them would make choosing a profile harder for an agent without protecting anything. A control over what agents may see or change in profiles would be a separate design. The background: An agent asked to clean up a table added `--allow-write` on its own and ran a 927,269-row `DELETE`; only the profile's `deny` stopped it. Options: make `deny` the default for new profiles (so writes take an explicit change to the profile's policy), keep `flag` and rely on agent guidance (the skill, Phase 8), or both. Also: `sqlh profile list` showed the agent the server's address and the login; whether it should, in agent hands, is part of the same question. Precedent (comparison with the owner's earlier sql-query-runner skill, 2026-10-12): that skill gives agents no write path at all (a query must start with `SELECT` or `WITH`, or be one allowed `EXEC` or `DBCC TRACESTATUS`), so trial 2's cleanup would have stopped at its refusal. Its check is weaker than sqlh's, though: it looks only at the first word and runs with no rollback, so `WITH x AS (...) DELETE ...`, `SELECT 1; DELETE ...` and `SELECT ... INTO` pass and write. The nearest sqlh equivalent of "no write path for agents" is `deny` as the default for new profiles, which keeps the stronger guard and makes writing an explicit change to a profile's policy. That change can run unattended, so an agent that can run `profile add` can make it (R19): `deny` stops an agent reaching for `--allow-write`, it doesn't make writing a person's decision. A human-only control over profiles, if wanted, is a separate design.
13. **`profile list` is text only (owner decision, 2026-10-13, from R25).** Profiles are ancillary to the product: listing them is setup an agent does once per session, and text is the cheapest format to read. A json listing would need a document shape of its own (R25 found that the anonymous batch it used breaks contract 2.0's batch metadata), which isn't worth its cost now, so `--format` is refused for `profile list` and the JSON contract is unchanged. Search (`--search`) stays. Revisit only if a consumer that can't read text needs the list (Phase 8's MCP connector might).
14. **Connection reuse comes through MCP first (owner decision, 2026-10-15, Phase 5).** The reuse engine (connections kept open, reset between calls, the cleanup and clean-cancel rules) is built once as a library module, and `sqlh mcp` (docs/mcp-mode.md) is its first front end. A local per-profile daemon behind the CLI, which would speed up Bash-driven use too, is deferred: it would be added on the same engine only if evidence (an agent trial with MCP) shows Bash-driven use stays the main path. Why: VISION.md asks that reuse preserve execution policy, isolation between calls and reliable cleanup, and under MCP the harness owns the lifecycle and cancellation is part of the protocol, where a daemon would make sqlh build auto-start, stale-process, idle-exit, pipe-security and cross-process cancellation itself; MCP also gives native tools and separate read and write tools a harness can gate, and Phase 8 already plans the connector. The cost, accepted: until a daemon exists, a CLI call still pays its connect (about 195 ms on the dev LAN, 2.1).
15. **MCP calls are stateless, for now (owner decision, 2026-10-15, Phase 5).** Before every call the reused connection is reset (TDS RESETCONNECTION: login defaults restored, temp tables dropped, a stray transaction rolled back, the profile's database restored), then the session setup and, for reads, the per-call wrapper transaction run: each call behaves exactly like one CLI run, without the connect. No `session_open` handles, so docs/mcp-mode.md §5's sessions, and the hour-long read-only transaction they needed, are not built. Why: isolation between calls and reliable cleanup (VISION.md) come from the reset itself, a cancelled call can leave nothing behind but the connection, and agents and sqlh have no handles, expiry or long transaction to manage. Sessions can be added later on the same engine if an agent trial shows agents need state across calls. The cost, accepted: work that needs state across calls isn't possible read-only (a wait-stats delta is two snapshots the agent compares itself); within one call, a script's batches still share one connection and its temp tables.
16. **MCP is read-only, for now (owner decision, 2026-10-16, Phase 5).** The first `sqlh mcp` offers only read tools (`query`, the schema commands, `info`), each in the read-only wrapper with the guard, whatever the profile's `write_policy`; there is no `execute` tool, so docs/mcp-mode.md's write tool and write sessions are not built. A write goes through the CLI, with its safeguards: the profile's policy (`deny` by default for new profiles, decision 12), `--allow-write` and the guard. Why: the speed win matters most for the many repeated reads of an investigation; agent trial 2's agent added `--allow-write` on its own and only the profile's `deny` stopped a 927,269-row `DELETE`, and under an `execute` tool the last check would be the harness's permission prompt, which users often set to always allow; and Phase 6's command categorization is where which statements need explicit approval, and how, gets decided, so `execute` is added with it rather than designed twice. The cost, accepted: a write during an MCP investigation pays the CLI's connect.
17. **A connection is reused after a cancel only when the server confirmed it (owner decision, 2026-10-17, Phase 5).** A call that ends with a TDS attention (a cancel from the client or harness, `-t`, or the bounded count of hidden rows stopping at its budget, decision 6) keeps its connection when the server acknowledged the attention within the settle bound (R15 B); the reset before the next call (decision 15) clears what the cancelled call left: an open wrapper transaction, temp tables, `SET`s. Anything less discards the connection and the next call reconnects: no acknowledgement (today's `COUNT_STOP_UNCONFIRMED`), the settle grace running out, a protocol error, a lost connection. Why: count stops end any query with many hidden rows, so cancels are routine, and always discarding would make the calls agents make most pay the login again; the reset is the mechanism connection pooling relies on, and the unclear cases are the ones discarded. Required before it ships: a live test that a confirmed cancel leaves the next call clean (`@@TRANCOUNT` 0, the cancelled call's temp table gone, the agent session's `SET`s restored), and fake-server tests that an unacknowledged or stalled attention discards and reconnects. The cost, accepted: more code and tests than always reconnecting, and a residual risk of driver state the reset doesn't clear, which those tests are there to catch (the driver can be swapped behind `src/db/`). **Amended 2026-10-17 (owner), after spike 5.1:** mssql-tds 0.2.0 gives no receipt for an acknowledged attention, so "confirmed by the server" can't be checked; a connection the driver kept (`is_connection_dead()` false, which covers an acknowledged attention, a cancel before the request was sent and a half-sent request withdrawn with EOM|IGNORE, all in step with the server) is reused, and one it marked dead, or one past sqlh's settle bound, is discarded. The check that a reused session is clean is the next call's reset, whose acknowledgement the driver verifies (the server's ResetConnection ENVCHANGE must come first, or the request fails with `ConnectionResetNotAcknowledged` and the connection is marked dead); then the connection is discarded and the call retried once on a new one (decision 19). Why: what matters is whether the session is clean and in step, which the verified reset answers on every reuse after any kind of cancel; the spike found every kind clean after it (docs/notes/mcp-reuse-spike.md §2). The missing receipt is U4 in docs/notes/upstream-issues.md, for the owner to raise; the rule can tighten if upstream adds one.
18. **An MCP server reaches the profiles listed at its launch (owner decision, 2026-10-17, Phase 5).** `sqlh mcp --profile test --profile reporting` serves those profiles and no others; each tool takes an optional `profile`, which must be one of them (with one listed, it is the default). The server's instructions name the allowed profiles with their descriptions (4.1), so the agent picks the right server in one call; a profile's connection opens on its first use. No tool argument names a server, a login or a password (docs/mcp-mode.md §3 stands for those). Why: the owner sets the reach once, in the harness config, and the agent never gets more; profile descriptions keep their job under MCP; one copy of the tool definitions keeps the agent's context cost flat however many profiles are listed; and with read-only tools (decision 16) the risk within the list is reads from servers the owner chose. Strict separation stays possible: a profile can get its own server entry, listed alone, so the harness gates it separately. The cost, accepted: within one server's list, the harness can't prompt per profile.
19. **MCP connection limits (owner decision, 2026-10-17, Phase 5).** Per listed profile, up to 2 connections by default (`--pool N`, 1–8), opened only when a call needs one, so a second exists only when calls overlap. A connection idle for 15 minutes is closed (`--idle MINUTES`; 0 keeps connections open while the server runs). A reused connection found dead (a network drop, a killed session) is reconnected and the call retried once, silently; if the retry fails, the call gets the real error. Why: harnesses make several tool calls at once (parallel discovery), and two connections cover that without loading the server; 15 minutes covers a human pause mid-investigation and ends idle sessions on production servers well before firewalls drop them; and a retry is safe because every call is a read in a rolled-back wrapper (decisions 15, 16). The cost, accepted: the first call after a long pause pays the login again, and a busy session holds up to two server sessions per listed profile.
20. **MCP ships in the one exe, behind a size gate (owner decision, 2026-10-17, Phase 5).** `sqlh mcp` is a subcommand of `sqlh.exe`, not a separate `sqlh-mcp.exe`. Its code runs only when a harness launches `sqlh mcp`, so CLI-only use pays nothing for it at run time: no startup time, no memory, no open connections; the cost is disk, about 0.2 MB. **The gate:** MCP's measured cost (`cargo bloat --release --crates` and the exe size before and after, in 5.3) must stay within its 300 KB budget, and the exe within the 3 MB size budget; past that, this decision is reopened. Why: one exe is a hard constraint (AGENTS.md); a split would double the release work (two files to sign, version, ship and document) and let the CLI and MCP drift apart in version while they share the profiles and the output contract; and "only as much tool as you need" is about what runs and what can surprise a user, which dormant code does neither. Splitting later stays cheap, because the reuse engine is a library module (decision 14). Measured so far: JSON handling (`serde_json`) costs 65 KB (spike 5.1).
