# sqlh design

Status: MVP built 2026-10-09; product direction updated 2026-10-10. [VISION.md](VISION.md) records the owner's strategy and takes precedence over older roadmap and compatibility assumptions. Rows marked **Decided** in §2 are the owner's calls. Unbuilt features remain proposals.

## 1. Purpose

Agents such as Claude Code need to query SQL Server. `sqlcmd` works, but it fights them. The classic version needs the ODBC driver installed. Its output is padded for humans. It can block on prompts. It wants the password on the command line. It has no row or size limits, prints NULL ambiguously, and reports errors without enough context to fix them.

sqlh (`sqlh.exe`) is a single exe with no dependencies that runs T-SQL and returns compact, unambiguous, size-limited output. It never waits for input, reports errors that point at the failing line, and refuses writes unless asked.

The primary workflow is an agent with limited context making several queries across a human-led DBA or developer question-and-answer session. Optimize time to the next useful answer: focused discovery, concise output, low repeated-call overhead, and quick cancellation so the agent can try again. Bulk analytics are secondary. An exact total row count costs the size of the result (seconds for millions of narrow rows, minutes for gigabytes), so a read-only run counts the rows it does not show for about 250 ms (5 s when later statements in the batch could produce output) and then reports a lower bound, and exact counting is opt-in (§4.4; owner decisions 6 and 45).

**Non-goals:** an interactive REPL, the full sqlcmd scripting language (`:r`, `:connect`, `:!!`), a GUI, and non-Windows builds (they may come for free later).

### Why mssql-tds

Alternatives considered:
- **go-mssqldb:** mature and Microsoft-maintained, but produces an 8–10 MB exe.
- **tiberius-ng:** a community fork of the abandoned tiberius driver.
- **C++ on the legacy in-box "SQL Server" ODBC driver:** deprecated, has no TDS 8, and handles modern types poorly.
- **.NET Framework SqlClient:** ships with Windows, but pays the CLR startup cost.

`mssql-tds` is Microsoft's new Rust TDS core, the base for their Python driver core and a new ODBC driver. On Windows it uses SChannel for TLS, so there is no OpenSSL, and SSPI is built in.

The risk is that it is a preview (0.x): its API may churn and upstream takes no outside PRs. Mitigations:
- Pin an exact version.
- Keep all driver use inside `src/db/`.
- Keep tiberius-ng as the fallback.
- Record driver problems worth raising in [notes/upstream-issues.md](notes/upstream-issues.md), which the owner files from.

Milestone 0 is a spike meant to find any deal-breakers early.

## 3. Platform and build

- **Target:** `x86_64-pc-windows-msvc`. The first release runs on Windows x64 workstations, validated on Windows 11; the database server is usually remote, so network latency is part of every call. A Windows 10 / Windows Server 2016 floor is a later candidate, not a current support claim. ARM64 may come later.
- **Static CRT:** set `-C target-feature=+crt-static` in `.cargo/config.toml`. Without it the exe needs `vcruntime140.dll`, which isn't on a clean server.
- **Allowed imports:** only DLLs that ship with Windows (kernel32, advapi32, secur32/sspicli, crypt32, ncrypt, bcrypt, ws2_32, ntdll, and similar). Check with `dumpbin /dependents`.
- **Release profile:** `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `strip = "symbols"`.
- **TLS:** SChannel. Validate the encryption modes (mandatory and strict) from a first-release workstation against SQL Server 2025; evaluate older-platform TLS behavior when assessing the candidate 2016 floor.

## 4. CLI

### 4.1 Invocation

```
sqlh [conn] [opts] -Q "<sql>"            run, print, exit
sqlh [conn] [opts] -i a.sql [-i b.sql]   run files in order; "-i -" reads stdin
<sql> | sqlh [conn] [opts]               piped stdin when there's no -Q or -i
sqlh [conn] <command> ...                tables, describe, find, def, deps, dbs, info (§9)
sqlh profiles add|list|test|rm ...        human setup; the only command that may prompt
sqlh mcp --profile A [--profile B ...]   MCP stdio server (§10)
```

With no SQL source and stdin attached to a console, `sqlh` prints a short usage message and exits 3. It never waits. `profile` and `mcp` must be the first argument: `sqlh --profile x mcp` (or `... profile`) is a usage error, where it would have run the word as SQL. `sqlh mcp` with a console for stdin is refused too (exit 3); its usage errors go to stderr, since its stdout carries only protocol messages (§10).

Multi-line SQL goes in a file or on stdin, not in `-Q`. `-i file.sql` works in every shell. Stdin takes a different form in each: a heredoc in bash and Git Bash, a here-string in PowerShell, and in cmd.exe only `type file.sql | sqlh` or `sqlh < file.sql`.

```bash
sqlh --profile dev <<'SQL'
SELECT TOP 5 * FROM dbo.Orders ORDER BY OrderDate DESC;
SQL
```

```powershell
@'
SELECT TOP 5 * FROM dbo.Orders ORDER BY OrderDate DESC;
'@ | sqlh --profile dev
```

Input is decoded as UTF-8. A BOM is honored, including UTF-16LE (older SSMS saves files that way, and `>` in Windows PowerShell 5.1 writes it). Bytes that are not valid UTF-8 are refused with exit 3. So is wide text with no usable BOM, which NUL bytes would otherwise let through as valid UTF-8, for the guard to refuse with a false reason: UTF-32's BOMs (the LE one starts as UTF-16 LE's does), and NUL as the second and fourth bytes or the first and third (`-- error: f.sql: looks like UTF-16 without a BOM, or UTF-32 (NUL bytes among its first characters); save it as UTF-8, or UTF-16 with a BOM`). A NUL anywhere else is text, which the guard and the servers read as whitespace. For piped input the message says what to change: `-- error: stdin: not valid UTF-8 (byte 11); save it as UTF-8, or UTF-16 with a BOM. Piped text is encoded by the shell: in cmd.exe run chcp 65001 first, in Windows PowerShell run $OutputEncoding = [Text.Encoding]::UTF8 first, or pass the SQL with -Q or -i`.

**Shells.** cmd.exe and Windows PowerShell 5.1 are the baseline, because every supported Windows has them; Git Bash and PowerShell 7 should work too ([VISION.md](VISION.md)). Each shell rewrites the command line before sqlh sees it, so one line can arrive differently in each. The measurements are in [notes/windows-shells.md](notes/windows-shells.md), and the examples in `--help` are written to run unchanged in all four: a test runs them in cmd.exe, Windows PowerShell 5.1 and PowerShell 7 (`tests/cli.rs`, `the_help_examples_run_as_written_in_every_shell`).
- **`-Q "..."` is safe in every shell when the SQL is one line without `"`, `$`, `%` or a backtick**, with single quotes for string literals: `-Q "SELECT TOP 5 * FROM dbo.Orders WHERE Status = 'Open'"`. Otherwise put the SQL in a file. Each of those characters belongs to some shell:
  - `"` inside the SQL needs a different escape in each shell (`\"` in cmd.exe and bash, `'...\"...'` in Windows PowerShell 5.1, a plain `"` in single quotes in PowerShell 7), and Windows PowerShell 5.1 drops it without an error. Write quoted identifiers as `[name]`.
  - `$` starts a variable or a `$(...)` subexpression inside double quotes in PowerShell and bash, sqlh's own `$(var)` included. Use single quotes there, `-Q 'SELECT $(db)'`; a single quote in the SQL is then `''` in PowerShell and `'\''` in bash.
  - cmd.exe replaces `%name%` when that variable exists (`LIKE '%temp%'` becomes the temp folder's path), and in a batch file every `%` has to be doubled.
  - A backtick is PowerShell's escape character, and cmd.exe can't carry a line break in a command line.
- **Quote what has a backslash or parentheses**, as `-S "db01\SALES"` and `-S "(localdb)\MSSQLLocalDB"` or `-i "C:\my dir\f.sql"`: Git Bash removes an unquoted backslash, PowerShell reads `(` as the start of an expression, and a path with spaces needs quotes in every shell. `host,port` needs none.
- **Piped text is encoded by the shell.** PowerShell 7 and Git Bash send UTF-8. Windows PowerShell 5.1 encodes with `$OutputEncoding`, US-ASCII by default, so every non-ASCII character arrives as `?`: the run succeeds with a changed literal, and sqlh can't tell. Set `$OutputEncoding = [Text.Encoding]::UTF8` first (the BOM it sends is accepted) or use `-Q` or `-i`. When the command's output is captured (`$r = $sql | sqlh ...`, or `... | Out-File`), 5.1 sends two BOMs, and one even with a BOM-less `$OutputEncoding`; `decode` drops every BOM at the very start, so these work too (measured 2026-11-08; before, the second was refused as `<U+FEFF>SELECT starts the batch`); `Get-Content file.sql | sqlh` also reads the file in the ANSI code page, so use `-i`. cmd.exe encodes `echo` and pipes in the console's code page, where an accented letter is not valid UTF-8 (refused, as above) and a character the page lacks becomes `?`: run `chcp 65001` first. `type file.sql | sqlh` and `sqlh < file.sql` pass the bytes unchanged.
- **Captured output is decoded by the shell.** sqlh writes UTF-8. A console shows it correctly under any code page (§11). When PowerShell captures it (`$r = sqlh ...`) or pipes it, it decodes with `[Console]::OutputEncoding`, the console's code page, so non-ASCII text arrives garbled unless that is UTF-8: set `[Console]::OutputEncoding = [Text.UTF8Encoding]::new($false)` first, or write `-o file` and read it with `Get-Content -Encoding UTF8`. A harness that only forwards PowerShell's stdout is not affected (the bytes come back unchanged); a script that handles the text, or writes it with `Out-File` or `>`, is.
- **csv puts its `-- ` lines on stderr** (§5.3). Windows PowerShell 5.1 turns each stderr line of a native program into an error record: decorated with `2>&1` or `2> file`, and with `$ErrorActionPreference = 'Stop'` the first one throws. text and json keep everything on stdout.

### 4.2 Flags

Precedence is: flags, then the profile, then `SQLCMD*` environment variables, then defaults.

The profile is chosen by `--profile`, then by `SQLH_PROFILE`. Failing both, the file's `default` profile applies, but only when no server was given by `-S` or `SQLCMDSERVER`; giving a server means you mean a different one.

These flags are sqlcmd-compatible:

| Flag | Meaning |
|---|---|
| `-S server` | `host`, `host\instance`, `host,port`, with an optional `tcp:` prefix. Env: `SQLCMDSERVER`. sqlh connects over TCP. Unlike sqlcmd, it doesn't fall back to Named Pipes for a remote name: the driver's first pipe open is a synchronous call on its runtime thread, so an unreachable host would hold the run for about 21 s, past `-l` and Ctrl+C. Local names (`.`, `(local)`, `localhost`, `127.0.0.1`, `::1`, LocalDB) keep the driver's order: shared memory, TCP, then a local pipe. An IPv6 address gets `tcp:` like a name, with or without a port or an instance (`-S "2001:db8::5\SALES"` is SQL Browser, then TCP only), since mssql-tds 0.4.0 splits a protocol off an address; on 0.3.0 it couldn't, and sqlh added port 1433 instead.<br>**A Named Pipes request to another machine is refused** (exit 3, before anything connects): an `np:` prefix with a remote host (`np:db01`, `np:db01\SALES`, an IPv6 address such as `np:2001:db8::5\SALES`), or a UNC pipe path (`\\db01\pipe\sql\query`, `\\2001:db8::5\pipe\sql\query`) with or without a prefix. The message gives the TCP spelling: `-S db01`. It applies to every source of the server (`-S`, `SQLCMDSERVER`, a profile), and `profiles add` won't save one. Local pipes are accepted: `np:` with `.`, `(local)`, `localhost`, `127.0.0.1`, `::1` or this computer's own name as the driver reads it, its DNS host name (owner decision 73: the name the driver takes as local, which the environment can't change; `COMPUTERNAME`, the NetBIOS name, only if the driver has none, so on a machine whose name is longer than 15 characters `np:` with the short name is refused), and `\\.\pipe\...`. So are `lpc:` (shared memory, local only), `admin:` and `(localdb)\name`, which are passed to the driver as written.<br>**In a shell, quote a name that has a backslash or parentheses** (§4.1): `-S "db01\SALES"`, `-S "(localdb)\MSSQLLocalDB"`. Git Bash removes an unquoted backslash and PowerShell reads `(` as the start of an expression. `-S db01,1433` works unquoted in cmd.exe, PowerShell and Git Bash. |
| `-d db` | Database. Env: `SQLCMDDBNAME`. Without it, the profile's database applies, else the login's default, which is often `master`. |
| `-E` | Windows integrated auth. This is the default when there is no `-U`, same as sqlcmd. The SPN is built for each login hop (owner decision 72): after a hop's TCP connect, prelogin and TLS, the driver calls sqlh's provider (`db::spn`, the driver's `SecurityContextProvider`) with the host and port it dials, which is the port given or 1433, SQL Browser's port for a named instance, 1434 for `admin:`, and each routed host's own, `-K ReadOnly`'s included. sqlh looks the host up on a thread of its own and waits at most 500 ms (owner decision 79): a name, short or full, by a forward lookup's canonical name (`GetAddrInfoW` with `AI_CANONNAME`, `src/dns.rs`; the wide API, decoded fallibly, so an answer that isn't valid UTF-16 is no answer and the name stays as given, R67), so a short name gets its DNS suffix and an alias (a CNAME) its host's name; an address as the driver would, by a reverse lookup (about 5 s when it has no PTR record, notes/connect-latency.md, Windows authentication). The driver's own rule for a short name is forward then reverse, which takes whatever a PTR record says: in an Azure domain it named Azure's host, not the domain's, so a login by short name was NTLM where Microsoft's SqlClient got Kerberos (upstream-issues.md U13). In time, the SPN is `MSSQLSvc/<name found>:<port>`, built by the driver's `make_spn`; past that, `MSSQLSvc/<host>:<port>` with the host as dialled, the driver's own when its lookup fails, so such a login is NTLM unless Kerberos has an SPN for that name. A loopback name, as the driver's `is_loopback_address` reads one (`localhost`, `127.*`, `::1`, `.`, this computer's DNS host name), isn't looked up, as in the driver; a local `\\.\pipe`, shared memory and LocalDB arrive as `localhost`, and a pipe named by host under that name. A dotted name goes to the forward lookup too, which the driver's rule doesn't do, so an alias's SPN is its host's. Either way sqlh sets the SPN, so the driver makes no lookup of its own, which has no bound of its own and at `-l 3` or less would fail a login by address (upstream-issues.md U9). At most 4 lookups run at once in a process; a wait for one comes out of the 500 ms, and a lookup left running past it holds its place until it ends (R53). The wait is inside the login deadline (`-l` + 1 s), once per hop, so a routing redirect can add one. A cancel ends the connect at once; the wait can't be cut, and it ends by itself within 500 ms on a thread nothing waits for. Before decision 72 (to 0.1.0's driver upgrade) sqlh ran the lookup before the connect, outside `-l`, and left a named instance without a port and `-K ReadOnly` to the driver's own lookup (R52). |
| `-U user` | SQL login. The password comes from the profile's credential or `SQLCMDPASSWORD`. Env: `SQLCMDUSER`. |
| `-P` | **Rejected** with exit 3 and a message pointing to profiles or `SQLCMDPASSWORD`. Command lines end up in agent transcripts and process lists. |
| `-Q sql` | SQL text to run. `-q` is treated as `-Q`, because there is no interactive mode. |
| `-i file` | Input file. Repeatable. The path may be `C:\dir\f.sql`, `C:/dir/f.sql` (any mix of slashes), a UNC path (`\\server\share\f.sql`) or relative to the working directory, and may have spaces (quote it in the shell, §4.1). **A Git Bash path** such as `/c/dir/f.sql` is converted by Git Bash itself before sqlh sees it. cmd.exe and PowerShell don't, and Windows reads it as `\c\dir\f.sql` on the current drive. When a path written that way isn't found, the usage error (exit 3) names the spellings that work: `-- error: -i /c/dir/f.sql: The system cannot find the path specified. (os error 3); that is a Git Bash path, which only Git Bash converts; in cmd.exe and PowerShell write C:\\dir\\f.sql or C:/dir/f.sql` (the text format doubles each backslash, §5.1). A path that is found is used as written, whatever it looks like. Only `/<letter>` followed by `/` or the end counts: `//server/share` is a UNC path, and `/tmp/x` gets no hint. The same goes for `-o` and `SQLH_CONFIG`. |
| `-o file` | Write output to a file (UTF-8). Input is read and checked first, so a bad input never touches an existing file. Naming an input file (however spelled, including a hard link) is refused with exit 3, and so is an existing file that can't be written. Each run writes its own new `file.<pid>-<n>.partial`, which no other process can change, and renames it over `file` when the output is complete: the file is replaced whole or not at all. A run whose output isn't complete, or that is killed while writing, leaves no `.partial` file behind: Windows deletes it when the last handle closes, because the file is marked for deletion as soon as it is created. If that mark can't be set (not expected), a run that ends normally still removes the file by name, but a kill, or an error while removing it, can leave it behind. A kill in the moment between finishing and the rename can leave one in either case. sqlh never touches a `.partial` file it didn't create. When runs overlap, each publishes a complete file and the last one wins. A device or pipe (`-o NUL`, `\\.\pipe\name`) is written directly. The path takes the same forms as `-i`, including UNC (the `.partial` file is created and renamed on the share), and the same Git Bash hint when its folder isn't found. The check against the input file compares the files, not the spellings, so `C:\x\a.sql`, `C:/x/a.sql`, `.\a.sql` and `\\localhost\C$\x\a.sql` are one file. |
| `-v n=v ...` | Values for `$(n)` substitution. Environment variables also resolve, as in sqlcmd. |
| `-x` | Turn off `$(var)` substitution. |
| `-l sec` | Login timeout. Default 15; 0 means none, as in sqlcmd. A name can resolve to several addresses (`localhost` has `::1` and `127.0.0.1`), and they are tried in turn, once each: nothing is retried. Each TCP connect attempt gets `-l` seconds, and the whole login (all the attempts, TLS, Windows auth's SPN wait of up to 500 ms a hop, and login) one second more. When every attempt fails before that deadline, the run ends with **exit 2**; a refused attempt takes about 2 s, because Windows retries it, so refusals at two addresses end after about 4 s. When the deadline expires first, the run ends with **exit 4**: a server that takes the connection but doesn't finish the login, or a later address's attempt still running at the deadline (`-l 2` against two refusing addresses: the first attempt ends at 2 s, and the deadline at 3 s cuts the second). So a name with one address that refuses or doesn't answer is exit 2, and a name with several can be either, depending on how long each attempt takes. With `-l 0`, a TCP connect ends only when Windows gives up on it, after about 21 s, and a login has no deadline; Ctrl+C still ends it. |
| `-t sec` | Query timeout per batch. Default 60; 0 means none. sqlcmd's default of none is wrong for agents. It is sqlh's own deadline, measured on the clock from when the batch is sent until its last result has been read, whatever the time goes to: the server, rows already in the read buffer, formatting, a slow reader (§4.4). It is also how long sqlh waits for a reader that stops reading its output (exit 7, §6). |
| `-b` | Accepted. Stopping at the first failing batch is already the default. |
| `-c term` | Batch terminator, one word. Default `GO`. One that is empty or holds whitespace is a usage error (exit 3): empty would make every blank or comment-only line a terminator, and one with a space could never match, so `GO` lines would go to the server. |
| `-C` | Trust the server certificate. `--trust-server-certificate=false` turns off a profile's saved trust for one run. Strict encryption (`-Ns`) checks the certificate anyway (§8). |
| `-N[s\|m\|o]` | Encryption: strict, mandatory or optional. Default mandatory. |
| `-K ReadOnly` | Application intent, for routing to AG readable secondaries. With Windows auth, each routed hop gets its own SPN (`-E`). |
| `-M` | Multi-subnet failover: connect to every address the name resolves to at once, and use the first that answers (Always On listeners). Without `-M` sqlh always tells the driver off, never its default (owner decision 40: mssql-tds 0.3.0's default is on, or `MSSQL_RS_MULTISUBNET_FAILOVER_DEFAULT`), so addresses are tried one after another. With `-M` on mssql-tds 0.3.0, measured 2026-10-31: the race of every address is bounded by `-l` itself; when no address answers in time it is a connect failure, exit 2, `no address accepted a TCP connection within 2 s (-M tries them all at once)` (`-M -S 192.0.2.1 -l 2`: 2.0 s; worded by sqlh since the review of the upgrade, where the driver's timeout had been reported as a missed login deadline, exit 4); a refusal reads `Connection Error: All parallel connection attempts failed to localhost:1` (2.1 s for `localhost,1`, where sequential took 4.1 s); a named instance without a port is refused before connecting, exit 2 (`Usage Error: MultiSubnetFailover requires an explicit TCP port for a named instance`); Ctrl+Break cancels a `-M` connect as any other (exit 6). An `np:` to a remote host is still sqlh's own refusal, exit 3, as for `-S`. Read from the driver's source (`resolve_policy`), not measured: local names (`.`, `localhost`, `(local)`) connect over TCP, and a local `np:`, `lpc:`, `admin:` and LocalDB are refused by the driver before connecting, exit 2 (`MultiSubnetFailover is only supported with TCP connections`). |
| `-h -s -W -w -y -Y -e -r -m` | sqlcmd formatting flags. Accepted and ignored, with one `-- note:` line, so models' sqlcmd habits don't break. |

These long flags are our own:

| Flag | Meaning |
|---|---|
| `--profile NAME` | Connection profile (§8). Env: `SQLH_PROFILE`. |
| `--format text\|json\|csv` | Output format (§5). Default `text`. `md` is planned. |
| `--max-rows N` | Rows shown per result set. Default 100; 0 means unlimited by this limit: `--max-output` (1 MB by default) still caps the whole response, and its footer names it (`-- 14448 of 52000 rows shown (--max-output)`), so every row needs `--max-output 0` as well. |
| `--max-cell N` | Characters shown per cell. Default 500; 0 means unlimited. |
| `--max-results N` | Result sets shown per run. Default 20. The rest are counted, not printed. Messages are capped at 100. |
| `--max-output N` | Bytes of output per run, across stdout and stderr. Default 1000000; 0 means no limit, and otherwise it must be at least 4096. See §4.4. |
| `--allow-write` | Turn off the read-only guard, if the profile's write policy allows it (§7). |
| `--lock-timeout SECONDS` | How long a statement waits for a lock before it fails with error 1222, `Lock request time out period exceeded.` Default 10; 0 means no limit, as `-t 0` does (the server's `LOCK_TIMEOUT -1`); at most 2147483 (about 24.8 days), because the server takes milliseconds in an `int`, and a larger value is a usage error. Same in read-only and `--allow-write` runs. Profile key `lock_timeout`, saved by `profiles add`. There is no environment variable, as for the other limits. A lock wait is not a query timeout: it ends with exit 1 at this limit, normally well before `-t` (§4.3, §6). |
| `--read-uncommitted[=true\|false]` | Read without shared locks (`SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`), so a read neither waits behind other sessions' writes nor blocks them. **Off unless asked for:** the session setup otherwise sets READ COMMITTED, a fresh login's level and the database's default, which honors `READ_COMMITTED_SNAPSHOT` where the DBA turned it on (§4.3). **Read-only runs only** (§4.3). With `--allow-write`, or with a profile whose `write_policy` is `allow` (so the run can write), the flag is a usage error (exit 3) that says why: a write could be based on rows that were never committed. A profile's `read_uncommitted = true` is ignored in a run that can write, silently: the run reads committed data. (No `sqlh mcp` call can write, so there an `allow` profile's `read_uncommitted = true` holds; mcp-mode.md §3.) `--read-uncommitted=false` turns off a profile's setting for one run. When it is in effect the run says so once, as a note written after the session is set up and before the first batch, so it comes ahead of the results: `-- note: reads were uncommitted (--read-uncommitted): rows may include uncommitted, duplicated or missing data` (in json it is an entry of the `notes` array, in csv a line on stderr). The note counts against `--max-output` like any note (§4.4). It is the same text whether the flag or a profile asked for it; in `sqlh mcp`, whose calls take no flag, the parentheses say `(the profile's read_uncommitted = true)` (mcp-mode.md §4). `--check` reads nothing, so it gets READ COMMITTED and no note. Profile key `read_uncommitted`, saved by `profiles add`. |
| `--exact-count[=true\|false]` | Count every row that is not shown, however long that takes, instead of stopping after about 250 ms (§4.4). Without it, a read-only run counts the rows past `--max-rows` (and those a limit hides otherwise) for 250 ms and then stops, so the total is a lower bound (`≥N`). A run that can write (`--allow-write`, or a profile whose `write_policy` is `allow`) and one whose input mentions `XACT_ABORT` count exactly whatever this says. `-t` still applies to an exact count (§4.4). `--exact-count=false` turns off a profile's setting for one run; it does not lift the two cases above. Profile key `exact_count`, saved by `profiles add`. |
| `--check` | Compile only: `SET NOEXEC ON`, executes nothing. Catches syntax errors and unknown columns of existing tables. Missing tables are only reported when a query runs, because SQL Server defers their resolution. Input that mentions `NOEXEC` is refused (exit 5; §7 lists the false positives), NOEXEC is re-armed before every batch, and the rolled-back wrapper transaction always applies. With `--allow-write`, write statements may be compiled; they still don't run. A later version could add `sp_describe_first_result_set` per statement. |
| `--continue-on-error` | Keep running later batches after a failed one. |
| `--stats` | **Planned, not built (M3):** turn on `SET STATISTICS IO, TIME` and print a summary instead of the raw messages. Until then the flag is refused as an invalid option (exit 3). |
| `--verbose` | Diagnostics to stderr. Never includes secrets. | `--help`, `--version` | `--help` is read by models: example-first and under about 60 lines (a test holds it to 62). Any other build (a developer's, CI's check) is `Cargo.toml`'s version with `-local`, so it never passes for a release. Build metadata (`+...`) isn't taken. **The Windows version resource** (Explorer's Properties > Details) carries the same: `FileVersion` and `ProductVersion` hold the whole version. The rest: `ProductName` `sqlh`, `FileDescription` `sqlh - SQL Server query tool for agents`, `CompanyName` `Tom Willwerth`, `LegalCopyright` `Copyright (c) 2026 Tom Willwerth`, `OriginalFilename` `sqlh.exe`, US English. **The icon** (Explorer, the taskbar) is `assets/sqlh.ico`, drawn by `scripts/make-icon.py` (Pillow; a dev tool, so building sqlh needs no Python): a navy tile holding a white database cylinder with an amber `>_` prompt, at 16, 24, 32, 48 and 256 pixels, each a palette PNG, 5,980 bytes in all (the exe grows 6,656). `build.rs` writes each image as an `RT_ICON` and the directory naming them as an `RT_GROUP_ICON` (name 1), in the same .res file as the version resource. |

### 4.3 Execution semantics

- **Batch splitting.** A line holding only the terminator splits batches. The match is case-insensitive and allows surrounding whitespace, an optional `GO n` repeat count, and a trailing `--` comment. Terminators inside string literals and block comments don't count, which is stricter and more correct than sqlcmd.
- **Variables.** `$(var)` is substituted after splitting, batch by batch, so a variable can't create a batch separator: a value of `GO` stays inside its batch. An unknown variable is a usage error (exit 3). Error lines stay mapped to the input even when a value contains line breaks. `$(SQLCMDPASSWORD)`, in any case, is never read from the environment, unlike every other name: it would put the password sqlh logs in with into SQL text, and so into rows, refusals and the server's errors (§8). It is a usage error (exit 3) that names it, `-x` leaves the text alone, and `-v SQLCMDPASSWORD=x` is that value like any other. Every other environment variable still resolves, as in sqlcmd; PLAN.md §4 has that question. `sqlh mcp` has no substitution at all (§10).
- **Fail fast.** The whole input is read, split and guard-checked (§7) before anything runs.
- **Execution.** Batches run in order on one connection. Every error a batch raises is reported. After a batch with an error of severity 11 or higher, later batches are skipped unless `--continue-on-error` is set. An error that ended the read-only wrapper stops the run whatever is set (§7).
- **Application name** (decision 30(c)). The login names what the run may do, so `APP_NAME()`, `program_name`, `sp_who2` and `sp_WhoIsActive` tell a DBA a read-only run from a write run:
  - `sqlh`: a run in the read-only wrapper (§7). That is a read-only CLI run, `--check` even with `--allow-write`, and sqlh's own SQL (the schema commands and `sqlh profiles test`), whatever the flags or the profile's `write_policy`.
  - `sqlh mcp`: every connection of `sqlh mcp`'s read tools. The name is fixed at login, so a pooled connection keeps it.
  - `sqlh (writes)`: `--allow-write` or `write_policy = "allow"`, in a run that has no wrapper.
  - `sqlh (allow: K,...)` for a kind grant comes with the grants (decision 32, Part 2 of Phase 6; not built).

  The client asserts the name, so it is a courtesy label, not evidence.
- **Session SET options** match SSMS: `ANSI_NULLS`, `ANSI_PADDING`, `ANSI_WARNINGS`, `ARITHABORT`, `CONCAT_NULL_YIELDS_NULL` and `QUOTED_IDENTIFIER` ON, and `NUMERIC_ROUNDABORT` and `XACT_ABORT` OFF. That way filtered and computed-column indexes behave as people expect. (§14 covers the ARITHABORT question.) `XACT_ABORT OFF` is sent, not assumed: a new session inherits the server's `user options` default, and with `XACT_ABORT` ON the attention that stops a count or `-t` rolls the read-only wrapper transaction back (§4.4, §7). It is in the first batch, ahead of the wrapper's `BEGIN TRANSACTION`, so it costs no round trip, and it is the same in read-only and `--allow-write` runs. The input may `SET XACT_ABORT ON` itself; such input is counted exactly (§4.4).
- **Agent session defaults** (owner decision 7, plan-history.md 2.8). Every connection, in read-only and `--allow-write` runs alike, gets `SET DEADLOCK_PRIORITY LOW` and `SET LOCK_TIMEOUT 10000` in the same first batch as the options above, ahead of the read-only wrapper's `BEGIN TRANSACTION`. An agent's queries give way to production work instead of waiting behind it:
  - **A lock wait ends at `--lock-timeout`** (default 10 s; 0 sends `SET LOCK_TIMEOUT -1`, no limit). The statement fails with error 1222 (severity 16, `Lock request time out period exceeded.`), long before the 60 s default of `-t`. The server ends only the statement: the batch's later statements still run (unless `XACT_ABORT` is ON), and so do later batches with `--continue-on-error`, because the transaction and the session carry on. The timeout covers waits for locks only: a query that is merely slow runs until `-t`, and a lock wait longer than `-t` (`--lock-timeout 0`, or a value above `-t`) is cut by `-t` as a query timeout (exit 4).
  - **A deadlock is lost by sqlh.** At priority LOW (-5), sqlh's session is chosen as the victim against any session at a higher priority, such as the default NORMAL (0); between sessions of equal priority the server picks the one whose rollback is cheaper. The statement fails with error 1205 (severity 13, `Transaction (Process ID n) was deadlocked ... chosen as the deadlock victim. Rerun the transaction.`) and the server rolls the transaction back, so a read-only run (whose wrapper transaction is gone, §7) stops there, and an `--allow-write` run has nothing from that transaction left. Retrying is the agent's decision.
  - **Both are ordinary SQL errors:** exit 1, the normal error line with `line` mapped to the input like any other (`-- error 1222 (severity 16, state 45, line 4): Lock request time out period exceeded.`, where line 4 is the statement in the file), and the later batches skipped unless `--continue-on-error`. A result set that was waiting for its first row when the lock wait ended is written as its header and `-- 0 rows`, then the error line (§5.1, "Order of events"). Neither is exit 4: that is `-t`.
  - **They are defaults, not enforcement.** The input may `SET LOCK_TIMEOUT` or `SET DEADLOCK_PRIORITY` itself (the guard allows these `SET` statements), and the new value holds for the rest of the run.
- **Isolation level.** The session setup sets it on every connection, in read-only and `--allow-write` runs alike: `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`, after `SET LOCK_TIMEOUT` and before the wrapper's `BEGIN TRANSACTION`, in the same first batch, so it costs no round trip. READ COMMITTED is a fresh login's level and the database's default, and it honors `READ_COMMITTED_SNAPSHOT` where the DBA turned it on, so a read then doesn't wait for writers at all; a CLI run reads as it would without the `SET`. **Why it is sent, not assumed:** `sqlh mcp` reuses connections (§10), and the reset a reused connection gets (`sp_reset_connection`) restores the login's options on SQL Server (all but Azure SQL Database) but not the isolation level, so a call that ran `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` (which the guard allows) would otherwise hand that level to the next call on its connection. Checked live: the reset leaves SERIALIZABLE in place, and the setup after it gives READ COMMITTED ([notes/mcp-reuse-spike.md](notes/mcp-reuse-spike.md) §1). **READ UNCOMMITTED is opt-in only,** by `--read-uncommitted` or a profile's `read_uncommitted = true` (§4.2), and for read-only runs only, because a write based on a dirty read could store rows that never existed. Under `--allow-write`, or a profile that allows writes, the flag is a usage error and a profile's setting does nothing (except in `sqlh mcp`, where no call can write, so an `allow` profile's `read_uncommitted = true` holds; §4.2, mcp-mode.md §3).
  - **What it does:** the setup batch sets `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` in place of READ COMMITTED, after `SET LOCK_TIMEOUT` and before the wrapper transaction begins, so every statement reads without shared locks: it doesn't wait behind writers and doesn't block them. Dirty reads can silently return rows that are later rolled back, the same row twice or not at all (when pages split or move during a scan), so the run says so once, as a note (§4.2), and the docs and the note both say "may".
  - **What it doesn't do:** it doesn't help against schema-modification locks (`ALTER TABLE`, an index build), which readers under any isolation level wait for, so the lock timeout stays. And `--check` runs nothing, so it gets READ COMMITTED and no note.
  - **Checked live** (`tests/cli.rs`, `a_blocked_read_fails_after_the_lock_timeout_unless_it_reads_uncommitted`): a `SELECT COUNT(*)` of a table with another session's open insert waits and fails with 1222 after `--lock-timeout 2`, and with `--read-uncommitted` returns 1, the uncommitted row, at once. The scratch database has row versioning off, which the test relies on: with `READ_COMMITTED_SNAPSHOT` on, the plain read would not wait.
- **READ UNCOMMITTED in the SQL** (decision 30(a)). `NOLOCK` or `READUNCOMMITTED` as a table hint, and `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`, are never refused; the guard allows the `SET` for the rest of that run (the next run's or call's setup sets the level again). They give the run one note, in the same place as the setting's (§4.2): after the session setup and before the first batch, an entry of json's `notes` array, a line on stderr in csv, counted against `--max-output` like any note (§4.4):
  - **The wording:** `-- note: some reads were uncommitted (NOLOCK in the SQL): rows may include uncommitted, duplicated or missing data`, with `READUNCOMMITTED` or `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` in place of `NOLOCK`. An input with more than one kind names each, in that order and across all its batches, so the reader knows what to take out: `(NOLOCK, READUNCOMMITTED in the SQL)`. `TRAN` for `TRANSACTION` is named as `TRANSACTION`. `sqlh mcp` words it the same, since it names no setting.
  - **Once a run,** however many times they occur and however many batches, or `GO n` repeats, hold them.
  - **Under `--read-uncommitted`** or a profile's `read_uncommitted = true`, every read is uncommitted, which says more: the run has that setting's note alone.
  - **`--check` reads nothing:** no note, with or without `--allow-write`. A refused run has none either.
  - **`--allow-write`:** the same note. The classifier doesn't run there, but this is a separate pass over the text (`guard::uncommitted_reads`, in `run::prepare`), and a write based on a dirty read is where the note matters most. sqlh's own SQL (schema commands, `profiles test`) isn't scanned.
  - **A hint is what SQL Server takes as one,** checked on 2016 and 2025. **`WITH (...)`:** a bare word of the list at its own depth, followed by `,`, `)` or another hint, and not after `=`: so `WITH (INDEX(1), NOLOCK)` and `WITH (NOLOCK INDEX(1))` count, and `WITH (INDEX = nolock)` and `OPENJSON(...) WITH (nolock int)` don't. **The legacy form without `WITH`:** `t (NOLOCK)` or `t a (NOLOCK)`, the hint alone in its parentheses (the server refuses or misreads a list there: errors 1018, 207), bare or quoted (`([NOLOCK])`, `([NOLOCK ])`, which the server takes as the hint), on a table named after `FROM`, `JOIN`, `USING` or a comma that follows such a table, qualified or not (`tempdb..#t (NOLOCK)`). A `FROM` inside an expression starts no table list: `TRIM(x FROM y)`, `a IS [NOT] DISTINCT FROM b`. `OPTION (TABLE HINT(t, NOLOCK))` needs the same hint in `WITH` (error 8722), so it adds nothing to look for. Hints and the level (`ISOLATION`, `LEVEL`, `UNCOMMITTED`) are spelled as §7's tokens are, and compared as it says for a word the servers don't reserve, so `(<U+0274>OLOCK)` and `NOLOCK<U+0218>` count. What opens a table list or turns the search off (`FROM`, `JOIN`, `USING`, `WITH`, `TRIM`, `DISTINCT`, `READ`) goes by the exact spelling, so an alias such as `DISTINCT<U+200D>` can't silence the note. An alias spelled like a temp table (`FROM t #a (NOLOCK)`) and a leading dot (`FROM .sys.objects (NOLOCK)`) are the servers' reads too, and count.
  - **Names don't count:** a column, an alias (`FROM t nolock` is the classic slip: an alias, and the read is committed), a `[NOLOCK]` column, a string, a comment, a column list (`INSERT #t (nolock)`, `WITH c (nolock) AS`, a derived table's or a function's `v (nolock)`) and a function's arguments in a list (`f(1, nolock)`) raise nothing. Nor does a batch that defines a module (`CREATE [OR ALTER]` or `ALTER` of a procedure, view, function or trigger), which stores its text without reading.
  - **Spellings:** each word of a hint, what follows `NOLOCK` with spaces, and the level's words go by the comparison of §7, repeat marks too: `WITH (READUNCOM<mark>ITTED)`, `WITH (NOLOCK FORCESEEK<joiner>)`. `USING<joiner>` opens no table list, since `FROM t USING<joiner> (NOLOCK)` in a read is an alias and a hint, so `MERGE t USING<joiner> s (NOLOCK)`, which needs `--allow-write`, gets no note.
  - **The limits, all from reading only the text.** It speaks for the input, not for what ran: a branch not taken, a batch skipped after an error, or a level `SET` back again still raises it. It can say too much in one shape: `FROM f(nolock)`, a table function given an outer query's column named nolock, reads like the legacy form; so does a `TRIM(x FROM f(nolock))` nested more than 63 parentheses deep, past what the scan tracks. It misses a legacy hint on a table list continued past a derived table or an `ON` (`FROM (SELECT 1 AS x) a, b (NOLOCK)`, `FROM a JOIN b ON 1 = 1, c (NOLOCK)`) and one after `APPLY`, where `f(nolock)` is more likely a function given a left-side column; a `WITH (NOLOCK)` in those places is seen. Dynamic SQL and the hints inside a view or procedure aren't seen at all.
  - **Cost:** one more pass of the lexer before the connection, with lookahead of at most five tokens and only at a `(` after a table, a `SET`, or a hint word; 105 ms for a 10 MB batch, against 97 ms for the classifier's own pass (measured with a release test build). No budget, like `mentions_xact_abort`.
  - **Checked live** (`tests/cli.rs`, `sql_that_reads_uncommitted_reads_past_a_write_and_says_so`, on 2016 and 2025): each form reads the row of another session's open insert and says so, and `FROM t nolock` waits, fails with 1222 and says nothing. `mcp_query_says_when_the_sql_reads_uncommitted` does the same through `query`.
- **Error line numbers** are mapped back to the original input: a file and line, not just a line within the batch.
- **Query timeout** is sqlh's own deadline for the batch (§4.4). When it passes, sqlh sends a TDS attention, reports `-- error: query timeout after 60 s in batch 2; raise -t or narrow the query` and exits 4. In `sqlh mcp` the advice names the call's `timeout` argument instead, and offers it only when it can go higher: a call below the server's limit gets `raise timeout (the server allows up to 60 s) or narrow the query`, and one that already had the limit (as a call without a `timeout` does) `narrow the query (60 s is the server's limit)` (`run::raise_timeout`, mcp-mode.md §4). The exception is a read-only run whose rows shown are complete and that is only counting the rows it doesn't show: it stops the count and ends with its own exit code (§4.4).
  - **A timeout before the first batch says where it struck.** The session setup is sqlh's own first request on the connection (`run::setup`, which the CLI and `sqlh mcp` share: the CLI runs it inside `run::open`), bounded by `-t` through the driver's own timeout (§4.4, "What `-t` bounds"). When that runs out it ends `-- error: query timeout after 60 s in the session setup`, exit 4, with no advice, since none of the input was running. In `sqlh mcp` a call's `database` adds a second such request, its `USE` (`run::use_database`): `query timeout after N s changing to the call's database`. (Until `becb56f` both were a bare `query timeout`.) On a reused connection in `sqlh mcp` the setup gets at most 5 s (a probe), and a setup the probe cuts is set up again, alone, on the same connection when the driver kept it and on a new one when it is dead, with the call's own timeout, so in every result a client gets such a message names the call's own timeout; the `USE` comes after the setup has worked, with the call's timeout, once on its connection (mcp-mode.md §5). (The engine calls `run::setup` and `run::use_database` apart, so that its probe bounds and repeats the setup alone, `4519341`; the CLI calls `run::open`, which runs the two in turn, and has no `USE`, since it connects to its database.)
- **Cancellation.** Ctrl+C, Ctrl+Break, the console closing, logoff and shutdown cancel the run wherever it is: connecting, setting up the session, running a batch, waiting for a slow reader, or delivering the last of its output.
  - A running statement gets an attention. sqlh waits up to 2 s for the statement to stop, or 1 s after a close, logoff or shutdown, because Windows ends the process about 5 s after those. Then it closes the connection, which stops the server's work too. A pending connect is dropped at once. No later batch starts.
  - The run exits 6 and says what became of the work: `-- error: cancelled by Ctrl+C: the statement was cancelled; the connection stayed usable`, or `...: the server didn't confirm the cancel, so the connection was closed` (the driver marked the connection dead), `...: nothing confirmed the cancel within 2 s, so the connection was closed` (the grace ran out; 1 s after a close, logoff or shutdown), `...: cancelled while connecting`, `...: cancelled while waiting for the reader; the connection was closed`. sqlh never says that the server confirmed a cancel: the driver marks the connection dead when its attention goes unacknowledged and offers no receipt otherwise, and a connection not marked dead is a liveness observation (a cancel before the request was sent leaves it unmarked too). A run whose batches had all finished keeps its own outcome.
  - The closing lines get 1 s to reach the reader, not the stall limit `-t`; past that, the run is exit 7 and stderr gives exit 6 and the reason (§6).
  - **Signals are handled through final delivery and `-o` publication.** The listeners are registered once the input has been read and checked, and they outlive the run: they stay until the closing lines are delivered and `-o` output is moved into place. Without them Windows' default handling would end sqlh at the next Ctrl+C or Ctrl+Break with status 0xC000013A, no diagnostic, and, with `-t 0`, nothing would bound the wait for the reader. A signal while the closing lines wait for the reader gives the rest 1 s, with `-t 0` too. So does a signal that arrived while the last batches finished, too late to change the outcome. If everything is delivered in that second, the run keeps its own exit code, since its SQL had finished. If not, the exit is 7, and stderr names the run's own exit code and the signal: `sqlh: output could not be delivered (the reader stopped reading for 1 s; cancelled by Ctrl+Break while delivering); the run itself ended with exit 0: ok: 1 batch, 41 ms`. A signal during the move of `-o` output into place is swallowed: the move is short, and it finishes.
  - **The end-to-end bound after a signal** is the grace for the work to stop (2 s, or 1 s after a close, logoff or shutdown), plus 1 s for the closing lines, plus at most 0.5 s for `--verbose` lines and 0.5 s for a last-resort message (§6). A signal that arrives during delivery costs 1 s plus those. That holds for a signal during a connect's name lookup too: the connect is dropped at once, and the lookup, which runs on a blocking thread (mssql-tds's `tokio::net::lookup_host`), is abandoned at the end, not waited for, since the CLI shuts its runtime down without waiting once the run, its delivery and its `-o` publication are over (`runtime.shutdown_background()` in `app::run_command`, `dc24d4b`; before, dropping the runtime waited for that thread, so the exit could come past this bound). `sqlh mcp` does the same (mcp-mode.md §2, The end), where, with a lookup pending, the exit came 1.2 to 2.6 s after its end began before `shutdown_background` (`6e7a0d8`) and 15 to 45 ms after it; in the CLI it is neither measured nor tested. `sqlh mcp` also takes console events through its whole end but its last wait, for its `--verbose` lines (at most 0.5 s, as here, which takes none since nothing is left to cut), under one deadline that a later event can only bring nearer (R36, `6e1a6e7`: about 2 s after a close, logoff or shutdown, 3 s after Ctrl+C or Ctrl+Break, plus that 0.5 s). `sqlh profiles test` runs like any run (`app::run_command`), so this bound applies to it. `sqlh profiles add`, `list` and `rm`, and usage errors found before the run starts, run without a runtime and have no listeners: their wait for the reader ends at the stall limit or when the signal's default effect ends the process.
  - Before it connects, while it reads and checks the input, Ctrl+C ends sqlh at once; nothing has run. A process started in a new process group gets no Ctrl+C from Windows, so a harness sends it Ctrl+Break. Windows sends logoff and shutdown only to services; other processes are just ended.
  - A harness that kills sqlh outright also cancels the server's work. Measured with TerminateProcess ([notes/harness-kill.md](notes/harness-kill.md)): a waiting, a CPU-bound and a lock-blocked request had ended within 0.14 s of the connection dropping in all 46 runs, and a killed blocker's locks were released within 0.13 s. What a kill can't shorten is the rollback of a big open transaction, which takes about as long as the work did (237 MB of log: 5 to 15 s) while other sessions that need the changed rows wait. A kill that reaches only the shell that started sqlh ends nothing: sqlh runs on until `-t`.
- **Malformed input never crashes sqlh.** Unterminated strings and names reach the server, which reports the syntax error.
- **Expected failures are results, never crashes,** including a closed stdout or stderr (§6).
- **A bug that panics still exits 10,** never an abort. Everything else about it is best effort: a stderr line, and a status line on stdout in text output if stdout takes it. Output still buffered is lost, a JSON document stays unfinished, `-o` output isn't published, and a password prompt's console mode is restored. Panic injection (`SQLH_DEBUG_PANIC`) exists only in debug builds, so the tests exercise the hook there; release builds have the same hook.

### 4.4 Output limits

These keep a careless query from flooding an agent's context:

**Product direction:** quick cancellation is essential to iterative investigation, so a limit must not make a call cost the size of the result. Owner decision 6 (PLAN.md §6, plan-history.md task 2.15) chose a bounded count of the rows that are not shown; the measurements behind it are in [notes/drain-experiment.md](notes/drain-experiment.md).

- **Rows.** After `--max-rows`, rows stop being formatted and are only counted. The count is bounded, in this way:
  - **Read-only runs count for about 250 ms,** from the first row that is not shown in a result set, then stop. A result that ends inside the budget is exact, as it always was, and later statements run: `-- 100 of 48213 rows shown (--max-rows 100)`. **In a batch where a stop could cancel a later statement's output, the budget is 5 s** (`db::LATER_STATEMENTS_BUDGET`, decision 45), so a modest result over a slow link ends inside it and the batch runs whole. `guard::several_outputs` decides this from the batch's text, erring toward yes. It counts the statements at parenthesis depth 0 that can return rows or messages: every statement start but `DECLARE`, `SET`, `USE`, `IF`, `BEGIN`, `END`, `ELSE`, transaction and cursor housekeeping. `EXEC`, an implicit procedure call, `WHILE`, `GOTO` and `DBCC` count as two, since a procedure returns several results, a loop repeats its own, and a `DBCC` command can return several (`SHOW_STATISTICS`: header, density vector, histogram). So does a `SET` of an option that adds output to the statements after it: `STATISTICS` (`PROFILE`, `XML`, `IO`, `TIME`) or a `SHOWPLAN_` option, `OFF` included. Such an option lasts for the session, so `guard::sets_output_modes` makes the batch that sets it and every later batch of the run get the 5 s too (R48). The query of a common table expression and a `SELECT` after `UNION`, `EXCEPT` or `INTERSECT` continue their statement and aren't counted. sqlh can't tell from the server's replies which statement a result came from, so in such a batch the last result gets the 5 s too. A result that doesn't ends with a lower bound, floored to one significant digit: `-- 100 of ≥800000 rows shown (--max-rows 100; counting stopped)`. Flooring makes the same query give nearly the same output when the link's speed differs: the counts a 250 ms budget reaches differ by a factor of 2 to 20 between runs, so the first digit mostly holds, and a count near a power of ten can still come out one digit up or down. Flooring never hides that rows were hidden: once a hidden row was counted, the bound is at least one more than the rows shown, so 154 rows counted with 100 shown read `100 of ≥101`, not `≥100`. When no hidden row had arrived yet (`-t` ran out while the server was still looking for the first one, below), the bound is the rows shown, `100 of ≥100`. The rows counted are those past `--max-rows`, those of a result set `--max-results` hides (no footer, the note below says it), and those the `--max-output` budget has no room for (the footer then names `--max-output`).
  - **How it stops.** sqlh sends the server an attention, the cancel Ctrl+C uses, from a timer, so even a server that is still looking for the next row cannot hold the count up. The server acknowledges it in 3 to 420 ms (the data in flight), stops its work, and the session survives: its transaction, temp tables and settings are intact. The cancel is of that batch's statement, so **the rest of the batch does not run**, and the output says so (§5.1): the footer, a note naming the batches and the status line (`counting stopped in N`). `GO` batches are separate requests: each starts as usual on the same session, with its own count. In JSON each result says whether its `row_count` is exact and each batch whether counting stopped (§5.2). If the server does not acknowledge the budget's attention within the driver's 5 s, the connection is closed and the run ends with exit 6 (§6); `--exact-count` has no budget, so no such cancel.
  - **Where the clock starts.** At the first row that is not shown, in each result set. Until one arrives nothing is being counted and the 250 ms do not run, so a server that is slow to produce it (a search that finds the first 100 matches at once and takes a minute for the 101st) is waited for, and only `-t` (default 60 s) bounds that wait. The run then ends as "The query timeout" below says, with the rows shown as the bound.
  - **Exact counting** (every row read, later statements run, as before this change) is used for: `--allow-write`, or a profile whose `write_policy` is `allow` (a stopped count skips later statements, and one of them can be the `COMMIT`; a transaction left open is rolled back when sqlh disconnects, so the write would be lost without a failure); input whose tokens include `XACT_ABORT` (with it on, the attention rolls the transaction back, and the read-only wrapper with it, which ends the run with exit 1 by sqlh's own invariant; the guard's tokenizer finds the word as it finds `NOEXEC`, so dynamic SQL in a string is not seen, which is no gap in a read-only run, since the guard refuses dynamic SQL; a server whose `user options` setting turns `XACT_ABORT` on for every session needs no case of its own, because the session setup sets it OFF before the wrapper begins (§4.3), so a stopped count leaves the wrapper in place there too, checked live with a session that starts with it ON); and on request, `--exact-count` or a profile's `exact_count = true`. Exact counting costs the size of the result: 1 to 4 s for millions of narrow rows, minutes for a few gigabytes.
  - **The query timeout** `-t` still applies, and ends exact counting like anything else, with one exception. When it expires while only rows that are not shown are being read or awaited, the rows shown are complete, so the count stops as above, reports `≥N` and the run ends with its own exit code (0, or 1 for SQL errors), not 4. The bound is the rows counted, floored as above, or the rows shown when no hidden row had arrived. This holds for a read-only run whether its count is bounded or `--exact-count` made it exact, and the note then advises raising `-t` (§5.1).
  - **What `-t` bounds (R15).** The elapsed time of a batch, measured by sqlh on a monotonic clock: a deadline of `-t` seconds from the moment the batch is sent until its last result has been read, in every kind of run (bounded count, `--exact-count`, `--allow-write`, `--max-rows 0`). It covers all the time the batch takes, not only the time spent waiting for the server: reading rows that are already in the read buffer, the chunks of a large value, formatting, waiting for a reader that is slow but not stalled (a stalled one is exit 7, §6), and a loop of many small result sets, whose count budget starts again with each result and so never ends the batch. `-t 0` means no deadline. The driver's own `timeout_secs` is not used for batches: it adds up only the time its transport reads wait (and, since mssql-tds 0.4.0, the request's send, in the same budget, cutting a send that stalls, which leaves the connection dead), so data that is already buffered never uses it (`--allow-write -t 1` on 10 million narrow rows ran 7.4 s to the end, and a loop of 20 million one-row results ran 92 s), and it cannot see sqlh's own work. It is still sent, as `-t`, with sqlh's own short statements (the session setup, `SET NOEXEC ON` and `OFF`, the closing rollback), which normally return at once. In `sqlh mcp` a call's `USE` gets it too, with the call's timeout; a reused connection's setup gets at most 5 s instead (the probe); and `put_back`'s `SET NOEXEC OFF;` and rollback, for a wrapper a cancel or timeout left open, get 2 s in all (`ROLLBACK_WAIT`) (mcp-mode.md §5). A setup on a server under load, or a `USE` waiting for its database to open, may not return at once: §4.3 ("A timeout before the first batch says where it struck") and mcp-mode.md §5 say how those end.
    - **How it is kept.** A timer fires the deadline while sqlh waits for the server or for the reader. The loops that read rows, chunks and statements look at the clock every few hundred hidden rows, a few dozen shown rows or a few big chunks (about 3.5 ns per row), and give the runtime back at least every 10 ms, so that the timer, the count budget and Ctrl+C run on the one runtime thread even when the data never makes sqlh wait. Measured in a release build on 10 million narrow rows the pacing could not be told from the noise (docs/notes/drain-experiment.md).
    - **How it ends the batch.** The statement is cancelled through a handle of its own, a child of the run's handle that is the parent of the count budget's, like the budget's cancel. The driver sends the attention, reads on to the server's acknowledgement and settles its state. Ctrl+C cancels the same statement through the run's handle, and wins: a deadline and a user's cancel that meet end the run with exit 6. A wait for the output gate (a reader that reads slowly) ends at the deadline too, and the connection is closed, as for a cancel there. A reader that stalls completely mid-batch therefore ends the batch at the deadline (exit 4) before the writer's own stall clock reaches `-t`; the batch's error line cannot be delivered either, and the closing lines then wait a full stall limit, so the run ends at about twice `-t` with exit 7 and stderr naming exit 4 as the run's own code (§6).
    - **Finishing late is not finishing.** A batch the driver has finished is a success only if it finished in time. The loops look at the clock only every so many rows, so the last few rows' work, or a final DONE that was already in the buffer, can carry a batch past `-t` without a look catching it. What matters is the phase the time went to, not what comes next. After each row to show (its reading, its formatting, the wait for the reader) sqlh checks the deadline: past it (and with no user cancel), the batch ends with exit 4 and the result is not closed as complete, even when that row filled `--max-rows` and the next would be hidden, since no hidden row was being counted. Where a result or the batch ends, it checks again: past it, a result whose rows to show were still coming, or any result in a run where `-t` may not stop a count (writes allowed, `XACT_ABORT` input), ends the batch with exit 4; so does the end of the batch. The owner's exception holds only for time spent after the shown rows were done: in a read-only run, a result whose shown rows were complete in time and whose hidden rows (or the wait for the final DONE) took it past `-t` is complete and exact, and a batch that ends right after it is a success.
    - **The grace.** The batch is over within `-t` plus the time the driver takes to settle the cancel, and never later than `-t` plus 5 s, a bound sqlh keeps itself. Settling an attention is the time the server takes to send what is already in flight: tens of milliseconds in a release build, up to 2 s measured in a debug build that cannot keep up with a 10-million-row stream; the driver waits for it 5 s at most, then marks the connection dead. A server in the middle of an operation that cannot be interrupted (one `REPLICATE` of hundreds of megabytes) answers only when it ends. The driver has a longer path too: a request it was still sending when the cancel came between two of its packets is withdrawn (EOM with IGNORE), and the server's DONE for that is awaited up to 120 s, with the cancel no longer applying (mssql-tds 0.2.0, and 0.3.0 unless a caller opts into its settlement budget, which sqlh doesn't: docs/notes/driver-0.3.0.md §2). So sqlh bounds the whole batch, not one read: 5 s after the deadline it drops the batch's work wherever it stands, retires the session (nothing more is sent on it) and ends the run with exit 4; the connection is closed, which ends the server's work. The `-t 1` timing tests (`timed_run`) allow `-t` plus those 5 s on sqlh's own clock, the run's time less its connect (the status line's time and `connect N ms`, or JSON's `elapsed_ms` and `connect_ms`), with 0.5 s for the session setup and the close, and the whole process 5 s more, enforced while it runs: past it the run is killed and fails with what it wrote (`tests/cli.rs`, `timed_run` on `run_bounded`, R43; until then that bound was checked only once the run ended, which a hung run never does; every other wait in the tests for a run's end is under a watchdog too, `finish` at 300 s or a test's own `wait_within`, but for one AGENTS.md names, which also lists the waits for a run's progress that are not); measured from outside, the connect counted against the bound, and a run that needed the whole 5 s on a busy server failed by its connect time (plan-history.md, Phase 5.4).
    - **Outcomes.** As above and below: exit 4 with `-- error: query timeout after N s in batch M; raise -t or narrow the query` where rows that would be shown are produced or awaited, with writes allowed, with `XACT_ABORT` in the input, and when the deadline falls between statements or results; the stopped count and the run's own exit code where only hidden rows are being read or awaited in a read-only run. In a read-only run that loops over many small results the deadline can fall in either place, so the exit is 4 or 0 (with `counting stopped`).
  - **Where `-t` stays a failure (exit 4),** with the timeout message and no stopped count:
    - **Writes allowed** (`--allow-write`, or a profile whose `write_policy` is `allow`): stopping would skip the statements that follow, and a skipped `COMMIT` has to be a failure, not a run that reports success with its write rolled back at disconnect. This is the reason these runs count exactly at all.
    - **`XACT_ABORT` in the input:** the attention that stops the count rolls the read-only wrapper transaction back, so the run would end with exit 1 (sqlh's own invariant, §7, checked before each batch and after the last) in place of the timeout. This is the reason these runs count exactly at all.
    - **Rows that would be shown are awaited:** `--max-rows 0`, or fewer rows have arrived than `--max-rows` allows. The rows shown are then incomplete.

    So the rule of owner decision 6 (`-t` expiring while only hidden rows are being counted reports `≥N` with the run's own exit code) holds in every run that loses nothing by it.
- **Cells.** A cell longer than `--max-cell` is cut at a character boundary and ends with `…[+N]`, where N is the number of characters left out. A binary value shows at most `--max-cell / 2` bytes and ends with `…[+N bytes]`. The result set's footer counts the truncated cells, and a note at the end of the run, among the limit notes (§5.1), counts them for the whole run and says how to see one whole: `-- note: 2 values were cut (--max-cell 500); read one in pieces with SUBSTRING, or raise --max-cell` (`1 value was cut`). A value cut only in a schema command's labeled sections, whose SQL is sqlh's own, can't be read in pieces, so the note then ends `; raise --max-cell to see them whole` (`it` for one). In `sqlh mcp` it names the call's argument, `max_cell`. Added after agent trial 3 (plan-history.md 5.6), where a model told not to raise `max_cell` read `…[+48197]` exactly but didn't think of reading the rest with `SUBSTRING`.
- **Result sets and messages.** Past their caps (for example, a `WHILE` loop that selects or prints), output is counted, not printed.
- **Row counts.** Consecutive row counts within a batch become one line, `-- 300 statements, 300 rows affected`, so a loop of inserts prints one line rather than 300. A result set, message or error in between starts a new line.
- **Total output.** `--max-output` (default 1,000,000 bytes; 0 = no limit, otherwise at least 4096) caps the whole response in every format: the bytes sqlh writes to stdout (or `-o`) and stderr together never exceed it. They are counted as encoded UTF-8 after escaping, so a `\x01` costs 4 bytes and a `\u2028` 6. Everything counts: data, metadata, result footers, csv's `-- result` markers, JSON's brackets and closers, notes, a guard refusal, the closing error, the status line and `--verbose` lines. The exceptions are `--help` and `--version`; the last-resort messages on stderr when delivery itself has failed (exit 7) or sqlh has crashed (exit 10); and a usage error in the options themselves, found before `--max-output` is known, which keeps to the default cap. An error found after that, in a profile, in the input or at `-o`, keeps to the cap like any other output.
  - **The body** (result sets, rows, messages, errors, row counts, batch markers, and json's description of the connection) is written piece by piece while each piece fits in what the cap has left after a reserve of 1,024 bytes (and, in text and csv, the status line's tail, below). Once one doesn't fit, nothing more of the body is written, even a small piece. The result set being shown still ends with its footer, `-- 80 of 500 rows shown (--max-output)`. JSON stays a valid document, with the cut result marked `"truncated":true`.
  - **Text of any length** is shortened to fit, as a cut cell is: it ends with `…[+N]`, N being the number of characters left out (counted before escaping; a cut never splits an escape sequence or a character). That covers notes, a guard refusal, the closing error, the limit notes below, and `--verbose` lines.
    - A note, a refusal or a `--verbose` line is shortened when it is written, to what the cap has left less 640 bytes. JSON counts a note from the moment it arrives, although the document gets it last.
    - A guard refusal is cut in its variable parts only: the location, the reason (which can quote a huge identifier) and the advice. The words between them stay, so the agent still reads that nothing was run and what to do: `-- blocked: line 1: UPDATE [aaaa…[+16537]; nothing was run. Rerun with --allow-write if the write is intended`.
    - The closing error and the limit notes are shortened when the run ends, to what the cap has left after the status line. When several need cutting they share that room evenly: a short one stays whole, and the long ones are cut by the same size.
    - Text that cannot fit even as a bare marker is dropped and counted, and the closing note says so: `...these weren't shown: 1 note`. That stops the body too, like any piece that didn't fit.
  - **The end is never cut.** The status line (JSON: `ok`, `exit_code`, `summary`, `elapsed_ms`) is always written whole, and in text and csv the result being shown gets its footer, in JSON the open result and batch their closers. Two reserves make room for them, and in text and csv a third piece, the status line's tail:
    - The body stops 1,024 bytes short of the cap (the reserve above). The rest of the run's end uses that room: the footer or closers, the closing error, the note that the output stopped and what wasn't shown (counts of result sets, messages, errors, row counts, batches, notes and the connection description), and the status. At the minimum cap of 4096 bytes the body has 3,072, less the tail.
    - Notes, refusals and `--verbose` lines stop 640 bytes short of the cap, however full it is (it was 512 before the stopped count, whose longer footer, `row_count_exact` and `counting_stopped` and `counting stopped in N` took JSON's widest ending to 561). The widest ending that has to fit those 640 bytes (a footer or JSON's closers, which include the batch's `elapsed_ms` and `counting_stopped`, and the status line, with every number at its widest and the longest status line sqlh builds) takes 561 bytes in JSON (the closers of an interrupted result, whose `row_count_exact` is always `false`) and 399 in text and csv, and the tests hold both to the 640. sqlh builds the status line from bounded parts and never shortens it; if a status line ever grows, the 640 must grow with it. In text and csv that is the status line without its tail.
    - **The status line's tail** (text and csv, §5.1): on a run that connected, `; db01/master, connect 195 ms` ends the status line. Its length depends on the names in it, so it is in neither constant. The sink holds back the tail's own length when the connection is described, before the first batch, on top of both reserves: the body then stops 1,024 bytes plus the tail short of the cap, and notes 640 bytes plus the tail. The status line, tail included, still comes out of that room and is never shortened.
      - A usual tail is about 30 bytes, which is what a connected run gives up of its body.
      - The widest one is 1,609 bytes: two names of 255 characters (the most a TDS name field holds) that are all six-byte escapes, each cut to 128 characters and ended by `…[+127]` (777 bytes), the `/`, and a connect time of 39 digits. A test builds it, and the sweeps of `--max-output` from 4096 up run with it. After it the smallest cap the CLI accepts still has 1,463 bytes of body.
      - Raising `STATUS_RESERVE` by the widest tail instead was rejected: it is about 2,100 bytes, with `OUTPUT_RESERVE` raised to match, for every run with a cap to protect against names that no SQL Server hands out, and at 4096 it would take half the body. The cost of reserving the actual tail is that the room is promised once, at the connection: notes written before it (the one about ignored sqlcmd flags) may have used it already, only with a cap near the minimum. The tail is then left out, the closing note counts it (`1 connection description`), and the budget is spent, as for JSON's `connection`. The status line is whole without it.
  - **Shortening changes no outcome.** A refusal is still exit 5 and a SQL error exit 1; the exit code, the status line and the JSON outcome fields say what happened whether or not the text around them was cut.
- **Limits change what runs in one way only.** The row, cell, result, message and output limits stop printing, and nothing else: the run continues to the end, and the counts (errors, row counts, the status line) stay exact. The exception is the bounded count above (owner decision 6, amended by decision 45): in a read-only run, a result set with more hidden rows than the budget reads ends its batch, and the statements after it in that batch do not run. Where there could be such statements the budget is 5 s, and a run that still lost them ends `-- partial:`, not `-- ok:` (§5.1). Nothing it skips outlives the run, because the wrapper transaction is rolled back at the end anyway; a later batch that depends on a skipped statement (a temp table it would have filled) can still be affected, which is why the output says it happened, in the footer, a note, the status line and JSON's `counting_stopped`. Where a skipped statement could be a write or a `COMMIT`, or an attention would roll the transaction back, counting is exact and nothing is skipped.
- **Input.** At most 10 MB of SQL per run, across `-Q`, `-i` files and stdin, and again after `$(var)` substitution; `GO n` runs a batch at most 1000 times. Past either, the run is refused with exit 3 before anything connects.

## 5. Output formats

All formats stream. None holds a whole result set in memory.

### 5.1 text (default)

```
-- result 1
id:int	name:nvarchar(50)	created:datetime2(7)
1	Alice	2024-01-05T09:12:00.0000000
2	Bob	2024-02-11T14:30:00.0000000
3	O'Neil\tCo	NULL
-- 3 rows
-- msg: cleanup starting
-- 12 rows affected
-- error 208 (severity 16, state 1, line 14): Invalid object name 'dbo.Nope'.
-- failed (exit 1): 1 error, first in batch 2, 48 ms; db01/AppDb, connect 31 ms
```

**Line types**

- Lines starting with `-- ` are tool metadata. Every other line is data.
- **Header line:** after `-- result N`, one `name:type` entry per column, tab-separated.
  - The type is everything after the last `:`, so names can contain colons. A type name never does: a `:` in one (only a CLR UDT's name comes from the server as is) is written `\x3A`. A reader splits a header entry at its last literal `:` first, then unescapes the name and the type separately.
  - An unnamed column has an empty name, as in `:int`.
  - Types carry their length or precision: `nvarchar(50)`, `varchar(max)`, `decimal(18,2)`, `datetime2(7)`.
- **Data rows:** tab-separated values.
- **Batch marker:** `-- batch N (line L)` appears only when the input has more than one batch.
- **Footer** after each result set: `-- N rows`, plus any truncation notes. With rows hidden: `-- 100 of 48213 rows shown (--max-rows 100)`, the limit that hid them in the parentheses (`--max-rows N`, or `--max-output`). When the count of hidden rows was stopped (§4.4) the total is a lower bound, written with `≥` and floored to one significant digit (and, once a hidden row was counted, at least one more than the rows shown: `-- 100 of ≥101 rows shown (--max-rows 100; counting stopped)`), and `counting stopped` ends the parentheses: `-- 100 of ≥800000 rows shown (--max-rows 100; counting stopped)`, `-- 610 of ≥1000 rows shown (--max-output; counting stopped)`. `; 8 values cut (--max-cell 500)` and the like follow as before. A result set hidden by `--max-results` has no footer.
  - **In `sqlh mcp`** the limit is named as its client can change it (`output::Advice`, mcp-mode.md §4): the call's arguments `max_rows N` and `max_cell N`, and `the server's --max-output`, a launch flag no call changes: `-- 100 of ≥800000 rows shown (max_rows 100; counting stopped)`, `; 8 values cut (max_cell 500)`. A cut definition's header (below) and the limit notes follow the same rule: `(the server's --max-output, max_cell 4000)`, `N more result sets not shown (at most 20 per call)`, and the output budget's note, `output stopped at the server's --max-output limit of N bytes; the run continued` (until `05032c0` it read `at the the server's`). The shape of each line is the CLI's.
  - **A result a SQL error ended** (the rows that arrived before, say, a divide by zero on the third row) has an incomplete footer, so a reader can't take its count for the total: `-- 2 rows so far (interrupted)`, or with rows hidden by the limit `-- 2 of ≥7 rows shown (--max-rows 2; interrupted)` (`≥` because rows after the error never arrived; `--max-output` replaces `--max-rows N` as above). `; 8 values cut (--max-cell 500)` follows as before. It is written where the normal footer would be, so the order is unchanged: the rows, this footer, the messages held, then the error. Only that result is incomplete: the ones before it, a later one in the same batch and those of later batches under `--continue-on-error` have the ordinary, exact footer. JSON marks the same result `"interrupted":true` with `"row_count_exact":false` (§5.2), and csv writes this footer on stderr (§5.3). A run that dies mid-result (a cancel, a timeout, a lost connection) has no footer for it at all: the failure's own lines say why.
- **Counting stopped:** two more places say so, so that a reader of any of them learns what the stop cost. A note at the end of the run, before the status line. Its first part depends on whether the stopped batch could have shown more (`BatchInfo::later_statements`, decision 45):
  - **A batch with later statements** (`guard::several_outputs`): `-- note: counting stopped in batch 1: the rest of that batch was cancelled, so its later statements did not run; put each query in its own batch (GO) to keep them; --exact-count counts every row`. Several such batches: `counting stopped in batches 2, 3: the rest of each was cancelled, so their later statements did not run; ...`.
  - **A batch with one statement that shows anything:** the stop cancelled nothing, so the note says only `-- note: counting stopped in batch 1, so its total is a lower bound; --exact-count counts every row`, or `in batches 1, 3, so their totals are lower bounds`.
  - **Both kinds:** `counting stopped in batches 1, 2, 3: the rest of batch 2 was cancelled, so its later statements did not run; ...`, or `the rest of batches 2, 3 was cancelled, so their ...`.
  - **Names:** a list names up to five batches, then counts the rest: `2, 3, 4, 5, 6 (+3 more)`. Its advice follows what stopped the counts: `; --exact-count counts every row` when the 250 ms budget did, which `--exact-count` lifts; `; raise -t to count longer` when `-t` did, including in a run that already has `--exact-count`; and both, in that order, when a run had both kinds of stop. In `sqlh mcp`, whose client can pass neither flag, the same note names what can change instead: `; a COUNT_BIG(*) query counts every row, as does exact_count = true` (the `query` tool's own argument since decision 45) and `; a larger timeout counts longer` (`output::Advice`, mcp-mode.md §4; the count since agent trial 3, plan-history.md 5.6, where the model ran one of its own while the note advised only the profile key, which a call couldn't set then; `COUNT_BIG`, not `COUNT`, since R44: the count was stopped because the result is large, and `COUNT` returns `int`, which fails past 2,147,483,647 rows); a call that already had the server's `-t` is offered no larger timeout, so its note leaves that advice out (`Limits::timeout_at_limit`). And the status line counts the batches: `-- ok: 2 batches, counting stopped in 1, 241 ms; db01/master, connect 195 ms`, also in every `failed (exit N): ...` line, before the time (`-- failed (exit 4): timeout, counting stopped in 1, 5012 ms`). A batch whose rest a stop cancelled is named after that, `, the rest of batch 2 not run` (`batches 1, 3`; five named, then `(+N more)`), and a run that would otherwise be `ok` is then `-- partial: 3 batches, counting stopped in 2, the rest of batch 2 not run, 5241 ms; ...`, still exit 0 (decision 45). Nothing is added to a run that stopped no count.
- **Statement summaries:** `-- N rows affected` for DML. Consecutive ones become one line, `-- 300 statements, 300 rows affected` (§4.4).
- **Messages:** `-- msg: text` for PRINT and messages of severity 10 or lower. Where one lands is under "Order of events" below.
- **Errors:** `-- error <num> (severity S, state T, line L[, proc P]): message`.
- **Notes, refusals and the run's error:** `-- note: text`; `-- blocked: line L: reason; nothing was run. advice` for a guard refusal (exit 5), whose reason says what sqlh knows of the statement (`UPDATE dbo.T would write`, `ALTER EVENT SESSION would write`, `EXEC sp_WhoIsActive isn't on sqlh's list of read-only procedures, so sqlh can't tell what it does`) and whose advice says what to do (§7 has them all); `-- error: text` for why the run stopped early (the closing lines come in this order: the error, the notes about limits that hid output, the status). With a short `--max-output` their variable text ends in `…[+N]`, N the characters left out (§4.4). The reason can quote an identifier of any length, so it is the part that gets cut; `; nothing was run.` and the advice are not.
- **Final summary:** the last line of complete output: `-- ok: ...`, `-- partial: ...` (exit 0, but a stopped count kept later statements of a batch from running; decision 45, above) or `-- failed (exit N): ...`. It is never shortened, not even by `--max-output` (§4.4). Output is cut short only when it couldn't be delivered (exit 7) or sqlh crashed (exit 10, where the line is best effort). Then the exit code is what counts (§4.3, §6).
- **Where the run went:** on a run that connected, the final summary ends with the server, the database the run started in and the connect time, `; <server>/<database>, connect N ms` (owner decision 10, PLAN.md §6): `-- ok: 1 batch, 241 ms; db01/master, connect 195 ms`. It is the first response's answer to "where did this run?", for about 10 to 15 tokens a call. It is on every connected run, not only when `-d` was missing, so the shape of the line doesn't depend on how the run was started.
  - `server` is the server's own name for itself (`@@SERVERNAME`), which need not be the name that was dialled; `?` if it reported none. It never contains `/`, so the database is everything after the first one.
  - `database` is the one in effect when the run starts, which is where the first batch runs: `-d`, else the profile's database, else the login's default (often `master`). A `USE` in the input moves the session on, and the tail does not follow it (as JSON's `connection`, §5.2).
  - `connect N ms` is the time to connect and log in, the same figure as JSON's `connect_ms`. The time before the tail (`241 ms`) is the run's whole time and includes it. **On a connection `sqlh mcp` reused it is `connect 0 ms`** (§10) when the call's session setup worked at its first try and the call wasn't retried (neither the setup nor the call's `USE` found the connection dead): the call made no connect of its own, and its time before the tail is only the call's. **When it didn't** (since `6e7a0d8`), the figure is the time from the call's first attempt, once it had a free connection, to the start of the setup that worked: a reused connection's setup that the 5 s probe cut and that ran again on the same connection (at least 5 s), or a dead connection replaced by a new one (its time and the new login: for one gone silent, the probe, the driver's wait for the attention and the login, about 10 s). So a slow or dead connection shows as connect time, not as an unexplained part of the call's total, which text, `sqlh mcp`'s default, doesn't split by batch for a one-batch call (mcp-mode.md §5, The connect time). A new connection, in `sqlh mcp` as in the CLI, reports its connect and login. The wait for a free connection is in no connect time, nor is a call's `USE` that worked (it runs after the setup, `4519341`); a `USE` that found a reused connection dead is part of the dead connection's time in the retry's figure, which runs from the first attempt.
  - Names are escaped like every variable field (below) and cut after 128 characters with `…[+N]`, as in JSON's `connection`. Never a connection string, a login name or anything from a credential. The auth method and whether the traffic is encrypted are not in the text: they stay in JSON's `connection` and in `--verbose`.
  - Left out when nothing connected (a usage error, a guard refusal, a failed connect, an input with no SQL), so those lines are what they always were, and in the rare case that the cap left no room for it (§4.4). **In `sqlh mcp` it is also left out when a call's session setup or `USE` failed** (the setup, `run::setup`, carries a reused connection's reset; the `USE`, `run::use_database`, follows when the call names a database) and the call wasn't retried: the engine describes a connection only once both have succeeded, so a silent retry never describes the dead connection, and a call whose `database` doesn't exist has no tail either (mcp-mode.md §5). The CLI describes its connection before the setup, so a CLI run whose setup fails keeps the tail.
  - The status before the tail can hold `; ` itself (`...; 3 later batches not run (...)`), but never a `/`. So a program that splits the line takes the first `/` as the end of the server, the last `; ` before it as the start of the tail, and `, connect N ms` at the end as the time.
  - In csv the line is on stderr with the rest of the metadata (§5.3). In JSON, `summary` is the status without the tail, because `connection` and `connect_ms` carry it (§5.2).
- **Diagnostics:** `--verbose` writes `sqlh: <text>` lines to stderr, the one thing text and json put there. They are escaped like a note, counted in `--max-output` and shortened like a note; if stderr is closed they are lost and nothing else changes (§6).
- **Sections** (schema commands, §9 and schema-commands.md §4): each result set of a schema command fills a labeled section, written differently from a query's result set.
  - `-- <label>` (`-- columns`, `-- indexes`, ...) replaces `-- result N`, and the header is the column names only, tab-separated, without types (they would be the catalog query's own). Both come with the section's first row.
  - **A section with no rows writes nothing.** The batch's empty sections are listed on one line after it: `-- no rows: foreign_keys, referenced_by`.
  - **A footer only for what wasn't shown:** a section that showed all its rows has no footer; one with rows hidden or values cut has the usual one (`-- 100 of 4000 rows shown (--max-rows 100)`).
  - **A definition** (`def`) is a block framed by its line count: `-- definition: dbo.usp_Get (SQL_STORED_PROCEDURE), 42 lines`, then exactly 42 lines. A reader skips that many lines, so a line inside that starts with `--` (a T-SQL comment) is never metadata. The name is shown as everywhere in the schema commands (schema-commands.md §5): bracketed when it needs to be. Each line is escaped like a value (a backslash doubled, a control character `\xNN`, U+2028 `\u2028`), except that a tab stays a tab: nothing in a line can break it. A trailing line break doesn't make an empty last line.
    - **When not all of it is shown** (R29), the header still starts with the number of lines that follow, and says what wasn't shown and why: `first 30 lines shown; 12 more lines not shown (--max-output)`. Two things cut a definition, and the header names each that did. The output budget leaves out whole lines that don't fit (`--max-output`), and the body stops there. The read keeps at most `--max-cell N` characters, or, with no cell limit, as many characters as the budget has bytes (§11); what it cut is unknown beyond its length. So a definition cut while read says `first 2 lines shown, the last one cut short; 52 more characters not shown (--max-cell 10)` when every line read is shown (`the last one cut short` when the cut fell inside a line), or `first 30 lines shown; ≥19 more lines not shown (--max-output, --max-cell 4000)` when the budget left out lines too: the lines after the cut are uncounted, so the number is a lower bound.
    - The closing note's `--max-output` count (`these weren't shown: 12 definition lines`, or `≥19 definition lines` after a read cut) appears only when the output budget left out lines. A cut by `--max-cell` alone is not an output limit and stops nothing.

**Order of events**

The output is not in the order of the server's bytes ("wire order"). It is in the order below, which holds for json (§5.2) and csv (§5.3) too. A result set is its `-- result N` line, its header, its rows and its footer, and **nothing else is ever written between them**: no message, no error, no row count. Those come before the result set or after its footer.

- **Where a message lands.** A message (PRINT, RAISERROR at severity 10 or below, a server warning) is written at a statement boundary, not where the server sent it. The driver keeps the messages it reads while it moves through the response, and sqlh writes them in the order they arrived, at each boundary before the next statement's own output, and once more after the last statement. So a message the server sends while a result set's rows are streaming comes after that result set's footer, never between its rows. `PRINT 'a'; SELECT 1; PRINT 'b'` writes `a`, the result set, then `b`.
- **Messages come before the output of the statement they precede.** At a boundary the held messages are written first, then the statement's result set, its row count or its errors. When a result set's rows end in an error, the order is the rows, the footer, the messages held, then the error.
- **Messages and errors.** A statement's errors are reported once the driver has read the statement to its end, so a message the server sent after an error, within that statement, comes before the error. A constraint violation therefore writes `-- msg: The statement has been terminated.` before the `-- error 2627 ...` line it follows on the wire. The driver doesn't say which came first.
- **Nothing was found that sends a message between two rows.** SQL Server 2025 sent every warning a query raised at the end of the statement, after its last row: a NULL dropped by an aggregate (in results of 50,000 rows, and of 1.2 million rows under a parallel plan) and a division by zero with `ANSI_WARNINGS` off. PRINT and RAISERROR can't run inside a query. The rule is for a server or a driver that does. The nearest real case is that warning, which the driver reads between the last row and the end of the statement, and an error that ends the rows; both land after the result.
- **A sink refuses a call out of this order.** A message, an error or a row count that arrives between a result set's header and its footer is answered with an error and writes nothing, in every build: the run ends as an internal error (exit 10, §6) with `-- error: internal error: a message arrived while a result set's rows were streaming...`. That means a bug in sqlh, or a driver that changed, not a problem with the query or the reader. Without the refusal a json document would hold an event among a result's rows, and could be invalid.

**Escaping (values, names, and every variable field in metadata lines)**

- Backslash, tab, newline and CR are written as `\\`, `\t`, `\n` and `\r`.
- Every other control character becomes `\xNN`, with exactly two uppercase hex digits: the C0 controls and DEL (U+0000–U+001F, U+007F) and the C1 controls (U+0080–U+009F). U+0085 is one of Unicode's line breaks, and U+009B is a control sequence introducer on some 8-bit terminals.
- U+2028 and U+2029, the other two Unicode line breaks, become `\u2028` and `\u2029`: `\u` and exactly four hex digits.
- A backslash before any other character means that character. A reader decodes `\xNN` and `\uNNNN` to the character they name, so a literal backslash is always doubled (`\\x3A` is a backslash followed by `x3A`, while `\x3A` is a colon).
- Other Unicode text (accents, no-break space, CJK) is written as it is.
- The same escaping applies to type names in headers, and to every variable field of a metadata line: column and type names, procedure names, source names in locations, guard reasons and advice, notes and error text, and the server and database names at the end of the status line. Nothing a database or an input contains can start a new line or pass for a `-- ` line, whether the consumer splits at `\n` only or at every Unicode line break (Python's `splitlines`, for instance). This is for text, and the metadata lines of csv. A csv data row follows csv's own quoting, and a json string keeps these characters as JSON allows (§5.2, §5.3).
- **Paths in `-- ` lines follow the rule** (owner decision 11, PLAN.md §6). A path there is a variable field like any other: a source name in a location (`-- batch 2 (sub\\b.sql:14)`, `-- blocked: sub\\b.sql:2: ...`, `-- error 208 (severity 16, state 1, sub\\b.sql:12): ...`), or a path in a note or a closing error (`-- error: -i C:\\dir\\f.sql: ...`). Each backslash is written `\\`, and a reader decodes the field like any other: `C:\\dir\\f.sql` is `C:\dir\f.sql`. Neither alternative was taken: rewriting backslashes as forward slashes changes what was typed, and some cmd.exe built-ins refuse forward slashes; escaping a backslash only before an escape letter changes the reader's rule, and `C:\new` would still be doubled. **One exception, the profile commands** (owner decision 38, 2026-10-26, from manual testing): `sqlh profiles add|list|test|rm` write the profiles file's path in their notes as typed, backslashes single (`-- note: profiles file: C:\Users\me\AppData\Roaming\sqlh\profiles.toml`; `output::path_as_typed`), since they are setup a person runs and nothing decodes the path; a control character or line break in it is still escaped. In json and csv those notes are written as any note.
- **Input is never escaped.** The escape rule is for what sqlh writes. What it reads is taken exactly as typed: the paths after `-i` and `-o`, `SQLH_CONFIG`, SQL text and `-v` values. A path from Explorer's "Copy as path", double-quoted, with single backslashes and spaces, works as it is after `-i` or `-o` in cmd.exe, PowerShell and Git Bash (`C:\my dir\f.sql` in quotes; the test `a_path_from_copy_as_path_works_after_i_and_o_in_every_shell` runs it through cmd.exe, Windows PowerShell 5.1 and PowerShell 7). Only Git Bash eats an unquoted backslash, which is the shell's rule, not sqlh's (§4.1). A path copied back from a `-- ` line still has its backslashes doubled: a local path survives that (Windows folds `\\` into `\`), a UNC path (`\\\\server\\share` for `\\server\share`) does not, so decode the field first.
- Bare `NULL` means SQL NULL. A string whose entire value is `NULL` is written as `\NULL`.
- A first-column value, or a first column name in a header, starting with `--` gets a leading backslash (`\--...`), so data and header lines never look like metadata.
- An empty string is an empty field.

**Value rendering**

| Type | Rendering |
|---|---|
| char, varchar, nchar, nvarchar, text, ntext, xml, json | The text, escaped as above. |
| tinyint, smallint, int, bigint | Decimal. |
| bit | `0` or `1`. |
| decimal, numeric, money, smallmoney | Exact decimal string with scale kept (`12.50`). Never goes through a float. |
| float, real | Shortest form that round-trips. |
| date, time, datetime, datetime2, smalldatetime | ISO 8601. Fractional digits match the type: datetime has 3, `datetime2(n)` has n. |
| datetimeoffset | ISO 8601 with offset, e.g. `2024-01-05T09:12:00.0000000+01:00`. |
| uniqueidentifier | Uppercase canonical form, same as SSMS. |
| binary, varbinary, image, rowversion | `0x` followed by uppercase hex. |
| sql_variant | The value of its base type. |
| vector (2025) | JSON array text, the form down-level clients receive: `[0.1,2,-3.5]`. sqlh asks for vector feature version 2 (owner decision 71, mssql-tds 0.4.0's default, set explicitly). A float32 element is written as `real` is. A float16 element (SQL Server 2025's half-precision vectors, `vector(n, float16)`, a preview feature) arrives natively only when the server acknowledges version 2, and is then written in the shortest form that reads back as the same float16, so `0.1` stays `0.1` rather than its widened `0.099975586`, and a whole number whole (`65504`); the header's type is `vector` for both. A server that sends float16 down-level gets it shown as the server wrote it, under the type the server gives it. SQL Server 2025 build 17.0.1155 did so to sqlh, which asks for version 2 (mssql-tds 0.4.0, `PREVIEW_FEATURES` on, 2026-11-14; which version the server acknowledged, and why, isn't visible outside the driver): `vector(4, float16)` holding `[0.1,2,-3.5,65504]` comes as `v:varchar(max)` with `[9.9975586e-002,2.0000000e+000,-3.5000000e+000,6.5504000e+004]`, while float32 vectors arrive natively. The native float16 form above is for a server that sends it (driver-0.4.0.md §10). |
| geography, geometry, hierarchyid, CLR UDTs | `0x` hex. The help text suggests `.ToString()` or `.STAsText()` in the query. |

### 5.2 json

`--format json` writes one JSON document. It is streamed, so memory stays flat. The head (the contract version, and once sqlh has connected, the connection and how long that took) comes first because it is known before anything runs, and the outcome fields come last because they are only known at the end.

```json
{"contract_version":"2.1",
 "connection":{"server":"SQL01","database":"AppDb","auth":"sql","encrypted":true,"server_version":"17.0.1000"},
 "connect_ms":31,
 "batches":[
  {"batch":1,"source":"-Q","line":1,"events":[
    {"type":"msg","text":"starting"},
    {"type":"result",
     "columns":[{"name":"id","type":"int","nullable":false},{"name":"total","type":"decimal(18,2)","nullable":true}],
     "rows":[[1,"12.50"],[2,null]],
     "row_count":48213,"row_count_exact":true,"truncated":true,"cells_cut":0},
    {"type":"rows_affected","count":5},
    {"type":"error","number":208,"severity":16,"state":1,"line":14,"text":"Invalid object name 'dbo.Nope'."}],
   "elapsed_ms":12,"counting_stopped":false}],
 "notes":["ignored sqlcmd flags -W (sqlh output is always compact)"],
 "error":"query timeout after 60 s in batch 2; ...",
 "ok":false,"exit_code":1,"summary":"failed (exit 1): 1 error, first in batch 1, 48 ms","elapsed_ms":48}
```

**Contract version**
- `contract_version` is the document's first field: `major.minor`, `"2.1"` here. `sqlh --version` reports it too, as `sqlh 0.1.0 (json contract 2.1)`, so a tool can see what to expect before it runs anything. Text and csv carry no version, because it would cost tokens on every call.
- The major version changes only for an incompatible change: a field or an event type removed or renamed, or its type or meaning changed. A minor version may add optional fields, event types and enum values (the `type` of an event, the `auth` words). So a reader written for N.x ignores fields and event types it doesn't know, and doesn't treat the values of an enumeration as a closed list.
- **A reader must check the major version first and reject a document whose major it doesn't support**, without reading further: it stops, or tells its user that the contract is newer than it handles. A reader that skips this check can misread a document whose meaning changed (the history below is the example). The minor version is never a reason to reject.
- **Version history.**
  - 1.0: `contract_version`, `connection` and `connect_ms` in the head, and `elapsed_ms` on every batch.
  - 1.1: added `row_count_exact` to every result and `counting_stopped` to every batch (the bounded count of hidden rows, §4.4). It was built during development and never released as a stable contract.
  - 2.1, the document described here: 2.0 with `label` on the result events of a schema command (below), an optional field a 2.0 reader ignores. Nothing else changed.
  - 2.0: the same fields and shapes as 1.1, under a new major version because a result's `row_count` can now be a lower bound (when `row_count_exact` is `false`, §4.4). A reader following the 1.0 rules ignores `row_count_exact` and `counting_stopped`, sees `ok: true` and no `interrupted`, and would take the bound for the exact total, and take a batch whose later statements were cancelled for one that completed. Adding a qualifier that an old reader may ignore does not keep the old meaning, so the major version changed: that reader sees `"2.0"`, fails its major check and rejects the document, rather than misreading it (a unit test in `output/json.rs` applies this check to a stopped-count document). In 2.0 `row_count` is the exact total only when `row_count_exact` is `true`, and a reader tests that field before it uses the count.

**Connection**
- `connection` and `connect_ms` follow the version once sqlh has connected. They are written as soon as the login is done, before the first batch, from facts the login already gave, so they cost no round trip. When nothing connected (a usage error, a guard refusal, a failed connect, an input with no SQL) both are left out, and so they are for a `sqlh mcp` call whose session setup or `USE` failed (the rule of §5.1's "Where the run went": in `sqlh mcp` they are written once the session setup, carrying a reused connection's reset, and, when the call names a database, its `USE` have succeeded).
- `connection` has five fields:
  - `server`: the server's own name for itself (`@@SERVERNAME`), which need not be the name that was dialled; `null` if it reported none.
  - `database`: the database in effect when the run starts, which is where the first batch runs: `-d`, else the profile's database, else the login's default (often `master`). A `USE` in the input moves the session on, and this field does not follow it. (The driver does track a `USE`, because it applies the server's environment-change token, so `Session::connection` would return the new database if it were read later. The head is written before the first batch, so it states where the run began.)
  - `auth`: `"windows"` or `"sql"`. Never the login name.
  - `encrypted`: whether the traffic after the login is encrypted.
  - `server_version`: `major.minor.build`; `null` if the server reported none.
- Never a connection string, and nothing from a credential. The names that come from the server are escaped like every string and cut after 128 characters with `…[+N]`. SQL Server's own names stop at 128, so the cut changes nothing real, and it bounds the object (under 2,000 bytes whatever the server sends), which is what keeps it inside the smallest `--max-output`.
- `connect_ms` is the time to connect and log in, in milliseconds: the connect time `--verbose` reports. It tells a slow connect from a slow batch. On a connection `sqlh mcp` reused it is `0` (§10) when the call's setup worked at its first try and the call wasn't retried: that call made no connect. After a probe that cut the setup, or a retry on a new connection, it is the time from the call's first attempt to the start of the setup that worked, the same figure as the status line's (§5.1, Where the run went; `6e7a0d8`).

**Batches and events**
- Each batch carries `batch`, `source` (a file name, `-Q` or `stdin`), `line` (where it starts), and `run`/`runs` when repeated by `GO n`.
- Its `events` array is in the order of §5.1's "Order of events", which is not the wire order: a message lands at a statement boundary, between results, and never among a result's `rows`. A message the server sends while a result's rows are streaming is an event after that result.
- After its events, each batch carries `elapsed_ms`: how long it took, from when sqlh sent it until its last result was read (waits for a slow reader included). A batch cut short by a timeout, a cancel or a lost connection lasts until the run ends.
- Then `counting_stopped`: `true` when the count of hidden rows was stopped in this batch (§4.4), which also means the rest of the batch was cancelled, so any later statements did not run; put each query in its own batch (GO) to keep them; `false` otherwise. On every batch, so a reader tests one field. Since decision 45 text tells a batch whose later statements a stop cancelled from one with nothing after its capped result (`-- partial:`, §5.1). JSON keeps contract 2.1 and doesn't: `counting_stopped` keeps its 2.0 meaning, which is the safe reading of either, and `summary` carries the text status line, `partial: ...` included.
- **result:**
  - `rows` holds only the shown rows (`--max-rows`), and `row_count` counts all of them.
  - `row_count_exact` is `true` when `row_count` is the exact total, and `false` when it is not. That is so when the count was stopped: `row_count` is then a lower bound floored to one significant digit, and at least one more than the rows shown once a hidden row was counted (the text format's `≥`). And it is so in a result that a failure cut short (`"interrupted":true`), which holds only the rows that arrived: its `row_count` is not the total whether or not a count was stopped. A failure here is a SQL error that ended the result's rows (the `divide by zero` on the third row of a query: the result holds the two rows that arrived, `"interrupted":true`, then the held messages and the `error` event) or a run that died mid-result. Only that result is incomplete: one that ended on its own before the error, a later result in the same batch (a statement-terminating error leaves the batch running) and the results of later batches under `--continue-on-error` are exact. On every result.
  - `truncated` means rows were hidden: a row past the shown ones was counted, so it is true whenever `row_count` is above the number of rows in `rows`. In a stopped count it is `false` only when `-t` ended the wait for the first hidden row, so none was counted; `row_count` is then the rows shown and `row_count_exact` is `false`, which is how a reader knows that more rows may exist.
  - `cells_cut` counts values cut by `--max-cell` (they end in `…[+N]`).
  - Result sets hidden by `--max-results` emit no event; a note counts them.
  - `label` (2.1): on a schema command's results only, after `type`, the section the result fills (`"object"`, `"columns"`, ...; §5.1 "Sections"). A section with no rows is kept, with `"rows":[]`, so the document's shape doesn't depend on the data. A definition is an ordinary value: the read cuts it like any value, at `--max-cell N`, or, with no cell limit, at the output budget (§11), and the value then ends in the usual `…[+N]`; and a row that doesn't fit `--max-output` is withheld whole, as any row. Names in the values are shown as in text (schema-commands.md §5). The batch's `source` is the command's name (`"describe"`), and `line` is 1.
- **rows_affected:** `count` is the number of rows. A run of consecutive statements is one event, which then also carries `statements`: `{"type":"rows_affected","count":300,"statements":300}`.
- **error:**
  - `line` is mapped to the input, as in the text format. `source` is added when there are several inputs.
  - Inside a procedure, the event has `procedure`, and `line` is the procedure's own line.

**Values**
- Integers within ±2^53 are numbers; larger ones are strings, so nothing loses precision. bit is `0`/`1`.
- Floats are numbers in shortest round-trip form.
- decimal, numeric, money, dates and GUIDs are strings in exactly the text format's rendering.
- Binary is a `"0x..."` string. NULL is `null`.

**Outcome**
- `notes` (when present), `error` (when the run stopped early, including a guard block), `ok`, `exit_code`, `summary` (the text format's status line) and `elapsed_ms`.
- Failures before any batch, such as a bad profile or a refused connection, still produce a well-formed document with `"batches":[]`. It has the `contract_version`; it has no `connection` or `connect_ms` when nothing connected.
- A run that dies mid-result, or a SQL error that ends a result's rows, closes the open result with `"interrupted":true` (and `"row_count_exact":false`, above).
- **Within `--max-output` (§4.4)** the whole document is: valid, no longer than the cap, and with `ok`, `exit_code`, `summary` and `elapsed_ms` intact. What gives way is text. A note is shortened when it is recorded, and a note that can't fit even as a marker is left out and counted (`"...these weren't shown: 1 note"`). `error` is shortened when the document ends, in its variable parts if it is a guard refusal; a cut string ends in `…[+N]`, N the characters left out. The closers of the open result and batch (`],"row_count":...,"row_count_exact":...}],"elapsed_ms":N,"counting_stopped":...}`) and the outcome fields are never cut: the reserves in §4.4 leave room for them, with every number at its widest. `--verbose` lines are not in the document; they go to stderr, counted in the same cap.
- The head with the `connection` is the first piece of the body and is admitted like one, so it counts against the cap and can't push the ending out of it. If notes and `--verbose` lines have already used up the room (only with a cap near the minimum), it is left out, and the closing note counts it among what wasn't shown (`1 connection description`).

### 5.3 csv and md

- **csv:**
  - RFC 4180 fields with LF line endings: a header row of column names, the rows, then a blank line before the next result set.
  - NULL is an empty unquoted field, and an empty string is `""`.
  - A field is quoted when it contains a comma, quote or line break, or starts or ends with whitespace.
  - The data stream (stdout, or `-o`) holds only CSV. Everything else goes to stderr as text-format `-- ` lines: `-- result N: name:type, ...` with the column types, row counts and truncation, messages, errors, notes, and the status line. `--verbose` adds `sqlh: <text>` lines to the same stream.
  - The status line on stderr is the text format's, and on a run that connected it ends the same way, with the server, the database the run started in and the connect time: `-- ok: 1 batch, 241 ms; db01/master, connect 195 ms` (§5.1). The data stream carries none of it, so a file written with `-o` holds data only.
  - `--max-output` (§4.4) counts both streams together. Notes, a guard refusal and the closing error are shortened with `…[+N]` as in the text format, and the status line is the last line of stderr, whole, tail included.
  - Limits apply as everywhere; for a full export pass `--max-rows 0 --max-cell 0`. A stopped count (§4.4) is on stderr: the footer `-- 100 of ≥800000 rows shown (--max-rows 100; counting stopped)`, the note, and `counting stopped in N` in the status line (§5.1).
  - A result a SQL error ended has the incomplete footer on stderr (`-- 2 rows so far (interrupted)`, §5.1); the data stream holds the rows that arrived, with nothing to tell it apart, so a reader of csv checks stderr or the exit code (1).
  - Known ambiguity: a one-column row holding NULL is an empty line, the same as the separator between result sets.
  - A schema command's section (§5.1 "Sections") writes its header row and a `-- <label>: name, name` marker on stderr with its first row, no types; a section with no rows writes nothing and is listed on stderr's `-- no rows:` line. A definition is one quoted field, cut like any value.
- **md (not built yet):** unpadded GitHub tables. `|` is written as `\|` and newlines as `<br>`. Messages are plain lines.

Usage errors found while parsing the arguments happen before `--format` is known, so they always use the text format.

## 6. Exit codes and streams

| Code | Meaning |
|---|---|
| 0 | Success: the status line is `-- ok:`, or `-- partial:` when a stopped count kept later statements of a batch from running (§5.1, decision 45); JSON's `ok` is `true` for both, and its `summary` says which. `sqlh mcp` exits 0 whenever it ends after serving, whatever ended it: stdin closed, stdout broken or stalled (its stall rule, R35), or a console event (mcp-mode.md §2, The end); a call's own exit code goes in its result. |
| 1 | One or more SQL errors were reported. A lock timeout (error 1222) and a lost deadlock (error 1205) are SQL errors like any other (§4.3). |
| 2 | Couldn't connect, or login failed. |
| 3 | Usage or config error: bad flag, missing profile, unknown `$(var)`, `-P`, `--read-uncommitted` in a run that can write. In `sqlh mcp`, also a tool call whose arguments the tool can't take, SQL over 1 MB, and a call past the 64 running, each the run's usage error in the call's format (mcp-mode.md §2, §4). |
| 4 | Timeout (login or query: `-l`, `-t`; `-t` also bounds the session setup, whose timeout says `in the session setup`, §4.3). `-t` is the elapsed time of a batch, kept by sqlh (§4.4), within the grace the driver takes to settle the cancel (tens of milliseconds), which sqlh cuts off at 5 s by closing the connection. A batch that the driver finished after `-t` is a timeout too, apart from the hidden-row exception below. Not a lock timeout, which is exit 1. Not `-t` expiring while a read-only run only counts rows it doesn't show: the rows shown are complete, and the run ends with its own exit code and `≥N` (§4.4). That exception does not reach a run that can write (a stop would skip a `COMMIT`), one whose input mentions `XACT_ABORT` (the stop would roll the read-only transaction back), or a wait for rows that would be shown (`--max-rows 0`, or fewer rows than `--max-rows`): there `-t` is exit 4, as it always was. |
| 5 | Blocked by the read-only guard, including input too complex for its check to classify in bounded work (§7). Nothing was executed. |
| 6 | Cancelled: Ctrl+C, Ctrl+Break, the console closing, logoff or shutdown (§4.3). Also when one arrives while a stopped count is being cancelled (§4.4): the user's cancel wins, the run is cancelled and is not reported as a stopped count. Also when the server does not acknowledge sqlh's own stop of a count within the driver's 5 s: nobody cancelled anything, the connection is closed, and the error says which it was, `-- error: stopped counting the rows that are not shown, but the server didn't confirm the cancel, so the connection was closed; the rows shown are complete (--exact-count reads every row instead)`. The result the stop cut gets no footer, and the status line no `counting stopped in N` (`-- failed (exit 6): cancelled, N ms`; pinned by the engine test `in_mcp_an_unconfirmed_count_stop_names_the_profiles_exact_count`, on the run core the CLI shares). In `sqlh mcp` the text is the same up to the parentheses, which name what its client can change: `(the profile's exact_count = true reads every row instead)` (mcp-mode.md §4). |
| 7 | Output could not be delivered (see below). |
| 10 | Internal error (a bug), including any panic. Details go to stderr, best effort (§4.3). In `sqlh mcp`, also a startup failure (its async runtime, stdin reader or stdout writer can't be started), one line on stderr (mcp-mode.md §3). A CLI run whose console-event listeners can't be installed ends here too (`cannot watch for Ctrl+C and other console events: E`), since it can't run without being able to cancel; `sqlh mcp` serves without them instead, under Windows' default handling of a console event, and says so only with `--verbose` (`sqlh mcp: console events can't be watched (E); Ctrl+C ends the process at once`; mcp-mode.md §3, as built). Also a sink's refusal of an event that came out of order (§5.1, "Order of events"): the run stops there, and the status line and `-- error:` say so as for any other failure. |

**Exit 7, undeliverable output.** sqlh couldn't hand its complete output, including the final status line, to its destination. That happens when:
- the program reading stdout closed it early (a broken pipe), for example a harness that stopped reading. This covers `--help` and `--version` too;
- the reader kept stdout open but read none of the waiting output for `-t` seconds (a stall; time with nothing to write doesn't count). Progress is measured per write of at most 4 KB: every write the reader takes restarts the clock, so a slow reader that keeps reading is not a stall, as long as it takes each 4 KB within `-t` seconds. In csv mode a single thread writes stdout and stderr in order, so a stalled reader of either stream stalls the whole output. A thread writes the output, so a stalled reader can't block timers or Ctrl+C: the batch waits for room in a bounded queue, then gives up. The stall limit counts from the writer's last progress, while the batch's own deadline (§4.4) counts from the batch's start, so a reader that stalls in the middle of a batch ends the batch at `-t` with exit 4, and the closing lines then wait a full stall limit: about twice `-t` in all, exit 7, with stderr naming exit 4 as the run's own code;
- a console event (Ctrl+C, Ctrl+Break, a close) arrived while the closing lines waited for the reader, and the rest wasn't delivered in the 1 s that follows (§4.3);
- in csv mode, stderr was closed: it carries the metadata and the status (§5.3);
- writing or flushing `-o file` failed, for example a full disk or lost permissions;
- the finished `.partial` file couldn't be renamed over `file`.

The SQL may have run, so exit 7 says nothing about the database: it means "don't trust what you received", and it is no reason to retry a write before checking what happened. It takes precedence over the run's own exit code. When that code is known, stderr gives it, as in `sqlh: output could not be delivered (...); the run itself ended with exit 1: ...`. When the failure stopped the run partway, stderr says that the outcome is unknown: the batch being written may have run, and later batches did not. With `-o`, an undelivered run leaves the existing file untouched, and its `.partial` file is deleted.

Diagnostics on stderr are best effort and bounded: one that can't be delivered never changes the exit code or holds up the response (csv mode aside, above). There are two kinds.
- **`--verbose` lines**, in text and json, are written by a thread of their own; the thread that writes stdout never touches stderr. So a stderr that is open but never read blocks only that thread, and the response on stdout is delivered as usual, even with `-t 0`. At the end sqlh waits at most 0.5 s for the lines, then drops what is left. They still count against `--max-output` (§4.4). In csv mode stderr is the metadata stream, and they are delivered with it.
- **The last-resort messages**, when delivery fails (exit 7) or sqlh crashes (exit 10). Taking the stderr lock and the write itself can each block for good when the reader has stopped reading (in csv mode the output thread may be holding the lock itself, §5.3), so a helper thread writes each message and sqlh waits for it at most 0.5 s. If stderr is closed the message is dropped at once. If it is open but unread, the message is abandoned after 0.5 s, and stderr isn't tried again, so all of a run's last-resort messages together cost at most that. The panic hook's stderr line and its stdout status line (§4.3) follow the same rule, together within the same 0.5 s.

Text in a diagnostic that comes from elsewhere, such as the run's own error message or a path, is cut after 1,000 characters with a `…[+N]` marker and escaped like metadata, so a file name holding U+2028 or U+2029 shows them as `\u2028` and `\u2029`, and a backslash is doubled.

In the text, json and md formats, everything goes to stdout in order: results, messages, SQL errors, connection and usage errors, and the summary. That gives agents one stream to read. stderr carries only `--verbose` diagnostics, delivery failures (exit 7) and internal errors (exit 10), except in csv mode (§5.3). The order is the one in §5.1, "Order of events". `--help` and `--version` print to stdout, with no status line. `--version` prints the program's version and the version of the JSON contract (§5.2): `sqlh 0.1.0 (json contract 2.1)`.

Connection errors must be actionable. They name the server, port, auth method and encryption mode, give the underlying error, and add a hint where one applies, such as:
- a named instance with SQL Browser unreachable: try `host,port`
- an untrusted certificate: pass `-C` or fix the cert
- a TLS version mismatch with an old server
- Schannel's credentials failing on this machine (`AcquireCredentialsHandleW(UNISP_NAME)` in the error), after TCP and, below strict, the prelogin, but before the login is sent, as on Windows Server 2016 (upstream-issues.md U12): `this machine couldn't set up TLS, so the login was never sent: the driver's TLS needs Windows 10 1809 or Windows Server 2019 or later (on a later Windows, check that this machine's Schannel settings allow TLS 1.2)`, the same in `sqlh mcp`, in every encryption mode; it names no `-C` or `-No`, which can't help, and takes the place of the strict hint (2026-11-09; its wording R62's)
- any certificate failure under strict encryption, which checks the certificate even with `-C` (R46): `strict encryption checks the server's certificate even with -C, and needs SQL Server 2022 or later: connect by the name on the certificate, from a machine that trusts its issuer, or use -Nm, where -C applies` (in `sqlh mcp`: `... even with trust_server_certificate = true ... or set encrypt = "mandatory" in the profile, where trust applies`)

In `sqlh mcp`, which connects only through profiles, a hint names the profile's key instead of a flag (`db::Hints::Profile`, set at launch): `set trust_server_certificate = true in the profile` for `-C`, `encrypt = "optional"` for `-No`, `raise the profile's login_timeout` for `-l`, `use a profile with a SQL login` for `-U`, `check the profile's database` for `check -d` (the connection logs in to the profile's database; a call's `database` is a `USE` after the login, whose failure is a SQL error, never this login error), and `the profile's login and its saved password (sqlh profiles add)` for `SQLCMDPASSWORD`. mcp-mode.md §4 lists each hint in both forms.

## 7. Read-only guard

Read-only is the default. Each profile sets a write policy:

| Policy | Behavior |
|---|---|
| `deny` | The profile can never write, and `--allow-write` is rejected. |
| `flag` | `--allow-write` turns on writes for that run. The policy of a profile saved without `write_policy`, and of runs without a profile. |
| `allow` | Writes are on by default. |

Database permissions are expected to provide the enforcement boundary. The tool's checks are also important when a DBA or developer has accidentally granted an agent excessive access. An agent can pass `--allow-write` itself, so `flag` is an accident guard; `deny` is the strongest tool policy, but does not replace restricted database permissions.

**New profiles refuse writes** (owner decision 12, 2026-10-12): `sqlh profiles add` saves `write_policy = "deny"` for a profile it creates, unless `--write-policy` is given, and says so in a note with the command that changes it. In agent trial 2 a model asked to clean up a table added `--allow-write` on its own and ran a 927,269-row `DELETE`; only the profile's `deny` stopped it. Writing therefore takes an explicit change to the profile's policy (`sqlh profiles add NAME --write-policy flag`), not a flag on one run. That change is not reserved for a person: `profiles add` reads from the console only when it needs a SQL login's password, so for a Windows-auth profile, or a SQL-auth profile whose password is stored and whose server and login stay the same, it runs unattended, and an agent that can run `profiles add` can change the policy itself (review finding R19). So `deny` refuses `--allow-write` for as long as the profile keeps that policy; it is a guard against an agent reaching for the flag, not a control over who may write. The login's database permissions remain the boundary (above). Human-only profile management would be a separate design, with tests for stored passwords and Windows auth, before sqlh claims it. Updating an existing profile keeps its policy, and a profile in the file without `write_policy` (saved before this change) is still `flag`.

Command categorization and the balance of allowlists/blocklists need further design using legitimate DBA workflows and their risks. The current classifier below is the MVP mechanism, not the final categorization system. See [VISION.md](VISION.md). The design is [command-categories.md](command-categories.md); its decisions are PLAN.md §6, decisions 22–36 (2026-10-23): kinds of change granted separately, per profile and per run, with `--allow-write` kept as the blanket switch; a deny tier refused in every mode; a wider read list, lock-holding SQL and agent-chosen paths refused in read-only runs; a client-side `:pause`; sqlh's own `activity` and `errorlog`; `sqlh mcp` stays read-only. Of it, only the interim step above, decision 23's refusal wording as it stands before the kinds (below) and decision 30's (a) (§4.3), (b) (the note below), (c) (§4.3), (d) and (e) (below) are built.

In read-only mode, three layers apply:

1. **Classifier** (`src/guard.rs`). It runs on the whole input before anything executes. It has its own T-SQL tokenizer that understands comments (including nested ones), `'..'`, `N'..'`, `[..]` and `".."`.

   **Tokens end where the servers end them,** or a keyword hides from every check. Found by review, 2026-11-01, when each of these reached the server, `COMMIT` of the wrapper among them. The sets come from parsing every code point of the BMP in several shapes (`SELECT 1<c>AS x`, `SELECT <c>1 AS x`, `SELECT 1 <c>DELETE #t`, ...) with `sys.dm_exec_describe_first_result_set`, which parses and runs nothing; SQL Server 2016 SP3 and 2025 gave the same sets, and the supplementary planes (2025) add none. `live::the_servers_read_the_guards_characters_as_it_does` holds them, and `guard::tests` hold the exact lists.
   - **A `--` comment** ends at LF or at a lone CR, and at nothing else (not U+2028, U+2029 or U+0085). A lone CR starts no new line in the servers' numbering, so a line number counts LF only. `script::split` reads a comment the same way, and a CR-only file stays one line to it, so `GO` isn't found there; the server then reads `GO` as an alias, and the guard reads all of it. It ends names, numbers and `money` literals where the guard does (`guard::plain_token_end`, held to the lexer by `plain_tokens_end_where_the_lexer_ends_them`), so a `GO` in a string or quoted name after `1e--` or `$--` stays in it. It reads the text before `$(var)` substitution (§4.3), so it can't see a literal a value makes: `SELECT $(v)-- 1 AS [a<LF>GO<LF>b]` with `v=1e` is two batches, which fails closed, since the guard and the server each read what they are given. On a terminator's own line too: `GO --c<CR>SELECT 2` is no terminator, since what follows the CR is a statement that would otherwise be lost, so the line goes to the server, whose error 102 says the `GO` is in the way.
   - **Whitespace** is every byte from U+0000 to U+0020 (VT and NUL too), and beyond ASCII U+0085, U+00A0, U+1680, U+2000 to U+200B, U+2028, U+2029, U+202F, U+205F and U+3000. A no-break space pasted into SQL no longer hides the next word.
   - **A number** stops at the first byte that can't continue it, so `1DELETE`, `1.DELETE`, `1e5DELETE`, `1e+5DELETE`, `.5DELETE`, `1eDELETE` and `0xINSERT` are a number and a keyword. An `E` is an exponent's: `1EXEC` is `1E` and an alias `XEC`, the servers' syntax error if a name follows, and `0xDELETE` is `0xDE` and an alias `LETE`. A binary literal goes on past a backslash at a line's end (LF or CRLF, with nothing between; only there, and in no other number), so `0xAA\<LF>AWAITFOR ...` is `0x0AAA` and a statement on the next line, which both servers ran. A backslash and a lone CR are the literal's too, and end it: `0xAB\<CR> AS x` is `0xAB`, and in `0xAB\<CR>CD` the `CD` is the next token. An exponent's sign is the number's with or without a digit after it: `1e--1 DELETE ...` is `1e-`, `-1` and a `DELETE`, no comment, while `1e---1` and `1e+--1` are a number and a comment.
   - **A `money` literal** is a currency sign, then spaces (U+0020 only), a `+` or `-`, and a number with no exponent: `$1DELETE`, `$ -1.5EXEC`, `£1EXEC`, `\1EXEC`. The signs are `$`, `\`, U+00A2 to U+00A5, U+09F2, U+09F3, U+0E3F, U+17DB, U+20A0 to U+20B1, U+FDFC, U+FE69, U+FF04, U+FFE0, U+FFE1, U+FFE5 and U+FFE6. With no number and no `+` or `-` the sign is the literal, so `£DELETE` and `$ DELETE` are it and a keyword. A `+` or `-` is the literal's with no number after it, as an exponent's is: `$--1` and `$ --1 DELETE ...` are `$-`, `-1` and a `DELETE`, no comment, while `$---1` and `$+--1` are a literal and a comment. `$` followed by a name's character is a name (`$action`; `$DELETE` is the servers' error 126).
   - **Everything else beyond ASCII** goes on in a name. Where the servers don't take it in a name, a syntax error stops the whole batch, so calling it part of the word hides nothing that would run.

   **Reserved words are exact, and the words the servers don't reserve go by a collation's comparison.** `SET NOEXEC<U+0218> OFF` switched a `--check` run off for real on both servers, `DISABLE<U+0218> TRIGGER` and `RECEIVE<U+0218>` reached their statements, and `NEXT<U+0218> VALUE FOR` was still a sequence's. Each of these measurements is on SQL Server 2016 SP3 and 2025 under `SQL_Latin1_General_CP1_CI_AS`, by parsing with `sys.dm_exec_describe_first_result_set`, which runs nothing; both gave the same sets. A database of another collation reads keywords the same, as measured ("Near, not whole", below):
   - **Which is which.** With U+0218, U+200D or U+0301 in the word, every reserved word the guard reads is the servers' syntax error, so it stays a name: `BACKUP`, `BEGIN`, `BULK`, `CHECKPOINT`, `COMMIT`, `CREATE`, `DBCC`, `DELETE`, `DENY`, `DROP`, `END`, `EXEC`, `EXECUTE`, `FROM`, `GRANT`, `INSERT`, `INTO`, `JOIN`, `KILL`, `OPEN`, `RECONFIGURE`, `RESTORE`, `REVOKE`, `ROLLBACK`, `SAVE`, `SET`, `SETUSER`, `SHUTDOWN`, `TRUNCATE`, `UPDATE`, `UPDATETEXT`, `WAITFOR`, `WRITETEXT`, `TRAN`, `TRANSACTION`, `DISTRIBUTED`, `DISTINCT`, `READ`, `KEY`, `IDENTITY_INSERT`, `STATISTICS`, `TO`, `ADD`, `ALTER`. The servers read these by the comparison: `CONVERSATION`, `DIALOG`, `DISABLE`, `ENABLE`, `GET`, `MERGE`, `MOVE`, `NEXT`, `VALUE`, `RECEIVE`, `SEND`, `USING`, `NOEXEC`, `AUTOPILOT`, `XACT_ABORT`, `SHOWPLAN_ALL`, `SHOWPLAN_TEXT`, `SHOWPLAN_XML`, `SYMMETRIC`, `MASTER`, `ISOLATION`, `LEVEL`, `UNCOMMITTED`, `NOLOCK`, `READUNCOMMITTED`, the table hints after `NOLOCK` (`FORCESEEK<joiner>` and `KE<mark>PIDENTITY` parse; `ROWLOCK<joiner>` is read as the hint, error 1047, conflicting), and `ADD`'s `SIGNATURE`, `COUNTER`, `SENSITIVITY` and `CLASSIFICATION`.
   - **What the comparison does (`guard::spells`, `guard::keyword`, for the words of the second list that a rule goes by).** It skips 10,700 BMP code points in a word, in 173 ranges (`src/guard_ignored.rs`): exactly what `N'NOE' + NCHAR(i) + N'XEC' = N'NOEXEC'` ignores under this collation (19,181 without the surrogates), among the 46,543 a word can hold at all. They run from U+0218 and the joiners to whole scripts it has no weight for, such as Ethiopic, Cherokee and CJK Extension A. Eight small capitals stand for a letter (U+0262 G, U+026A I, U+0274 N, U+0280 R, U+028F Y, U+0299 B, U+029C H, U+029F L). Ligatures stand for two (`Æ` AE, `Þ` TH, `ß` SS, `Ĳ` IJ, `Œ` OE, `Ǉ` LJ, `Ǌ` NJ, `Ǳ` DZ, with their other cases, and U+FB00 FF, U+FB01 FI, U+FB02 FL, U+FB06 ST), 22 code points: that list is from the collation's `=`, over every pair of letters, and `SET N<U+0153>XEC OFF`, `OPEN MA<U+FB06>ER KEY` and `CLA<U+00DF>IFICATION` parse as the words. The comparison isn't that `=`, though, which also takes a full-width letter and U+207F for N: in `SET` and `OPEN` those are errors 195 and 156. A supplementary character in a word is error 102. Sqlh also skips U+0B3C, U+0B3D, U+0DCA, U+0ECC and U+200C, which `Latin1_General_100_CI_AS` ignores and this one doesn't: unmeasured in a parser, and free to refuse.
   - **Eight repeat marks stand for the letter before them (`guard::is_repeat_mark`):** U+0651, U+3031, U+309D, U+30FC, U+30FD, U+FE7C, U+FE7D and U+FF70. Past what is ignored on either side (`SYM<joiner><mark>ETRIC`, `SYM<mark><U+0218>ETRIC`) and after a small capital (`SHOWPLAN_A<U+029F><mark>`). Not first in a word (`<mark>NOEXEC` and `<joiner><mark>NOEXEC`, error 102), with a letter too many (`NOEXEC<mark>`, `SHOWPLAN_AL<mark><mark>`, `SHOWPLAN_AL<mark>L`, `SYM<mark><mark>ETRIC`, `CLA<U+00DF><mark>IFICATION`, `MA<U+FB06><mark>ER`), or in the place of any other letter (`SY<mark>METRIC`, `NO<mark>EXEC`). In `[...]` too, for a hint without `WITH`: `([READUNCOM<mark>ITTED])`. The reserved words with a pair stay exact (`ADD`, `COMMIT`, `CROSS`, `DBCC`, `KILL`, `ROLLBACK` with a mark are error 102, with every mark).    - **What was swept, every BMP code point in each place, by parsing (2026-11-02, both servers).** The second letter of each pair (`UNCOM<c>ITTED`, `UNCOMMIT<c>ED`, `SYM<c>ETRIC`, `SHOWPLAN_AL<c>`, `CLAS<c>IFICATION` on 2025, and the hint `READUNCOM<c>ITTED` and `READUNCOMMIT<c>ED`): the letter in either case, the eight marks, U+029F for L, and nothing else. One place for each other letter these words use (N, O, E, X, C in `NOEXEC`; A, U, T, P, I, L in `AUTOPILOT`; `_`, B, R in `XACT_ABORT`; S, H, W in `SHOWPLAN_ALL`; M in `SHOWPLAN_XML`; V in `LEVEL`; D in `UNCOMMITTED`; Y in `SYMMETRIC`; G in `SIGNATURE`; K in `NOLOCK`; F in `CLASSIFICATION`, on 2025 alone, since 2016 has no such statement): the letter in either case, its small capital if it has one, and nothing else. By the collation's `=`, no one character equals three or more letters in a row of these words. **Not swept:** every position of every word, and two or more characters in one letter's place other than what is above. So this is the most that was measured, not a proof that no other spelling exists: `live::the_servers_read_a_repeat_mark_as_the_letter_before_it` holds the marks.
   - **Only a match that refuses or reports goes by it.** A real name stays a name, because the whole word must spell the keyword: `SEND时间`, `UPDATE时间`, `NOEXEC` with an accent, and `Dele<U+0301>te`, a full-width `SAVE` or `DELETE<U+200D>` as aliases all reach the server, each of which it takes. The characters that are skipped cost a false refusal only in a word that spells one of these keywords without them, such as `SEND` followed by an Ethiopic letter. Where a match lets something through or turns a report off (the allowlists, a statement's first word, a scratch target's `TABLE`, the end of an argument scan, the note's `FROM` and `DISTINCT`), the spelling is exact, so `sp_who<joiner>` isn't on the list, and `SELECT<joiner> 1` at a batch's start is still an implicit call.
   - **Object names go by their ASCII letters alone (`guard::names`).** Resolving a name follows the collation of the database it resolves in, not the parser's comparison, and no table can hold what folds to `sys` or `dm_db_index_physical_stats` under every collation: by `OBJECT_ID`, one or two letters replaced at a time, 893 spellings resolve under `Latin1_General_100_CI_AI` and 118 under `SQL_Latin1_General_CP1_CI_AS` ("Near, not whole"). ASCII must spell the target's letters in order, in any case, so `Sales_<U+00E9>` is no `sys` and `dm_db_index_<U+00F3>perational_stats` isn't the function. Nothing else goes by this: it can only refuse.
     - **What that doesn't cover: collations that fold ASCII itself.** By `=` on 5,273 non-binary collations, an upper bound, `Frisian_100_*_AI` reads `i` as `y`, `Maori_100_*` ignores `-` and `Mohawk_100_*` ignores `:` anywhere, and under `Finnish_Swedish_100_CI_AI`, `Norwegian_100_CI_AI` and `Danish_Greenlandic_100_CI_AI` `u` with U+0308 or U+030B equals `y`. So `sis.dm_db_index_physical_stats`, `[sy-s].` and `[sy:s].` pass in the `NULL` shape, through the exe against a closed port. That any of them resolves wasn't tried, for want of a database of those collations. Under `Latin1_General_100_CI_AI` no ASCII character does this, by `OBJECT_ID` and by 192 million comparisons of an ASCII character followed by another.
     - **What that can refuse for nothing:** a call of a user's function that has all of it: a schema and a function name whose ASCII letters fit the target's in order, exactly five arguments, the literal `NULL` or `DEFAULT` first and a literal `'DETAILED'` or `'SAMPLED'` fifth. A name with no ASCII letter at all fits anything, so `<CJK schema>.<CJK function>(NULL, 2, 3, 4, 'DETAILED')` is refused with this rule's reason, which names the system function, as it can't know more (a test holds it). Every neighbour tried keeps passing: another function by one ASCII letter (`s<U+00FD>s.dm_db_index_operational_stats`, `sys.dm_db_<U+00ED>ndice_physical_stats`), another schema (`Sales_<U+00E9>.`, `[Syst<U+00E8>me].`), a scoped call, `'LIMITED'`, `NULL` or a variable as the mode, and the same names not called. So nine calls of a function with no ASCII letter in those arguments of a `NULL`-first call, at any argument count and with any mode, are refused as too complex (`the arguments of sys.dm_db_index_physical_stats name it more than 8 times`), which fails closed and is rare.
     - **The mode has its own reading (`guard::mode_letters`, `guard::best_fits`),** since it doesn't follow a database's collation (below): full-width forms and U+207F as the letter, small capitals and ligatures as theirs, everything else beyond ASCII as nothing; and, for a string that goes through a code page, any character beyond ASCII in a letter's place.

   T-SQL doesn't require semicolons, so statement boundaries are unreliable. The classifier therefore doesn't try to find statements to allowlist. Instead it reads **every word token** against the rules below. In the middle of a batch those are lists of what is refused, with allowlists for `EXEC` and `DBCC`, so **a statement whose words are on no list passes**: it fails closed only for a batch's first word (implicit calls, below). `ADD SIGNATURE` got through that way until 2026-11-01, and `RAISERROR ... WITH LOG` until 2026-11-02. A review of the servers' statement-starting words found nothing more that does anything, but a statement a later server version adds would pass mid-batch until a rule names it, and only the wrapper and the login's permissions stand behind that. (`ADD INFORMATION PROTECTION TO` passes on 2025; the parser knows the words and answers error 102, so it reads as a grammar rule that is turned off.)
   - **Writes to scratch objects are allowed.** These are `INSERT`, `UPDATE`, `DELETE`, `SELECT … INTO`, `OUTPUT … INTO`, `TRUNCATE TABLE`, `CREATE TABLE`, `CREATE INDEX … ON`, `ALTER TABLE` and `DROP TABLE [IF EXISTS]`, when their target is a session temp table (`#t`) or a table variable (`@t`), bare, with nothing after it that continues the name. The same keywords with any other target are blocked, including plain aliases (`DELETE t FROM dbo.T t`). Of `ALTER TABLE #t`, only `ADD` and `SWITCH` pass: the main loop reads the keyword inside `ALTER COLUMN`, `DROP COLUMN` and `DROP CONSTRAINT` as a statement of its own, so they are refused as `ALTER would write` or `DROP would write`.
     - **A dot after the name makes it another name.** The servers read `#x.dbo.t` as a table in a database `#x` (error 2702), `#x.t` in a schema, and `#x.a.b.c` on a linked server (7202). These reached both servers until 2026-11-02, and in `DROP TABLE #a.b, dbo.T` the check stopped at the first name, so the second was really dropped (shown on a temp table, `#a.b, #real`, on both). Refused like any other target: `DROP TABLE #a.b would write`. `@x.y` too, which is the servers' error 102 anyway.
     - **Global temp tables (`##t`) are blocked:** other sessions share them, so a write could block or confuse them.
     - **A temp table written another way is refused, and told how to write it.** The servers read `[#t]`, `"#t"`, `tempdb..#t` and `tempdb.dbo.#t` as the session's table (`SELECT a FROM [#t]` runs on both), but the rule is one bare token's, which keeps it simple, so a write through one is refused with `INSERT [#t] isn't read as a temp table: only the bare name is` and the advice `Write it as #t` first (`--allow-write` may be no way out: a `deny` profile, `sqlh mcp`). For `##t` so written, the global temp table's refusal. A name that can't be written bare (`[#a b]`), or that a qualifier puts elsewhere, keeps the plain `would write`.
     - **A `TOP` clause's `PERCENT` is skipped,** being reserved and so no target's name: `DELETE TOP (10) PERCENT FROM #t` passes and `... FROM dbo.T` is `DELETE dbo.T would write`.

More than 16 tokens before `TO` is refused: `ALTER TABLE ... SWITCH would write`.

   When it blocks something, nothing runs. It reports `-- blocked: <where>: <reason>; nothing was run. <advice>` and exits 5, for example `-- blocked: line 3: UPDATE dbo.Orders would write; nothing was run. Rerun with --allow-write if the write is intended`. The advice fits the refusal. `--allow-write` is suggested only where it helps, and a better spelling comes first where there is one: a `#temp` table instead of `##t`, `sys.sp_who` instead of `dbo.sp_who`, `sp_spaceused` without `@updateusage`, `sys.configurations` instead of `sp_configure` with a value, a view instead of a DBCC command, or fixing a typo. Under a profile whose `write_policy` is `deny`, `--allow-write` is a usage error, so no refusal offers it: the alternative stays, and the advice says the profile doesn't allow writes instead, `-- blocked: line 1: DELETE dbo.T would write; nothing was run. Profile test doesn't allow writes (write_policy = "deny")`, or `… Use a #temp table; profiles test doesn't allow writes (write_policy = "deny")` (plan-history.md 2.16, from agent trial 2). `sqlh mcp` is read-only (owner decision 16), so its refusals don't offer `--allow-write` either: `... Use a #temp table; sqlh mcp is read-only`, or `sqlh mcp is read-only` alone (`guard::WritesOff`). A refusal `--allow-write` can't lift (`NOEXEC` under `--check`) keeps its own advice; in `sqlh mcp` that advice names no flag either: `Remove SET NOEXEC (the check tool sets it already); write a column named NOEXEC as [NOEXEC]` (mcp-mode.md §4).

   | A procedure not on the list | `EXEC sp_WhoIsActive isn't on sqlh's list of read-only procedures, so sqlh can't tell what it does` | `Rerun with --allow-write to run it as written` |
   | An implicit call of one | `sp_WhoIsActive starts the batch, so SQL Server would run it as a stored procedure (a typo?); it isn't on sqlh's list of read-only procedures` | `Fix it if it's a typo, or rerun with --allow-write to run it as written` |
   | `sp_query_store_flush_db`, however qualified, `EXEC` or implicit | `EXEC sys.sp_query_store_flush_db isn't on sqlh's list of read-only procedures: it writes Query Store's in-memory data to disk` | `Read sys.query_store_runtime_stats instead: it has the rows not yet flushed too; aggregate by plan_id, execution_type and runtime_stats_interval_id` |
   | A DBCC command not on the list, with a replacement | `DBCC PAGE isn't on sqlh's list of read-only DBCC commands` | `Read sys.dm_db_page_info (SQL Server 2019 and later) instead, or rerun with --allow-write` |
   | Without one | `DBCC FREEPROCCACHE isn't on sqlh's list of read-only DBCC commands` | `Rerun with --allow-write to run it as written` |
   | DDL | `ALTER EVENT SESSION would write` | `Rerun with --allow-write if the write is intended` |
   | A data change | `UPDATE dbo.T would write` | the same |
   | `AI_GENERATE_EMBEDDINGS` (decision 55) | `AI_GENERATE_EMBEDDINGS is not allowed in read-only mode: it can send its text to an outside endpoint (if it is a column name, write it as [AI_GENERATE_EMBEDDINGS])` | `Rerun with --allow-write to run it as written` |
   | A call of `sys.fn_ledger_retrieve_digests_from_url` (decision 56) | `sys.fn_ledger_retrieve_digests_from_url is not allowed in read-only mode: it reads from a URL the query names, which can carry text off the server` | `Rerun with --allow-write to run it as written` |
   | `USE MODEL` inside a call (decision 57) | `USE MODEL is not allowed in read-only mode: it names an external model, which can send text to an outside endpoint` | `Rerun with --allow-write to run it as written` |
   | A `RAISERROR` that doesn't quote its message (decision 59) | `RAISERROR with a message number, or a variable that can hold one, can write to the error log, which a rollback can't undo` | `Quote the message instead, as in RAISERROR('%s', 16, 1, @msg), or rerun with --allow-write to run it as written` |
   | A listed procedure in another case (decision 62) | `EXEC SP_WHO2: only the lowercase spelling is taken as the system procedure (in a case-sensitive database another case can name a different one)` | `Write it as sp_who2, or rerun with --allow-write to run it as written` |
   | A temp table's name where only an alias or a CTE's name can be (decision 61) | `#o here isn't a temp table but an alias or a common table expression's name, through which a write would reach the table behind it` | `Name it without the #, or rerun with --allow-write to run it as written` |

   - **A DBCC command's replacement:** `LOGINFO` → `sys.dm_db_log_info`; `DBINFO` → `DATABASEPROPERTYEX(name, 'LastGoodCheckDbTime')`; `SHOWCONTIG` → `sys.dm_db_index_physical_stats`; `PAGE` → `sys.dm_db_page_info (SQL Server 2019 and later)`, since the guard runs before connecting and SQL Server 2016 SP3, which sqlh supports, lacks it; `IND` → `sys.dm_db_database_page_allocations (undocumented)`; `PROCCACHE` → `sys.dm_exec_cached_plans`; `SHOWFILESTATS` → `sys.dm_db_file_space_usage`, whose `total_page_count / 8` and `allocated_extent_page_count / 8` gave the command's `TotalExtents` and `UsedExtents` on both versions. Each form is `Read <replacement> instead`. A command is shown in upper case; with no bare word after `DBCC`, the reason shows what is there, or `DBCC ?`.
   - **A DDL statement's name** is sqlh's own, from a fixed list of what `ALTER` and `CREATE` make (`guard::DDL_STATEMENTS`), so the input's words never pass for one, in any case and however it is spaced: `ALTER RESOURCE GOVERNOR`, `ALTER DATABASE SCOPED CONFIGURATION`, `ALTER DATABASE`, `ALTER INDEX`, `ALTER AVAILABILITY GROUP`, `CREATE STATISTICS`, `CREATE EVENT SESSION`, `CREATE OR ALTER VIEW`, and `DROP` other than `DROP TABLE` from the same list (decision 67): `DROP DATABASE`, `DROP INDEX`, `DROP DATABASE SCOPED CREDENTIAL`. The longest that fits is named (`ALTER DATABASE SCOPED SET READ_ONLY`, a database called `SCOPED`, is `ALTER DATABASE`), and it is read past `CREATE`'s `UNIQUE`, `CLUSTERED` and `NONCLUSTERED`. A word not on the list leaves `ALTER would write`, `CREATE would write` or `DROP would write` (`DROP SIGNATURE`), refused all the same. It is a few tokens of lookahead, once, on the way to a refusal, under the budget below. A table keeps its name (`ALTER TABLE dbo.T would write`, `CREATE TABLE dbo.T would write`), and an index on a table keeps the table's (`CREATE INDEX dbo.T would write`). `ALTER INDEX ... ON #t` and `CREATE STATISTICS ... ON #t` are refused like the rest until the scratch additions (command-categories.md §6.3).
   - **Unchanged until the kinds of change exist** (command-categories.md §6.9, With v2): `EXEC (dynamic SQL) would write`, `EXEC of a procedure named by a variable would write` `EXECUTE AS would write`, `ARG_CHECKS`' refusals and the qualifier rule's.
   - **Under `--check`** `--allow-write` only compiles (`RunPolicy::wrap`), so the advice can't promise a run: `to run it as written` becomes `to compile it as written`, in an unknown procedure's, an implicit call's, a DBCC command's without a replacement and the qualifier rule's (`Rerun with --allow-write to compile it as written`). The other advice never said it would run.
   - **Under a `deny` profile and in `sqlh mcp`** the `advice_for` rule above holds for all of these: `EXEC sp_WhoIsActive ...; nothing was run. Profile test doesn't allow writes (write_policy = "deny")`, or `... sqlh mcp is read-only`; `... Fix it if it's a typo; sqlh mcp is read-only`; `... Read sys.dm_db_log_info instead; profile test doesn't allow writes (write_policy = "deny")`. `--allow-write` lifts the flush's refusal too, as it does every refusal of the classifier; its advice just doesn't offer the flag, since a read does what the flush is usually run for.

   **Under `--check`** one more rule applies, whether or not writes are allowed: input that mentions `NOEXEC` is refused, because `SET NOEXEC OFF` would run the SQL instead of compiling it. The rule is deliberately coarse. It refuses the word anywhere outside strings, comments and quoted names, read as the servers read it (the comparison above), so a bare column or alias named `NOEXEC` is refused too, while `[NOEXEC]` is fine. That comparison is what stands between `--check` and a real run, and it was measured on one collation: on a database of another (above), a spelling sqlh doesn't know could still switch the check off. The advice says so, and that `--allow-write` doesn't lift this rule.

   Malformed input (an unterminated string, name or comment) never stops the classifier: everything after the opening quote is treated as quoted, and the server reports the syntax error, so nothing in that batch runs.

   A refusal's line is the line of the keyword that makes it. An `EXEC` is reported on its own line, also when nothing follows it or when the procedure's name is on a later line.

   **Bounded work.** The classifier runs on the whole input before anything connects, before the signal listeners exist, so neither `-l` nor `-t` limits it, and sqlh's cancellation response is not there to cut it short. It therefore reads every batch in time that does not depend on how the input is shaped, whatever its size under the 10 MB cap (§4.4). Its lookahead is bounded in three ways, and a budget stands behind them.
   - **`TOP (` clauses are read in one pass.** The target of an `INSERT`, `UPDATE` or `DELETE` that has a `TOP (...)` clause follows the clause's closing parenthesis. The classifier counts parentheses as it reads and finishes the check when the clause closes, instead of scanning ahead to it from each keyword, which cost time quadratic in the nesting. A refusal is still the earliest keyword's, as if each target had been looked up at once. At most 16,384 clauses may be open at once, a few bytes each; one more is refused. Real statements nest a few.
   - **The arguments of `sp_spaceused` and `sp_configure` are scanned a bounded number of times.** The scan for `@updateusage` (or `@configvalue`) runs to a `;` or a statement keyword outside parentheses (a procedure number's `;`, and an unreserved keyword where a value goes, are read past, above). Neither procedure takes parentheses, so a scan that reads more than 8 refuses the input. A scan can reach a later call only through an open parenthesis (an `EXEC` ends it otherwise), so with that limit no token is read by more than a handful of scans.
   - **A call of `sys.dm_db_index_physical_stats` is scanned a bounded number of times.** The scan (decision 30(d), above) stops at the first token of the first or the fifth argument that isn't its literal, and at the call's closing parenthesis, so only the second to the fourth arguments can read on to a later call. Those may call the function, or a name that spells it, at most 8 times, since only a name with its `(` can start a scan: a scan that reads more refuses the input, so no token is read by more than 9 scans. Nothing real calls it there at all. The call itself is followed in the pass, with no lookahead from its `sys`.
   - **A procedure name is read a few times, and then the classifier is done with it.** The name after an `EXEC` is read by the allowlist check, the qualifier check and, for a refusal, the message. A name that is accepted has at most three parts; a longer one is refused after those reads, and the classifier stops there, so the reads of one name are never repeated from an `EXEC` inside it.
   - **The budget.** Every read of a token counts as one unit of work, lookahead included, and a read counts one more unit for each 32 bytes it went over (a token, with the whitespace and comments before it), so a huge string or comment that a lookahead crosses repeatedly is not free. Each pass over a batch (the write classifier; under `--check`, the NOEXEC search too) gets 2,000,000 units plus 3 for each byte of the batch: 32,000,000 for the largest. A plain pass costs at most 1 unit a byte, and the costliest input found, a `DROP TABLE #,#,...` list, 2.5 (a test holds it; a list of `#a` is 1.7, the figure here until 2026-11-02). When a pass spends its budget the batch is refused. The answer the truncated text would give is never used. The measured cost of the limits above and of the budget is in §11 and [notes/memory.md](notes/memory.md).

   Input that goes past one of these is refused before anything connects, with exit 5 and a message that says what the check could not do and what to do about it:

   `-- blocked: line 1: this input is too complex for the read-only check: TOP ( clauses are nested more than 16384 deep; nothing was run. Simplify it or split it into smaller batches with GO, or rerun with --allow-write if the write is intended`

   The reason after the colon is one of four: `TOP ( clauses are nested more than 16384 deep`; `the arguments of sp_spaceused have more than 8 parentheses` (or `sp_configure`); `the arguments of sys.dm_db_index_physical_stats name it more than 8 times`; or `it would take more than N token reads to classify, which is the most one batch of this size is given`, N being that batch's budget. The line is where the limit was met. The limits apply to each batch: a `GO` splits input into batches, each classified with its own budget. `--allow-write` skips the classifier, so it lifts this refusal as it does the others (the `--check` NOEXEC rule, which `--allow-write` does not lift, is one plain pass and cannot reach its budget).
2. **Transaction backstop.** The session-setup batch ends with `BEGIN TRANSACTION`, and the run ends with `ROLLBACK`. This catches classifier gaps, such as an allowlisted procedure that writes.
   - `XACT_ABORT` stays OFF, so error behavior matches `--allow-write` runs. It is set OFF explicitly in the session-setup batch, ahead of `BEGIN TRANSACTION` (§4.3), not left to the server's `user options` default: with it ON, the attention that stops a counted result or `-t` would roll the wrapper back. Input that sets it ON itself is counted exactly and keeps `-t` a failure (§4.4).
   - The invariant: before each batch, the driver must report an active transaction. If an error rolled the wrapper back (a deadlock victim, a severity 20+ error, and ordinary errors too, such as `USE` of a missing database, 911, and a conversion error, 245, both severity 16 and both seen on both servers), the run stops so nothing executes outside it, `--continue-on-error` or not. The guard can't foresee these. They fail closed: the batch has ended, and inside a `TRY` a conversion error leaves the transaction uncommittable (`XACT_STATE()` -1, then 3930 on a write, seen on 2025), so nothing writes. After the last batch the same check runs: a wrapper that is gone without any batch having failed (rolled back by something that raised no error) ends the run with exit 1 and `-- error: read-only guard: the wrapper transaction was gone after the last batch ...`, not a success.
   - It does not undo effects outside transactions: sequence and identity values, xp or CLR side effects, linked servers, mail, and the error log. `RAISERROR ... WITH LOG` and a `RAISERROR` that doesn't quote its message (a number or a variable, decision 59) are refused above, but a module's body is opaque to the guard, so a procedure, trigger or function that raises a logged message is not, and nor is an error the server logs by itself (R55). On SQL Server 2025, `AI_GENERATE_EMBEDDINGS` sends its text to an outside endpoint where an external model is defined, as `sp_invoke_external_rest_endpoint` does, and neither can be called back; both are refused above (decision 55), as is `sys.fn_ledger_retrieve_digests_from_url`, which reads from a URL the query names (decision 56), but a view, a user function, a synonym over such a function or a computed column over it isn't visible to the guard, and reading one is still a read.
   - No driver reconnect can run a batch outside it: sqlh keeps mssql-tds's session recovery (idle connection resiliency) off, since `connect_retry_count = 0` means the login never asks for it, and `Session::connect` fails if it were ever negotiated (owner decision 41; docs/notes/driver-0.3.0.md §2). A broken connection is reported, never silently replaced; in `sqlh mcp` the engine's one retry on a new connection (decision 19) is the only reconnect.
3. **Honest docs.** `--help` and the README say plainly that the guard reduces accidents but is not a security boundary. For real enforcement, use a login with only `db_datareader` (plus `VIEW DEFINITION`).

## 8. Credentials and profiles

The profile file is `%USERPROFILE%\.sqlh\profiles.toml` (decision 53). It isn't under `%APPDATA%` because Windows redirects that folder for a packaged app such as the Claude desktop app: where the package made `%APPDATA%\sqlh` first, what it starts reads its own copy under `...\Packages\<package>\LocalCache\Roaming`, and a profile added in the user's shell never reaches it. `%USERPROFILE%` isn't redirected, so a shell and a harness read one file.

**The move from `%APPDATA%\sqlh\profiles.toml`** happens whenever a run that reads profiles at the default place finds that file, under the profiles lock (below). With nothing at the new place it is copied as it is. Otherwise a profile the new file lacks is added, the file's `default` is taken if the new file has none, and the new file is rewritten as `profiles add` rewrites it. A profile in both that differs keeps the new file's version; the old file is then kept beside the new one as `profiles.from-appdata.toml` (`-2`, `-3` and so on, never overwritten), and one line on stderr names the profiles and both files. The old file then goes, with its lock file and empty folder; failing to remove it is an error that names it, since left there it would add back a profile removed later. A run takes up to two copies: under a packaged app, removing the package's copy uncovers the real file, which a process in the package can read and delete (measured 2026-11-01). A file that doesn't parse stops the run with its name and stays. A later run from the other side of the package finds the old place empty. Stored passwords stay where they are: they go by profile name, whichever file holds it, and a profile's identity doesn't depend on the file (Passwords, below). An `SQLH_CONFIG` file is never moved, and neither is anything when `APPDATA` isn't set.

**Each earlier file is moved under its own edit lock too (R51).** Its editor holds that lock and not the new file's: an earlier sqlh, or this one with `SQLH_CONFIG` naming the old path. So the move takes the new file's lock, then `%APPDATA%\sqlh\profiles.toml.lock`, then for the move from before the rename `%APPDATA%\sqlharness\profiles.toml.lock`, checks again under them, and reads and removes the file only while it holds them; an editor holds one lock only, so the order can't deadlock. A lock held for the profiles lock's wait (10 s) is the usual error, `another sqlh is editing the profiles (<lock> is held); try again when it has finished`, with nothing copied or removed, and the next run moves what the editor left: an addition, a policy change or a removal it made arrives as it made it. The lock files and empty folders are removed only after the move lets go of them; a lock another process holds can't be removed. Not covered: under a packaged app, a lock file the package opens may be its private copy rather than the real one an editor outside the package holds, so there the lock may not exclude that editor (decision 53's redirection, unmeasured for locks).

**The move from before the rename:** profiles saved before the project was named sqlh (2026-10-12) are in `%APPDATA%\sqlharness\profiles.toml` with passwords under `sqlharness:<profile>`. The first run that reads profiles while only that file exists, with none at `%USERPROFILE%\.sqlh`, moves them to `%APPDATA%\sqlh`, from where the move above takes them, once: each SQL login's stored password to `sqlh:<profile>` first, bound to that profile's identity (Passwords, below) and keeping the old credential's login, and deleting the old credential only after the new one is written; then the file, copied as it is, after which the old file and its empty folder are removed. The move runs under the profiles lock (`profiles.toml.lock`, Profile commands below) and checks again under it that the new file still doesn't exist, so a profile edit and the move never overlap and two first runs at once move once (R21); the old file's password replaces any under the new name, since that file is the one that describes the profile. Every step can be repeated, so a move cut short by an error is finished by the next run; an existing new file is never overwritten, and an `SQLH_CONFIG` file is never moved.

Override the profile file's path with `SQLH_CONFIG`, in any of the path forms of `-i` (§4.2). A missing file is "no profiles yet", and saving a profile creates its folder, so a Git Bash path (`/c/Users/me/profiles.toml`) in cmd.exe or PowerShell, which Windows reads as a folder on the current drive, is refused when that folder isn't found (exit 3, with the hint of §4.2) rather than creating `\c\Users\me` at the root of the drive.

It is read by a small, strict parser of our own, which avoids pulling in the `toml` and serde crates. It understands the subset `sqlh` writes:
- a top-level `default`
- `[profiles.NAME]` tables
- `"strings"` (with the escapes `\" \\ \n \t`), whole numbers and booleans

Unknown keys, repeated keys and contradictions are errors that name the line, so a typo can't fail silently. `sqlh profiles add` rewrites the file, which drops any comments.

**Profile settings that mirror flags** take the usual precedence: the flag, then the profile, then the default. `login_timeout`, `query_timeout`, `max_rows` and `max_cell` are whole numbers like their flags. `lock_timeout` is whole seconds (0 means no limit, at most 2147483), and `read_uncommitted` and `exact_count` are `true` or `false`; an out-of-range or mistyped value is an error that names the line (exit 3). A profile's `read_uncommitted = true` has no effect in a run that can write (`--allow-write`, or `write_policy = "allow"`), and is not an error (§4.3). A flag given as `--read-uncommitted=false` turns it off for one run.

**`description`** (plan-history.md 4.1) says what the profile is for, so that an agent can pick a profile from `profiles list` in one call: environment, purpose, sensitivity. It is optional, one line of at most 300 characters (counted as characters, not bytes), with no control character (tab included), no Unicode line or paragraph separator and no bidirectional control character (Unicode's Bidi_Control: U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069, which reorder how text is shown; right-to-left text itself is fine); a file that breaks this is an error that names the line (exit 3), and an empty one is no description. `profiles add` writes it first in its table. Whoever can run `profiles add` can set it, a person or an agent (R19), so it is data, never instructions, and is escaped on output like any other field.

`auth` decides the auth method: `"windows"` or `"sql"`, and `user` must be set exactly when it's `"sql"`. Files without `auth` fall back to "SQL auth when `user` is set". The method is resolved before the login, with the usual precedence (flags, profile, environment), so a Windows-auth profile stays Windows auth even when `SQLCMDUSER` is set; `-U` or `-E` override it for one run.

```toml
default = "dev"

[profiles.dev]
description = "dev box, disposable data; safe for ad-hoc"   # one line, at most 300 characters
server = "devsql01,1433"
database = "AppDb"
auth = "windows"             # windows | sql
encrypt = "mandatory"        # optional | mandatory | strict
trust_server_certificate = false
write_policy = "deny"        # deny | flag | allow; profiles add saves deny for a new profile
max_rows = 100
query_timeout = 60
lock_timeout = 10            # seconds a statement waits for a lock; 0 = no limit (§4.2)
read_uncommitted = false     # true: read-only runs read without shared locks (§4.3)
exact_count = false          # true: count every hidden row, however long it takes (§4.4)

[profiles.reporting]
server = "tcp:myserver.database.windows.net"
database = "Reporting"
auth = "sql"
user = "agent_reader"        # password: Credential Manager target "sqlh:reporting"
write_policy = "deny"
```

**Passwords**
- Stored in Windows Credential Manager as a generic credential with target `sqlh:<profile>` (`sqlharness:<profile>` before the rename; moved once, above). Windows protects it per user with DPAPI.
- Accessed through `CredWriteW` and `CredReadW` from `windows-sys`, so no extra crate is needed.
- A stored password is only ever sent to its profile's own server and login, or to a server that server routes the login to (owner decision 43, 2026-10-31: SQL Server can redirect a login during it, as Always On read-only routing does with `-K ReadOnly`, and the driver follows with the same credentials, as 0.2.0 already did; mssql-tds 0.3.0's Enhanced Routing can also name the database; docs/notes/driver-0.3.0.md §1.3). When sqlh checked the server's certificate, only the server sqlh connected to can route, inside its TLS session, so an agent still can't repoint a profile to harvest its password. Whether the certificate is checked depends on the encryption the connection negotiated (mssql-tds `resolve_tls_validation`, R46): strict (`-Ns`) always checks it, even with `-C`; mandatory checks it unless `-C`; optional (`-No`) doesn't ask for it. Under optional, a server that requires encryption gets full TLS, checked as under mandatory; otherwise only the login packet is encrypted, with no certificate check, or nothing is, if the server can't encrypt. Where the certificate isn't checked (`-C` without strict, or optional without the server's full encryption), the route is no better protected than the login itself: anyone on the network path who can answer for the server can route the login, password included, as they could read it. To rely on the certificate, ask for it: mandatory without `-C`, or strict. In `sqlh mcp`, a long-lived process, mssql-tds 0.3.0's DNS cache can also send the login to the address the server name had at the last accepted login, when looking the name up fails, if the server enabled the cache, which the on-prem SQL Server 2025 test server does not (measured 2026-10-31, docs/notes/driver-0.3.0.md §8) (decision 42; wherever the certificate is checked, as above, it is checked against the name). `--profile x -S elsewhere` refuses rather than leak it, and `profiles add` asks for the password again whenever the server or login changes. Otherwise a prompt-injected agent could repoint a profile and harvest the password. Other edits, like `-C` or `-d`, keep the stored password; `--new-password` forces a new prompt.
- **Each stored password is bound to what it was stored for** (R20). The credential's user name is the SQL login, and its comment is `sqlh connection profile password; identity <16 hex digits>`: the profile's identity, a 64-bit FNV-1a hash of its server (case folded), login, `encrypt` and `trust_server_certificate`, as a run would use them (`config::identity`). The hash detects a mismatch; it protects nothing. A run sends a stored password only when it fits the profile the run read from the file: the login matches and, when the credential has an identity, so does the identity. A credential with no identity (stored before R20, or by `cmdkey`) is checked by its login alone.
  - **Why:** the file and the credential are two stores, written one after the other, and a run reads them without the lock. `profiles add` stores the new password before it saves the file, so a run can read the old profile and then the password stored for the new server; and an edit killed between the two writes leaves that pair behind for good. Neither is sent.
  - **A password that doesn't fit:** the run takes the profiles lock (waiting up to 10 s for an edit under way) and reads the file and the password again. If they fit now, the run goes on. If not, an edit was cut short, and the run fails (exit 3): `profile NAME's stored password was stored for another server, login or encryption than the profile now has (an edit of it was cut short), so it isn't sent; run: sqlh profiles add NAME`. If the lock can't be taken, the failure says another sqlh is editing the profiles.
  - **What this does not cover:** a run that reads the old file and then the new password of an edit that changed only the password (same identity) sends the new password to the same server and login, which is the edit's intent. A legacy credential an interrupted edit of an older sqlh left behind for another server, with the same login, can't be told apart.
- `SQLCMDPASSWORD` also works, for CI. No `$(SQLCMDPASSWORD)` reads it (§4.3).
- A password is never printed or logged. `profiles list` checks that a credential exists without reading the password (the login and comment are read; the password is not copied).
- **sqlh's own copies are wiped when dropped** (F14, plan-history.md 3.2): every password sqlh holds is a `Secret` (`src/secret.rs`, `zeroize::Zeroizing<String>`), whose bytes, spare capacity included, are zeroed when it goes: the prompt's line (read into a buffer allocated once at 1,024 bytes, which the read can't grow, so no reallocation leaves a copy behind; a longer line is refused, and SQL Server allows 128 characters), the copy read back from Credential Manager (one that isn't UTF-8 too, which is refused: `from_utf8`'s error hands its bytes back to be wiped), `SQLCMDPASSWORD`'s copy and the connection settings' copy; the buffer handed to `CredWriteW` is zeroed too, and so is the blob in the block `CredReadW` returns, before `CredFree` releases it (whether or not the password was wanted). **What sqlh can't wipe:** the driver's own `String` in its client context, kept for the connection's life (it can log in again), which `mssql-tds` doesn't zero; the console's input buffer and stdin's; `SQLCMDPASSWORD` in the process environment, which outlives any copy; and what Windows keeps inside `CredReadW` and `CredWriteW` themselves. So this narrows how long a password sits in sqlh's memory; it is no defense against a process that can read sqlh's memory.

**Profile commands**
- `sqlh profiles add NAME -S server [-d db] [-U login] [-C] [-N..] [--write-policy ..] [--lock-timeout S] [--read-uncommitted[=false]] [--exact-count[=false]] [--description TEXT]`
  - It asks for a SQL login's password, with echo off, only when it needs one: a new SQL-auth profile, one with no stored password, a stored password that doesn't fit the profile as saved (an interrupted edit's; it is never rebound to the saved server), a changed server or login, or `--new-password`. A kept password whose identity changes (`-N`, `-C`) is stored again with the new identity, without a prompt. Otherwise it reads nothing from the console (a Windows-auth profile never asks), so it can run unattended. This is the tool's only prompt, and it refuses to run if stdin isn't a console, if echo can't actually be turned off (Git Bash's mintty: use PowerShell, cmd or `winpty`), or if the handler that puts echo back on Ctrl+C or a close can't be registered. Echo comes back on every return path, errors included, and after a crash. Ctrl+C, Ctrl+Break or closing the console at the prompt restores it before the process ends; only a process killed outright can leave echo off in that console.
  - It saves the profile and runs `profiles test`, whose status line times that test alone, from after the save: not the password prompt or a wait for the profiles lock (owner, 2026-11-14; it once said 4782 ms for a 211 ms connect, the time spent typing included).
  - **One edit at a time** (F12, plan-history.md 3.2). `add` and `rm` hold `profiles.toml.lock` (opened with no sharing, next to the profiles file) from reading the file to writing it, so two edits can't lose each other's changes; another sqlh's edit is waited for up to 10 s, then the command fails with `another sqlh is editing the profiles`. The one-time migration takes the same lock, and so does a run whose stored password doesn't fit its profile (Passwords, above). Runs that only read take no lock. The lock is held while `add` prompts, so another edit fails after 10 s while someone types. The file is written whole through a `.partial` file of the run's own, renamed over it, which a failure deletes; a reader sees the old file or the new one.
  - **The file and the password: never a usable mismatch, not atomic.** They are two stores written one after the other. A new password is stored first and, if the file then can't be saved, the previous password is put back as it was (binding included) or the new one deleted, and the error says nothing was changed; if putting it back fails too, the error says so and how to repair it (`--new-password`, or `cmdkey /delete:sqlh:<profile>`). A process killed between the two writes can't undo anything: it leaves the new password, bound to the new identity, beside the old file, which runs then refuse until `profiles add` is run again (R20). An old password goes only after the file no longer refers to it: switching a profile to Windows auth deletes it after the save, and a failed delete says so and how to finish.
  - Options you leave out keep their saved values, so `sqlh profiles add NAME --write-policy flag` changes that alone, and `sqlh profiles add NAME --new-password` replaces the stored password. A given `--lock-timeout 0` or `--read-uncommitted=false` is a value that replaces the saved one, not "unset". `--description TEXT` replaces the saved description and `--description ""` removes it; one that breaks the rule above is refused before anything is read or written (exit 3, `--description: description must be one line of text, ...`, `--description: description must not hold bidirectional control characters, ...` or `--description: description is N characters; at most 300`). `--write-policy`, `--new-password` and `--description` on a run, not `profiles add`, are a usage error (exit 3).
  - The first profile you add becomes the default.
- `sqlh profiles test NAME` connects and reports server, version, edition, database, login, user, encryption and auth scheme, with a note on how long connecting took (the `--verbose` line). Encryption and auth scheme come from `CONNECTIONPROPERTY`, which needs no extra permission. This is the first thing to run when a connection misbehaves. Its query is sqlh's own (`QueryOrigin::Generated`): it skips `$(var)` and the guard, and always runs as a read-only run, inside the wrapper transaction, even under a profile whose `write_policy` is `allow`.
- `sqlh profiles list [--search TEXT]` shows every profile and whether its password is stored, without revealing it. Its columns are `name`, `default`, `server`, `database`, `auth`, `user`, `password` (`stored`, `missing`, `unreadable` or `-` for Windows auth), `write_policy`, `lock_timeout` (`int`, seconds), `read_uncommitted` (`bit`), `exact_count` (`bit`) and `description` (`NULL` when not set). `write_policy` to `exact_count` show what a run with the profile gets, so a key that isn't saved shows its default: `flag`, `10`, `0` and `0`. The server and the login are shown to whoever lists, agents included (owner decision 12): every run's status line names the server anyway, and a login isn't a secret.
  - **`--search TEXT`** (plan-history.md 4.2) keeps the profiles whose name or description contains `TEXT`, in any case (both are lowercased with Unicode's rules), so an agent finds the right server in one call. The status line says how many matched: `-- ok: 1 of 3 profiles matches, 2 ms` (`0 of 3 profiles match` for none, which is an empty list and exit 0, not an error); without `--search` it is `-- ok: 3 profiles, 2 ms`. The search text is never echoed.
  - **The output** is text only (owner, 2026-10-13, PLAN.md §6.13): a result set like a query's text output, with the profiles file's path as a note. Every field is escaped as in any result (§5.1), so a description's backslash is doubled and nothing in it can start a line. `--format` is a usage error here: listing profiles is setup an agent does once, text is the cheapest format to read, and a json listing would need a document shape of its own (R25).
- `sqlh profiles rm NAME` removes the profile from the file, then its credential. If the credential can't be deleted, the error says so; running `rm` again finishes the job, deleting a password a removed profile left behind.

## 9. Schema commands (built 2026-10-13, `deps` 2026-10-14; plan-history.md Phase 4)

The spec is [schema-commands.md](schema-commands.md): invocation, labeled output sections (§5.1 "Sections"), name resolution, patterns, and each command's SQL. A command is the first word that isn't an option (`sqlh --profile dev describe dbo.Orders`), runs its own SQL in the current database as a read-only run, and takes `--format`, `-o` and the limits like any run. Summary:

| Command | Output |
|---|---|
| `info` | Server, version, edition, database, login, user, transport, auth scheme, server time, and `server_permissions`: `sysadmin`, else the held ones of VIEW SERVER STATE (or the 2022 PERFORMANCE and SECURITY STATE it implies), VIEW ANY ERROR LOG, VIEW ANY DEFINITION and securityadmin, else `none` (schema-commands.md §6.1); the connection as a note. |
| `dbs` | Databases with state, access, compatibility level, recovery model, read-only and collation. |
| `tables [pattern]` | Tables and views (name, type, estimated rows, modified) whose name or `schema.name` matches. |
| `describe <object>` | Tables: `object` (rows, flags, description), `columns`, `indexes`, `foreign_keys`, `referenced_by`, `check_constraints`, `triggers`. Views: `object`, `columns`, `indexes`. Procedures and functions: `object`, `parameters` (and `columns` for table-valued functions). System objects too (`describe sys.dm_exec_requests`). |
| `find <pattern> [--text]` | `objects` and `columns` whose names match (substring, or a `*`/`?` glob; case-insensitive); `--text` adds `definitions`, the first matching line of each module body the login can see (an encrypted body, or one without VIEW DEFINITION, isn't searched). |
| `def <object>` | The source of a view, procedure, function or trigger, as a block framed by its line count (§5.1). |
| `deps <object>` | `uses` and `used_by`, one level each way (`name, type, via, note`): code references from `sys.sql_expression_dependencies`, foreign keys, synonyms; `via` names the column or constraint that holds a reference, `note` says `other database`, `caller-dependent`, `not found`, `schema-bound` and the like. Without VIEW DEFINITION on the database SQL Server shows no dependencies, so `deps` fails (exit 1) rather than answer "none". |

Names: `describe`, `def` and `deps` take up to four parts, each plain or delimited (`[...]`, `"..."`); sqlh parses them before connecting, and an invalid part (an unclosed delimiter, more than 128 UTF-16 units, five parts) is a usage error (exit 3), never taken for an omitted part. Every name sqlh shows (in `tables`, `find`, `describe`, `def`, and in its errors and hints) is bracketed when it isn't plain ASCII letters, digits and `_@#$` starting with a letter or `_`, so it can be given back as it is; column lists bracket each column the same way (`[a, b], [c DESC] DESC`). Name errors (an unknown or ambiguous name, a table given to `def`, a temporary table, a definition that can't be shown, `deps` without VIEW DEFINITION) end the run with exit 1 and say what to do; a name in another database, in no database, or on another server is a usage error (exit 3). Whether a database part names the current database is SQL Server's decision (`DB_ID`), made once. `--check` and `-Q`/`-i` don't combine with a command (exit 3).

Catalog SQL must run on SQL Server 2016 SP3 and later (decision 49), validated on SQL Server 2025 Standard and on the 2016 test instance; a feature that needs a later version says so on an older server instead of failing. There is no SQL Server 2012 restriction. Azure-specific constraints remain relevant to future expansion and are not first-release gates.

The commands are canned SQL run through the normal pipeline, with `describe`'s lists aggregated server-side: by `STRING_AGG ... WITHIN GROUP` on SQL Server 2017 and later (the lookup reads `SERVERPROPERTY('ProductMajorVersion')`; 2016 has no `STRING_AGG`, 2026-10-31) at the database's compatibility level 110 and up, and by the ordered `FOR XML PATH` form, which every level parses, only on SQL Server 2016, at level 100 (which refuses `WITHIN GROUP`) or when the lookup returns no level (`schema::Aggregate`, `d6237da`; the threshold 110 since `2504b7c`, R37, where it had been 130). Only there can a name with a character XML can't carry make `describe` fail, after its columns, with the server's error 6841 (exit 1); schema-commands.md §3 explains why.

## 10. MCP mode (built 2026-10-17, plan-history.md 5.2 and 5.3; decided 2026-10-15 to 2026-10-17)

The detailed design and the spec of what's built is [mcp-mode.md](mcp-mode.md); its shape is owner decisions 14–20 (PLAN.md §6). Built and self-reviewed 2026-10-17 (five rounds, the second's fixes in `05032c0`, the third's in `becb56f`, the fourth's in `6e7a0d8`, the fifth's in `4519341` and `dc24d4b`); the owner's external review of `2f53735..a8c5390` (2026-10-18) requested R35–R39, fixed in `6e1a6e7` and `2504b7c` with the internal review's follow-ups in `f1d8b51` and `4663978`, and accepted by its fix verification at `c50dd3c`; the follow-ups R40–R42 are fixed and closed by external verification through `ab6eed7` (plan-history.md, Phase 5.2 and 5.3 review fixes and the fix verifications). The live tool tests (5.4, 2026-10-18) run it against the test server, and real clients drove it (5.5: OpenCode in the legacy era, 2026-10-20; the MCP Inspector in the modern, legacy and `auto` eras, and Claude Code in the modern era, 2026-10-21); none of it changed its behavior (mcp-mode.md §9). Summary:

- **A front end on a reuse engine** (decision 14): `sqlh mcp --profile A [--profile B ...]` is a stdio MCP server, the first front end of a connection-reuse engine built as a library module (`src/engine.rs`), so a daemon behind the CLI could use the engine unchanged; that daemon is deferred until an agent trial shows Bash-driven use stays the main path.
  - **In the same exe** (decision 20): `sqlh mcp` is a subcommand of `sqlh.exe`, and its code runs only when a harness launches it, so CLI-only use pays nothing for it at run time (no startup time, no memory, no open connections). Its size is gated: within 350 KiB, or decision 20 is reopened (300 KB until the R35–R39 fixes took it to 310.0 KiB at `367f8b0`, and the owner amended the decision on 2026-10-18, with `serde_json` built for size). It is 309.0 KiB as built (mcp-mode.md §8).
  - **Dual-era protocol:** it serves revision 2026-07-28 statelessly, each request picking its era by its own `_meta`, and also serves legacy clients that open with `initialize` (2025-11-25, 2025-06-18). `subscriptions/listen` is acknowledged with no notifications (the tool list never changes), held open (at most 8 at once), and, when the server ends, answered and then torn down with `notifications/cancelled`. A response and a notification are never answered, whatever their `id` or `params`; no protocol deviation is known (the self-review's four were fixed, and so were the external review's two, lossy numeric ids, R38, and unchecked method parameters, R39; mcp-mode.md §2, §4).
  - **Its transport can't be stalled by its client** (R35, R36): stdin is read while answers wait for stdout, so a cancel or the end of the input is taken at once while requests wait their turn (at most 64, or 16 MiB, held back); while 64 answers wait for stdout, a stdout that takes no byte for the stall limit (the longest of the listed profiles' query timeouts, a 0 counting as 60 s, so never none) means a client that stopped reading, and the server ends as if stdout had broken. Console events are taken through the whole end but its last wait, for the `--verbose` lines (at most 0.5 s, `delivery::SIDE_WAIT`, as the CLI gives its own), and the end has one deadline an event can only bring nearer: about 2 s after a close, logoff or shutdown, 3 s after Ctrl+C or Ctrl+Break, plus that 0.5 s with `--verbose` and a stderr that isn't taking lines. The process exits 0 however it ends (mcp-mode.md §2, Bounds and The end).
  - **Fixed reach** (decision 18): it serves only the profiles listed at launch, and each tool takes a `profile` among them (the schemas spell it as the profiles file does, and a call's matches in any ASCII case, as `--profile` does), optional with one listed (the default) and required by the tools' schemas with several. Connection settings and credentials are fixed at launch, so no tool argument can choose a server or carry a secret.
- **Tools, read-only** (decision 16): `query` (guarded, in the rolled-back wrapper), `check`, `info`, `databases`, `tables`, `describe`, `find`, `definition`, `deps`. No write tool: writes stay on the CLI, and an `execute` tool comes with Phase 6's command categorization. A profile whose `write_policy` allows writes is read-only here too, and refusals say `sqlh mcp is read-only` (§7).
- **Stateless calls** (decision 15): every call runs on a pooled connection reset (TDS RESETCONNECTION) on its first request, then the session setup, which also sets the isolation level because the reset doesn't restore it (§4.3), then its own wrapper, so it behaves exactly like one CLI run without the connect, but for the session state it refuses because the reset isn't known to clear it (§7, decision 30(e)). No session handles. Checked live (5.4): after a call that set them, the next call on the same session gets a fresh login's `ROWCOUNT`, `TEXTSIZE`, language, `DATEFORMAT`, `DATEFIRST`, `CONTEXT_INFO`, database and options, and no global cursor or #temp table, values and effects (mcp-mode.md §5, §9).
- **Pool** (decision 19): up to 2 connections per profile (`--pool`, 1–8), opened when a call needs one and closed after 15 idle minutes (`--idle`); a reused connection that turns out dead before any of the call's own SQL ran (at its session setup, which carries the reset, or at its `USE`) is reconnected and the call retried once, silently. A reused connection's setup gets at most 5 s (a probe, `REUSE_PROBE`), so one gone silent while idle is found dead in about 10 s (the probe and the driver's wait for the attention) and replaced; a setup the probe cut on a live connection (the attention acknowledged within the driver's 5 s) is reset and run again, alone, on that connection with the call's own timeout, so a slow server keeps its connections and no login is risked, as long as it acknowledges within those 5 s: one silent longer, about 10 s after the setup was sent, can't be told from a dead connection and is replaced like one, the profile's idle connections with it (`dc24d4b` states this boundary in the code's comments; the external review accepted decision 19 as built with it, and engine tests play both sides since `c3c4a63`); the call's `USE` then runs once on its connection, with the call's timeout (`6e7a0d8`, and `4519341`, which keeps the `USE` out of the probe's loop; decision 19 as built and accepted, PLAN.md §6; mcp-mode.md §5). The connect time reports what a probe or a retry took (§5.1). A call beyond the pool waits for a connection for at most its timeout; each batch then gets the full timeout, as `-t` is per batch. A connect, when a call needs one (the retry's included), is bounded by the profile's `login_timeout`, as a CLI run's is by `-l`, not by the call's timeout (mcp-mode.md §4).
- **After a cancel** (decision 17, amended): after a cancel, timeout or count stop, a connection the driver kept is reused, and the next call's reset, whose acknowledgement the driver verifies, is the check that it is clean; one the driver marked dead, or one past sqlh's settle bound, is discarded. A wrapper a cancel or timeout left open is rolled back (after `SET NOEXEC OFF`, for a `check` cut short) before the connection goes back to the pool.
- **Results:** the text format as a single text content item (`format: "json"` for the JSON document). `isError` is set when the exit code isn't 0. A reused connection's status line says `connect 0 ms` (JSON `connect_ms: 0`), or after a probe or a retry the time they took, and a call whose session setup or `USE` failed has no connection tail (§5.1, §5.2). A result's advice, and the limit it names when output was hidden, is what the client or the server's owner can change, not a command-line flag the client can't pass (`output::Advice`): `(max_rows 100)` for `(--max-rows 100)`, `(the server's --max-output)`, the profile's `exact_count = true` for `--exact-count`. A failed connect's hint names the profile's keys (`db::Hints`: `trust_server_certificate = true` for `-C`, the profile's `login_timeout` for `-l`). A timeout's advice offers a larger `timeout` only below the server's limit; a call that had the limit is told so (`narrow the query (60 s is the server's limit)`). The schema tools' hints name the tools (`try: find with pattern X`, `for a table use: describe with object X`). Besides the server's own launch flags, named as what the server's owner changes (`the server's --max-output`, `start sqlh mcp with a larger --pool`, `... --pool or -t` at the limit), only the guard's reasons still mention a flag, to describe a refusal, not to advise, and so does the refusal of a `GO N` past 1000, whose source label is `-Q` (`-Q:2: GO ...`, open; mcp-mode.md §4 has both tables and that list).
- **Calls:** `$(var)` substitution is off (the environment is the server's); each tool takes `profile`, `database` (a `USE` with `]` doubled), `max_rows`, `max_cell`, `timeout` (clamped to the profile's `-t`) and `format`. Only a request that doesn't fit `CallToolRequest` (no tool name or one that isn't a string, an unknown tool, `arguments` present but not an object, `null` included, a mistyped `inputResponses` or `requestState`) is `-32602`, as is any request whose envelope breaks its method's schema (`params` present but not an object, `null` included; a `_meta`, a `subscriptions/listen` filter or an `initialize` whose declared members are missing or mistyped; a `tools/list` cursor that isn't a string; R39, mcp-mode.md §2); arguments the tool can't take are a tool error (`isError`, the run's usage error, exit 3), as the MCP tools page lists input validation among tool execution errors (mcp-mode.md §4), and so is whatever the run finds. Every such refusal is held to the server's `--max-output`, and a name the client sent is cut after 100 characters, with `…` (`tools::echo`). Any request reusing a running call's, an open subscription's or a held-back request's id, whatever its method, `_meta` or arguments, and a malformed one that carries such an id, gets `-32600` and nothing else: the id is every request's first check. An id is a string or an integer within 64 bits, echoed exactly and compared everywhere by its JSON text (R38), and at most 1024 bytes of JSON; an unknown method's name is cut after 100 characters too. At most 64 calls run at once (one more gets the usage error, in its format) and 8 subscriptions are open (mcp-mode.md §2).
- **Launch:** each listed profile is resolved at launch as a run's would be (what it leaves unset comes from the launch environment's `SQLCMD*` variables, as in the CLI), then made read-only; nothing connects until a call needs it, and launch errors are one line on stderr (exit 3; a runtime or thread that can't be started, exit 10), escaped as any field is, so a launch argument holding a line break can't split the line (`dc24d4b`); console-event listeners that can't be installed are done without, which only `--verbose` logs, where the CLI fails with exit 10 (mcp-mode.md §3). `sqlh mcp` must come first: `sqlh --profile x mcp` is the CLI's usage error, on stdout (mcp-mode.md §3). `--max-output` can't be 0, since a result is held in memory.

## 11. Performance targets

The primary product measure is time to the next useful answer across repeated agent turns. Measure repeated-call connection/setup overhead, response size/context consumption, and cancellation-to-retry time alongside the existing executable and startup targets. Bulk throughput is secondary; additional numerical interaction targets need measurement before being committed.

- **Size:** the release exe (stripped) stays under the 3 MB budget that `scripts/check.ps1` enforces (owner, 2026-10-12; plan-history.md 3.3): 2,911,232 bytes at `7feae17`, 234,496 under it. Growth is justified with `cargo bloat --release --crates` and the exe size before and after, and MCP's by decision 20's gate: 350 KiB since the owner amended it on 2026-10-18, after the R35–R39 fixes took MCP past 300 KB (310.0 KiB); `serde_json` is built for size (`opt-level = "z"`), and MCP was 309.0 KiB when last measured, with the R40–R42 fixes (§10, mcp-mode.md §8).
- **Startup:** under 10 ms from process start to the first TDS packet, on a warm cache.
- **Connect:** measured in [notes/connect-latency.md](notes/connect-latency.md), on one dev server and one LAN. Against SQL Server 2025 with SQL authentication, a connect took about 195 ms, and about 150 ms of it was the login step, the wait for the server's reply to the login packet. SQL Server 2025's documented password hashing (PBKDF2) is the likely cause, but that is an inference from the interval; nothing isolated the hashing from the server's other login work. sqlh and the driver added about 5 ms. Not measured: other servers and networks, strict encryption. Windows authentication, by NTLM and with no name lookup, connected in 31–94 ms on the same server; by an address with no PTR record, it pays §4.2's 500 ms wait as well. That supports putting connection reuse first for fast repeated turns (plan-history.md Phase 5), not client tuning; it is no universal lower bound for a connect. **With reuse** (`sqlh mcp`, §10; measured 2026-10-17 on the same server and LAN, release build): a `SELECT 1` call took 223 ms the first time (connect 201 ms) and 9–11 ms on each of the next seven, on the connection the first call opened (mcp-mode.md §9).
- **Failing fast:** every address of a name gets one attempt: a refused one fails in about 2 s, one that doesn't answer after `-l` seconds, and the login deadline, `-l` + 1 s, bounds them all (§4.2). Ctrl+C ends a pending connect at once.
- **Memory:** a run holds one row at a time plus the output path's buffers. Nothing grows with the number of rows, and a large value is cut as it arrives. Measured on a release build ([notes/memory.md](notes/memory.md)), the peak working set is about 10 MB, also for a 1 GiB `varchar(max)` value shown with `--max-cell 500` (before plan-history.md 2.7 it was 2 GB: two copies of the value).
  - **A value.** The PLP types (`varchar(max)`, `nvarchar(max)`, `varbinary(max)`, `xml`, `json` and CLR types) are the only ones that can pass 8 KB, apart from `text`, `ntext` and `image` (below). The driver's row readers allocate a value's whole declared length before they hand it over, so sqlh reads these through the driver's column cursor, in 32 KB chunks, and keeps only what is shown: `--max-cell` characters (binary: half as many bytes), or, with `--max-cell 0`, as many characters as `--max-output` has bytes, since a longer value can't be written whole. The rest is decoded and counted, so the `…[+N]` is exact in every encoding. No value of a row past `--max-rows` is kept: in a result set with such a column the driver skips the row's columns, a large value chunk by chunk, and in any other the row is decoded into a writer that keeps nothing.
  - **What is not bounded.** With `--max-cell 0 --max-output 0` a value is held whole, and so is the line written from it (about 2.7 times its size, measured). `text`, `ntext` and `image` are read whole by the driver, which refuses more than 100 MB (exit 10): a value of about 90 MB peaked at 181 MB (`text`), 224 MB (`ntext`) and 95 MB (`image`).
  - **A row** is its values and the line formatted from them: at most the number of columns × the cell limit × the longest escape (6 bytes for a control character in JSON, 4 in text). A row over `--max-output` is formatted before it is withheld. Ordinary rows take kilobytes; 400 columns of 500 control characters, 1.2 MB of JSON per row, peaked at 12.8 MB.
  - **The queue.** The sinks write into 64 KB buffers (one per stream) and hand full chunks, never more than 64 KB, to an output thread (`output/delivery.rs`), which writes at most 4 KB at a time. Once more than 256 KB is queued, counting the chunk being written, the batch loop stops reading rows and waits for the reader, without blocking the async runtime. That is a threshold, not a ceiling: it is checked after each row and before each statement's results, so the queue can hold 256 KB plus the event that crossed it (a row, or the messages of one statement, of which at most `--max-messages` are formatted), and each stream's buffer up to 64 KB more. With a reader that never reads, the peak was 10 MB for narrow rows and 12 MB for 1,000 columns of 600 characters. The queue is flushed at the end of each batch, and sqlh waits for it to drain before it exits.
  - **SQL input** is capped at 10 MB (§4.4) as a `$(var)` substitution is built, not after it: 200,000 references to a 3,000-byte value are refused when the text reaches the cap, with a 29 MB peak (595 MB before). The text never takes more capacity than the cap, and the line map, made only when a value adds lines, takes 4 to 8 bytes a line of the result. The read-only guard (§7) reads the input as a stream and keeps no tokens, so its memory does not depend on what the input looks like: 10 MB of one-character tokens peaks at 36 MB working set, as without the guard (795 MB when it kept a token list), and a refusal that quotes a 10 MB name, the worst case, 54 MB ([notes/memory.md](notes/memory.md), plan-history.md 2.14).
- **Guard time:** the read-only classifier (§7) runs on the whole input before anything connects, so it is bounded by construction, not by `-l` or `-t` (plan-history.md R18). Measured on a release build ([notes/memory.md](notes/memory.md)), it classifies `UPDATE TOP (` repeated N times, `@t`, then `) @t ` N times (a few hundred kilobytes that no server accepts) in 0.5 ms at 2,000 deep, 1 ms at 4,000, 2 ms at 8,000 and 4 ms at 16,000 (214 ms, 949 ms, 3.4 s and 15.5 s before); the whole process, from start to the refusal, takes under 30 ms. Deeper than 16,384 clauses, or `sp_spaceused` or `sp_configure` arguments with more than 8 parentheses, are refused at once. The largest single batch, 10 MB, takes 0.1 to 0.33 s to classify in every shape tried (flat one-character tokens, statement lists, a `DROP TABLE` list of 3.3 million names, names, strings, comments, nested calls), but for `ADD ` and one joiner repeated, 0.37 s on 9.4 MB under `--check` (§7), and its work budget (32,000,000 units) is the backstop, 0.4 to 1 s at the rates measured. Decision 30(d)'s scan of `sys.dm_db_index_physical_stats` adds little (a single process run, start to refusal, 2026-11-01, without it and with it): 10 MB of 117,647 scoped calls, 0.22 s and 0.24 s; 123,457 `NULL`, `'LIMITED'` calls, 0.22 s and 0.29 s; 10 MB of `sys.sys.`, 0.26 s and 0.37 s; 10 MB of `SELECT 1` lines, 0.26 s both. 10 MB of calls unclosed, each in the last one's arguments, is refused at its ninth (0.17 s, most of it reading the file), and calls nested to that limit before a 10 MB tail reach the budget (0.62 s). The tests (`tests/cli.rs`, `guard.rs`) bound the process at 5 s, a headroom for debug builds and busy machines, and count the work done instead of timing it.
- **Runtime:** Tokio `current_thread`, with only the features we use enabled in our crate.
- **Lazy setup:** the profile file isn't read when flags alone are enough.
- **Console encoding:** output is always UTF-8 without a BOM, and sqlh never changes the console's code page. When stdout is a console, Rust writes it as UTF-16 (`WriteConsoleW`), which shows correctly under any code page, so nothing needs telling. sqlh used to call `SetConsoleOutputCP(CP_UTF8)` in that case and never put the page back, so every program run afterwards in the same console, a later PowerShell session included, inherited UTF-8, and a kill or an early Ctrl+C could not have been made to restore it. Measured and removed ([notes/windows-shells.md](notes/windows-shells.md)); a test pins it. The one write the switch used to help is raw bytes to a console device (`-o CON`), which the console reads in its own code page, as it would from any program. What a shell makes of sqlh's bytes is in §4.1.

## 12. Testing

- **Unit tests (no server):**
  - batch splitting and `$(var)` handling
  - line mapping
  - argument parsing
  - value rendering and escaping
  - the guard classifier, table-driven, including adversarial cases: keywords hidden in comments or strings, nested brackets, a CTE followed by `UPDATE`, `SELECT INTO`, `EXEC('...')`, nested `TOP (` clauses and the work bound (counting the work done, not timing it)
  - "never panics" property tests for both lexers, over generated input
- **Golden tests:** fixed outputs for text and JSON, `tests/golden/smoke.txt` and `smoke.json` (volatile values normalized: the times, the server's name and version, the database's name, and in JSON each batch's `source`, the script's path, which is the checkout's, written `<repo>/tests/smoke.sql`, so the test passes in any checkout, a worktree's included; `42d8d7c`), checked by the live test `the_smoke_script_matches_its_golden_output` against `tests/smoke.sql`'s representative result sets; `SQLH_BLESS=1` rewrites them. csv has exact-output unit tests (`output/csv.rs`) but no golden file; csv and md golden outputs are planned (md isn't built, §13).
- **Process-level tests** (`tests/cli.rs`): run the real binary, isolated from the machine's profiles and `SQLCMD*` variables, and assert exit codes, files and output: `-o` safety (identity, concurrent runs, files that can't be replaced, devices), exit 7, closed stdout/stderr in every format, the panic net, `--check`, guard blocks and their advice, auth precedence, connect failures (refused, a server that never answers) and Ctrl+Break during a connect, every path form for `-i`, `-o` and `SQLH_CONFIG` (backslashes, forward slashes, relative, UNC, spaces) and the Git Bash hint, piped input in other encodings, the `--help` examples run in cmd.exe and PowerShell, and the console's code page left alone. Tests that need no server use an unreachable address or a local listener that never answers. Ctrl+Break reaches a child started in its own process group, which needs a console shared with the test; `cargo test` run from a terminal has one. They run against the debug and the release binary (`cargo test --release --test cli`); the panic-injection tests exist only in debug builds.
- **`sqlh mcp`** (§10): protocol and schema unit tests in `src/mcp`, process tests through the real binary (`tests/cli.rs`, `mcp::`), engine tests against a pooled fake TDS server (`src/engine.rs`, on `db::fake_server::serve_pool`), which plays the faults a pool meets on loopback, and live tool tests through the real binary against the test server (`tests/cli.rs`, `live::mcp_tools`, 5.4); and, by hand, real clients: OpenCode 2.0.26 with a local model, in the legacy era, and the MCP Inspector 2.11.0 in both (5.5, 2026-10-20 and 21). mcp-mode.md §9 lists them and what isn't covered yet.
- **Live tests:** the `live` tests in `tests/cli.rs` are `#[ignore]`d, so a plain `cargo test` reports them as ignored rather than passing. Run them with `cargo test --test cli -- --ignored live` and `SQLH_TEST_PROFILE` naming a profile on the dev box; asked for without it, they fail. They use the scratch database `sqlh_test` (default; override with `SQLH_TEST_DATABASE`), created by `tests/fixtures/sqlh_test.sql` and removed by `tests/fixtures/drop_sqlh_test.sql`. A test that writes first checks the database's `dbo.sqlh_scratch` marker, then writes only to a table of its own, which it drops. The one exception is `sqlh_test`'s compatibility level, which `describe_shows_any_name_from_compatibility_level_110` sets and puts back (owner decision 21, PLAN.md §6): every live test holds a file lock in the temp directory, shared (`target()`), so the debug and release runs and another checkout's can share the database, and the level test holds it alone (`target_alone()`) while the level is changed; once per test process, before any live test takes the lock, a level a killed run left changed is put back (`hold_scratch`). Planned coverage (plan-history.md 3.4):
  - every data type
  - multiple result sets
  - PRINT and RAISERROR at severities 0–10 and 11–16
  - error line mapping and rows affected
  - query timeout and attention, including `-t` over a result read as fast as it is sent, a large value, and a loop of many small results (R15)
  - a session that starts with `XACT_ABORT` ON (R14): debug builds only, through `SQLH_DEBUG_SESSION_PREFIX`, SQL sent ahead of the session setup in the same batch (like `SQLH_DEBUG_PANIC` and `SQLH_DEBUG_STOP_HOLD_MS`, it does not exist in release builds)
  - the work of sqlh's own in the row and chunk loops (R15): debug builds only, `SQLH_DEBUG_ROW_WORK_US` makes `count_rows` and `large_value` spend that many microseconds per row and per chunk after reading it, so a ready stream outlasts `-t` (the real loops, not a model of them)
  - `profiles add`'s connection-test time (decision 77): debug builds only, `SQLH_DEBUG_ADD_HOLD_MS` makes `add` wait that long before its edit, in place of the password prompt, so a test can check the test's status line leaves it out
  - very long values
  - the guard's transaction backstop
- **Compatibility:**
  - check each release's imports with `dumpbin /dependents`
  - validate the first release on a clean Windows 11 x64 workstation against a remote SQL Server 2025 Standard, including supported authentication and cancellation paths
  - run the smoke script and the live tests against the owner's SQL Server 2016 SP3 instance too (decision 49); assess a Windows 10 / Windows Server 2016 floor for the client separately, including its maintenance cost
  - other versions and Azure may be tested opportunistically; those results do not establish an unqualified support promise

## 14. Open questions and risks

- **Name.** Settled 2026-10-12: sqlh, repository `tkwj/sqlh`, now `sequeltom/sqlh` (the owner's account renamed, 2026-11-07; PLAN.md §6.8). "sqlharness" collided with an active project in the same space. The name reads as "SQL for harnesses": a tool that agent harnesses (Claude Code, OpenCode and the like) call, not a harness itself, which is the runtime that drives the model. The README's first sentence says so (decision 82); "SQL harness" isn't used as a name, since it reads as the colliding one.
- **mssql-tds maturity.** We pin 0.4.0 (from 0.3.0 on 2026-11-08, the last driver for 0.1.0 by owner decision 70; what changed is in `docs/notes/driver-0.4.0.md`; from 0.2.0 to 0.3.0 on 2026-10-31, `docs/notes/driver-0.3.0.md`); size, imports, and SQL Server 2025 data rendering checks are recorded in `docs/notes/m0-driver-spike.md`. First-release validation still needs supported authentication, reliable attention/cancellation, and a clean Windows 11 workstation deployment. Older-server negotiation and Azure redirection are future compatibility questions.
- **Compatibility cost.** SQL Server 2016 SP3 is supported for reading (decision 49), so a change that breaks 2016 is a defect, caught by the live tests on the 2016 instance. Assess a Windows 10 / Windows Server 2016 client floor without letting it complicate or delay the first release. SQL Server 2012/2014 are not targets, and Azure follows its own plan. Supporting any expansion needs explicit tests and an acceptable maintenance budget.
- **Exact row counts.** Settled by owner decision 6 (PLAN.md §6, plan-history.md task 2.15): a read-only run counts the rows it does not show for about 250 ms and reports a lower bound, and `--exact-count` reads them all (§4.4). Decision 45 (2026-10-31, from real-environment feedback) gives a batch whose later statements could produce output 5 s, so they run, and a run that still loses them ends `-- partial:`. What is left is whether these budgets are right, which is for the agent evaluations and real sessions to say (PLAN.md Phase 7).
- **Command categorization.** Develop the policy around legitimate DBA workflows and excessive database privileges. The current classifier is an initial implementation, and database permissions remain the enforcement boundary. Owner direction (2026-10-10): the EXEC allowlist must grow to cover read-only server-state procedures such as `xp_readerrorlog` and `xp_instance_regread`, and others where the login's permissions allow them; that interim step is built (§7, 2026-10-23), and the categorization itself is open (PLAN.md, Phase 6).
- **ARITHABORT.** SSMS sets it ON, while ODBC and ADO.NET apps leave it OFF, so plans can differ ("fast in SSMS, slow in the app"). Consider an `--app-settings` switch for performance investigations.
- **Environments.** The owner's existing test server is reached through a local profile; details stay outside the repo. Release validation needs a clean Windows 11 x64 workstation and a SQL Server 2025 Standard server reached over the network. A SQL Server 2016 SP3 instance of the owner's carries the 2016 tests (decision 49).
- **Code signing.** Built: the release workflow signs `sqlh.exe` (plan-history.md 3.6; a valid, timestamped signature on the draft pre-release `v0.1.0-dev.1`, 2026-10-15). What SmartScreen and antivirus make of the signed exe on a locked-down workstation is still to check, on the first-release checklist (PLAN.md §7); a new exe, even signed, can trip them there.
